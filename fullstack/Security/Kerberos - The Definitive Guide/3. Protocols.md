## El Protocolo Needham-Schroeder

Roger Needham y Michael Schroeder, del Xerox Palo Alto Research Center, publicaron un artículo en Diciembre de 1978 describiendo su marco para diseñar un seguro sistema de autenticación de red. El artículo, titulado "Uso del cifrado para Autenticación en grandes redes de ordenadores", describió dos diferencias Protocolos que pudieran implementarse para proporcionar un sistema fiable y seguro servicio de autenticación para una red distribuida de ordenadores. La primera El protocolo descrito en el artículo utiliza cifrado de clave privada, y es este protocolo que forma la base de la red Kerberos protocolo de autenticación.

Needham y Schroeder expusieron varias suposiciones en torno a las cuales diseñaron su protocolo. Una suposición, la capacidad para un atacante malicioso para capturar paquetes en tránsito en la red, modificar ellos, y enviar paquetes de su propio diseño, fue descrito por los autores como una "visión extrema", pero ahora se considera un requisito rutinario para Cualquier protocolo de red seguro. Diseñar un protocolo que sea resistente a este tipo de ataques es difícil, y señalaré los específicos decisiones de diseño que se tomaron para frustrarlas, mientras discuto el protocolo.

Sin embargo, otras suposiciones hechas por los autores no se sostuvieron como bueno, en la práctica, como en el papel. La suposición de que los usuarios secretan Las claves no están fácilmente disponibles mediante una búsqueda exhaustiva no se ha cumplido en los entornos hostiles donde opera Kerberos. No importa cómo Mucha educación que proporcionas a los usuarios, los usuarios seguirán eligiendo la pobreza Contraseñas. El protocolo Needham-Schroeder, y en consecuencia el básico El protocolo Kerberos no ofrece protección contra una fuerza bruta offline o un ataque de diccionario contra la clave secreta de un usuario, como veremos en [el capítulo 6](https://learning.oreilly.com/library/view/kerberos-the-definitive/0596004036/ch06.html "Chapter 6. Security").

El protocolo Needham-Schroeder define tres participantes en el Intercambio de protocolos: una máquina cliente, un servidor que el cliente desea Acceso y un servidor de autenticación. El cliente es cualquier máquina que solicita autenticación; Normalmente, es el escritorio personal del usuario. El Servidor es cualquier servidor de aplicaciones, por ejemplo un servidor de correo, que proporciona un el servicio que el cliente desea contactar. Finalmente, el servidor de autenticación es un servidor dedicado que almacena una copia de las claves de cifrado de todos usuarios y servidores en la red (el "tercero de confianza"). Esto debería sonar familiar; Estos son los mismos tres jugadores implicados con el protocolo Kerberos.

El concepto detrás del protocolo Needham-Schroeder no es autentica directamente al usuario enviando una contraseña o contraseña equivalente (como un hash de la contraseña) a la autenticación servidor. En su lugar, el protocolo Needham-Schroeder proporciona un mecanismo para distribuir de forma segura una clave de cifrado de corta duración a dos partes (a cliente y servidor) para que su comunicación pueda ser segura con el Clave de cifrado. La verificación de la identidad de cada punto final ocurre con Sería un efecto secundario de este proceso de intercambio de claves. Veremos qué significa esto mientras discutimos cómo funciona el protocolo.

El protocolo comienza con el cliente contactando con la autenticación servidor. El cliente envía al servidor de autenticación un mensaje que contiene su propia identidad y la identidad del servidor de aplicaciones que desea contactar. Además, el cliente incluye un nonce, o un aleatorio valor, con su petición. Veremos por qué este valor aleatorio es importante en un momento. El servidor de autenticación recibe esta información y localiza las claves secretas de cifrado que almacena tanto para el cliente como para el cliente servidor de aplicaciones. También crea una tercera clave, la clave _de sesión_, que puede usarse para permitir una comunicación segura entre el cliente y el servidor de aplicaciones. Esta nueva clave es aleatoria generado por el servidor de autenticación, es completamente ajeno a la claves a largo plazo tanto del cliente como del servidor, y nunca es reutilizado.

A continuación viene la parte complicada. En el protocolo Needham-Schroeder, el El servidor de autenticación nunca se comunica directamente con la aplicación servidor, solo el cliente. Por lo tanto, el servidor de autenticación envía un Responde al cliente que incluye la clave de sesión y el Verified identidades de ambas partes. Pero, ¿cómo se puede mantener este mensaje a salvo de un observador que está observando el tráfico de red para conseguir estas claves de sesión ¿a medida que pasan por el cable? Y además, cuando el cliente transmite la clave de sesión y su identidad al servidor de aplicaciones, ¿cómo sabe el servidor de aplicaciones que el cliente no miente, y ¿Que el mensaje es auténtico?

La respuesta implica varias capas de cifrado. Primero, un mensaje está construido que está destinado a ser visto solo por la aplicación servidor. Este mensaje incluye el nombre del cliente solicitante y el clave de sesión. Para mantener este mensaje seguro y evitar escuchas ocultas y Manipulado por un cliente malicioso, se cifra con la clave a largo plazo del servidor de aplicaciones. Dado que solo el servidor de aplicaciones y el El servidor de autenticación conoce esta clave, un atacante no puede descifrarla para alterar el contenido o robar la clave de sesión. En Kerberos Terminología, este mensaje cifrado también se conoce como _ticket_ .

El mensaje está envuelto dentro de otro mensaje, este Destinado al cliente. El mensaje del cliente también incluye el nombre de el servidor de aplicaciones, una copia de la clave de sesión y una copia de la Nonce envió originalmente en el primer mensaje. El mensaje completo es entonces Cifrado con la clave a largo plazo del cliente. Una vez que toda la información ha sido ensamblado y cifrado, el servidor de autenticación lo envía al cliente ([Figura 3-2](https://learning.oreilly.com/library/view/kerberos-the-definitive/0596004036/ch03s01.html#kerberos-CHP-3-FIG-2 "Figure 3-2. Needham-Schroeder authentication reply")).

Needham-Schroeder, Kerberos y cajas cerradas

Es fácil confundirse con todo el cifrado que es ocurriendo en el protocolo Needham-Schroeder (y, en consecuencia, en el Protocolo Kerberos). Ya que a menudo hay múltiples capas de Encriptación en acción, es útil tener una analogía del mundo real para relacionar al hablar de estos intercambios de protocolos.

Una buena analogía en este caso es un conjunto de cajas cerradas, anidadas dentro el uno del otro. Las claves de cifrado pueden considerarse como de la vida real Llaves que pueden abrir estas cajas. Así que, en esta analogía, el usuario La contraseña puede traducirse a una clave física. Dos copias de esa clave existir: el usuario tiene una copia, y el servidor de autenticación tiene Otra copia. La misma situación se aplica a las claves de servicio: cada una El servidor de aplicaciones tiene dos claves idénticas, una que tiene el servidor a sí mismo, y al otro que poseen los servidores de autenticación. Cajas cerradas con llave con la clave del usuario puede desbloquearse con una copia de la clave del usuario, y Lo mismo con la llave de servicio.

La [figura 3-3](https://learning.oreilly.com/library/view/kerberos-the-definitive/0596004036/ch03s01.html#kerberos-CHP-3-FIG-3 "Figure 3-3. Needham-Schroeder authentication reply represented as locked boxes") muestra el Respuesta del servidor de autenticación a la solicitud de autenticación de un cliente. La segunda caja (la _caja de respuesta_) contiene la otra copia de la sesión y está bloqueada con la llave del usuario. Además, la primera caja, Con la llave del servicio, se coloca dentro de la segunda caja. Por Colocar la caja de tickets dentro de la caja de respuesta, la autenticación El servidor garantiza que solo el usuario legítimo pueda desbloquear la respuesta en para obtener el ticket, ya que solo el usuario tiene una clave que puede abrirse La respuesta.

Cabe señalar que el servidor de autenticación no sabe si el El cliente solicitante es en realidad quien dice ser. La autenticación El servidor devolverá este mensaje cifrado a quien lo solicite, siempre que, por supuesto, el nombre del cliente exista en la autenticación la base de datos de claves de cifrado del servidor. Esto parece indicar que cualquier El usuario podía hacerse pasar por cualquier otro usuario al solicitar la autenticación a un servicio arbitrario. Sin embargo, dado que el mensaje está cifrado con la clave del cliente, no puede ser descifrada por nadie más que por el legítimo cliente.

Por lo tanto, cuando el cliente recibe esta respuesta de la servidor de autenticación, primero descifra la capa "externa" con su clave (la contraseña del cliente). Se le pide a la usuaria su contraseña. Si el la contraseña no logra descifrar el mensaje, luego la solicitud de autenticación ha fracasado.

Ahora solo queda que el cliente devuelva la clave de sesión al servidor de aplicaciones ([Figura 3-4](https://learning.oreilly.com/library/view/kerberos-the-definitive/0596004036/ch03s01.html#kerberos-CHP-3-FIG-4 "Figure 3-4. Client sends session key to application server")). Aquí es donde llegan los contenidos internos del último mensaje en juego. Ahora que el cliente ha eliminado la primera "capa" de Cifrado, el cliente puede enviar al servidor de aplicaciones la parte interna del mensaje (el ticket), que consiste en una copia de la clave de sesión y el nombre del cliente. Dado que este mensaje sigue cifrado con el la clave del servidor de aplicaciones, solo el servidor de aplicaciones puede leerla, y los atacantes no pueden modificarlo.

A estas alturas, parece que hemos terminado; Cualquier comunicación que ocurre a partir de entonces que se cifra con la clave de sesión debería Solo debe ser entendido por el cliente y el servidor de aplicaciones. El cliente sabe que el servidor de aplicaciones es legítimo ya que solo el El servidor de aplicaciones legítimo puede descifrar el mensaje que contiene el clave de sesión (ya que está cifrada con la clave a largo plazo de la servidor de aplicaciones). El servidor de aplicaciones sabe que el cliente es legítimo porque solo el cliente legítimo podía descifrar el mensaje que contiene la clave de sesión e identidad del cliente que fue reenviado al servidor de aplicaciones.

Sin embargo, hay un ataque más que se puede emprender contra Este esquema, y aquí es donde surge el nonce que mencionamos antes en juego.

Veamos la situación que se presenta a un Atacante que desea hacerse pasar por un cliente, para que el atacante pueda Comunicarse con un servidor de aplicaciones bajo la apariencia de la víctima Identidad. Asumiremos que el atacante tiene la capacidad de leer todos mensajes de red y enviar mensajes de su propia creación, pero no lo hace tener conocimiento de la clave a largo plazo del cliente o del servicio (que Obviamente, le permitiría hacerse pasar por la víctima sin ninguna engaño).

Dado que todos los intercambios de protocolos anteriores son simplemente electrónicos mensajes enviados a través de una red insegura, que el atacante logra adquirir el mensaje de autenticación enviado desde una víctima al servidor de aplicaciones (el mensaje que contiene la clave de sesión y la identidad de la ambos cifrados con la clave del servidor de aplicaciones). El atacante simplemente puedes reenviar ese mensaje más adelante a la aplicación servidor. Dado que el mensaje puede ser descifrado por el servidor de aplicaciones, generando una clave de sesión válida e identidad (de la víctima), entonces es aceptada como legítima y la sesión se autentica. Mientras que el El atacante no conoce la clave de sesión, si el servidor de aplicaciones solo utiliza el protocolo para asegurar la autenticación y no utiliza la sesión clave para cifrar sus comunicaciones con los clientes, entonces el atacante puede Hacerse pasar por la víctima por completo.

Estos ataques se conocen como _repetición y_ el protocolo Needham-Schroeder proporciona un más bien Solución obvia para frustrar estos ataques: obligar al cliente a demostrar El servidor de aplicaciones que realmente conoce la clave de sesión. Que hacer Esto, el servidor de aplicaciones genera otro número aleatorio, cifrando Con la clave de sesión y la envía al cliente. Luego el cliente descifra el número, realiza una operación sobre él (por ejemplo, sumando uno a él), cifra el nuevo número con la clave de sesión y envía el mensaje de vuelta al servidor de aplicaciones. A través de este proceso, solo Los clientes auténticos que conocen la clave de sesión pueden enviar de vuelta el número correcto, y los observadores que reproducen mensajes anteriores no pueden ([Figuras 3-5](https://learning.oreilly.com/library/view/kerberos-the-definitive/0596004036/ch03s01.html#kerberos-CHP-3-FIG-5 "Figure 3-5. Needham-Schroeder replay attack prevention")).

Aquí vemos uno de los muchos problemas prácticos presentados cuando Se asume que los atacantes tienen la capacidad de leer toda la red así como enviar mensajes arbitrarios en la red. El protocolo Needham-Schroeder utiliza un sistema interactivo sistema de desafío-respuesta que requiere que el cliente demuestre que Conoce la clave de la sesión. El protocolo Kerberos utiliza una versión ligeramente diferente Enfoque—basado en relojes sincronizados—para frustrar la repetición, como veremos en La siguiente sección. ## Kerberos 4

El protocolo Kerberos 4 se basa en gran medida en el Protocolo Needham-Schroeder, con dos cambios importantes.

Los hosts implicados en los intercambios de protocolos Kerberos 4 se corresponden directamente con el los principales implicados en el protocolo Needham-Schroeder. El el cliente de autenticación es una estación de trabajo de usuario Kerberos 4, y el El servidor de autenticación se asigna a una distribución de claves de Kerberos 4 Centro.

El primer cambio en el protocolo Needham-Schroeder redujo el cantidad de mensajes de red enviados entre el cliente y el servidor de autenticación. El protocolo original Needham-Schroeder no Depender de una fuente de tiempo de red, pero el coste era un extra Dos intercambios de mensajes. Los dos últimos intercambios de mensajes en el El protocolo Needham-Schroeder establece que no hay hombre en medio haciéndose pasar por el servidor de autenticación, y que la clave de sesión no es un repetición. En el protocolo Kerberos 4, la repetición se ve frustrada mediante un mensaje autenticador que se construye a partir de la hora local del cliente cifrado con la clave de sesión recién negociada del conexión. Aunque esto requiere sincronización temporal entre todos los hosts De hecho, reduce el número de mensajes de red requeridos por Intercambio de autenticación.

El segundo cambio, más significativo, en el protocolo básico crea el concepto de Ticket de Emisión de Tickets, que permite a los usuarios autenticarse a múltiples servidores de aplicaciones mientras introducían su autenticación secreto solo una vez. Si el protocolo original de Needham-Schroeder fuera Implementado tal cual, un usuario tendría que introducir su contraseña cada vez que desea iniciar sesión en un servidor de aplicaciones. Uno de los principales Los objetivos de diseño de Kerberos eran crear un sistema de inicio de sesión único en el que los usuarios solo tuvieran que ingresar sus credenciales una vez al día y todas las futuras solicitudes de autenticación se gestionan de forma transparente, sin intervención del usuario.

Como resultado, el protocolo Kerberos 4 se divide en dos lógicas componentes: el Servidor de Autenticación y el Servidor de Concesión de Tickets. Ten en cuenta que hay un desafortunado Choque de terminología aquí. El Servidor de Autenticación Kerberos no debe confundirse con el servidor de autenticación Needham-Schroeder; el primero realiza un subconjunto de los servicios de estos últimos, como veremos en un momento. Para mantener el distinción clara, referencias al Servidor de Autenticación Kerberos y El servidor de concesión de tickets se escribirá en mayúscula o abreviará como AS o TGS, respectivamente. Aunque estos componentes suelen implementarse como un solo programas que se ejecutan en el KDC, son lógicamente separados procesos.

Otros cambios reflejan la realidad de la seguridad de Las redes informáticas actuales. El protocolo original de Needham-Schroeder se suponía que todos los secretos implicados, incluida la clave a largo plazo del usuario, la clave a largo plazo del servidor de aplicaciones, y la clave de sesión, es decir, generados aleatoriamente por el KDC, siempre se mantienen en secreto. En realidad, Las máquinas están comprometidas y la gente da sus contraseñas. En además, la capacidad de inicio de sesión único proporcionada en Kerberos 4 significa que que las estaciones de trabajo de los usuarios tendrán credenciales en caché que, si se mantienen desprotegido, puede ser utilizado por un atacante para hacerse pasar por el usuario. Por ello, Kerberos 4 introduce una vida útil limitada para las credenciales, impuesta por el KDC y Kerberos Bibliotecas. Sin caducidad del ticket, un usuario podía iniciar sesión una vez, y Nunca más tener que iniciar sesión (siempre que sus credenciales nunca lo sean eliminado de la estación de trabajo). Las vidas útiles aseguran que los usuarios deben verificar su identidad periódicamente—por ejemplo, una vez al día—introduciendo su contraseña otra vez. También cierran la ventana de vulnerabilidad en caso de robo Credenciales.

### El servidor de autenticación y la concesión de tickets Servidor

El Servidor de Autenticación realiza una función: recibir una solicitud que contiene el nombre de usuario del cliente que solicita autenticación, y devolver un Ticket Concededor de Tickets cifrado para ese usuario. Luego, el cliente puede usar este Ticket Granting Ticket (el TGT) para solicitar más información entradas para otros servicios.

Cuando un cliente no tiene tickets de Kerberos almacenados en caché, o tickets que han expirado, entonces el cliente debe comunicarse con la Autenticación Servidor para obtener un ticket inicial al Servidor de Concesión de Tickets. Esto suele ocurrir en el al inicio de cada día, como la mayoría de las implementaciones de Kerberos por defecto Una duración de billetes de 8-10 horas.

El primer mensaje enviado al KDC de Kerberos desde el cliente es la Solicitud del Servidor de Autenticación mensaje, también conocido como AS_REQ mensaje. Este mensaje se envía en texto plano, que contiene la identidad del cliente, la hora local del cliente y el nombre principal del Servidor de Concesión de Tickets. Por convención, en Kerberos 4, el nombre principal del servidor que otorga tickets, es _krbtgt_. Además, el principio del servidor de emisión de tickets siempre tiene un componente de instancia. El componente de instancia es el reino para lo cual el servidor que otorga tickets puede emitir más tickets. Cada reino contiene al menos un Servidor de Concesión de Tickets, un TGS con una instancia del propio reino. Por ejemplo, el Ticket Conceder Server para el reino WEDGIE.ORG es _krbtgt.WEDGIE.ORG@WEDGIE.ORG_.

Un caso especial ocurre cuando dos o más reinos confían mutuamente Usuarios y servicios. Esta relación, conocida como _fideicomiso_ entre reinos, requiere que se establezcan principales TGS especiales en todos reinos participantes, con diferentes componentes de instancia que representan los diferentes reinos. No hablaremos más sobre el interreino aquí; En su lugar, volveremos y exploraremos la implementación del sistema entre reinos autenticación en [el capítulo 8](https://learning.oreilly.com/library/view/kerberos-the-definitive/0596004036/ch08.html "Chapter 8. Advanced Topics").

Una vez que el KDC recibe el mensaje AS_REQ, verifica que el existe el principal solicitante y que la marca temporal del cliente está cerca a la hora local de la KDC (normalmente esto significa dentro de cinco minutos). Esto se realiza una comprobación para no detectar repeticiones; al fin y al cabo, el mensaje AS_REQ es Enviado completamente en texto claro. En su lugar, realiza la comprobación de la marca de tiempo para que los clientes puedan proporcionar a los usuarios un mensaje temprano en el proceso de autenticación en caso de un desajuste temporal entre los cliente y el KDC. Si alguna de estas comprobaciones falla, aparece un mensaje de error se envía de vuelta al cliente y este no está autenticado.

A continuación, el Servidor de Autenticación genera una clave de sesión aleatoria. Esta clave de sesión será compartida entre el cliente y el Servidor que concede tickets. Esta clave asegura las solicitudes de tickets que el el cliente hace referencia al Servidor de Concesión de Tickets más adelante para obtener un objetivo específico Servicios kerberizados. El KDC realiza dos copias de esta clave de sesión: una para el cliente, y otro para el servidor de concesión de tickets.

El KDC responde con un mensaje de Respuesta del Servidor de Autenticación, o mensaje AS_REP. Este mensaje incluye la información anterior — lo más importante, una copia de la clave de sesión y la identidad verificada del cliente cifrado con la clave del servidor que concede tickets y otra copia de la clave de sesión cifrado con la clave a largo plazo del usuario. Mientras el cliente lo haya hecho conocimiento de la clave a largo plazo del usuario, entonces el cliente puede descifrar la el mensaje cifrado con la clave del usuario y obtener la clave de sesión ahora compartido entre el cliente y el servidor de concesión de tickets. El conocimiento de esta clave de sesión y la posesión del Ticket Conceder un ticket (la otra copia de la clave de sesión, cifrada con el Clave del servidor que concede tickets) permiten al cliente obtener tickets para Servicios adicionales de Kerberos sin necesidad de que el usuario vuelva a introducir su contraseña.

Esto implica que la seguridad de tu sistema Kerberos es muy alta Depende de las contraseñas que elijan tus usuarios. Desde la autenticación El servidor devolverá encantado un ticket cifrado que concede un ticket válido para cualquier principal para cualquier cliente, la única línea de defensa contra Atacantes es una contraseña fuerte. Una vez completada la transacción del Servidor de Autenticación, el El cliente posee una clave de sesión, cifrada con la de largo plazo del usuario clave, así como un Ticket de Concesión de Tickets, cifrado primero con el Llave del servidor que concede tickets. El cliente intenta descifrar el mensaje con la clave a largo plazo (contraseña) del usuario. Si esta descifración si tiene éxito, entonces la contraseña es correcta y el cliente almacena la Ticket de Concesión de Tickets, así como su copia de la clave de sesión en un Caché de credenciales. Recuerda que, aunque el cliente haya eliminado el capa externa de cifrado del Ticket de Concesión de Tickets, sigue siendo cifrado con la clave del servidor de emisión de tickets. Por lo tanto, el cliente no puede leer el contenido del Ticket de Concesión de Tickets; en su lugar, simplemente almacena el contenido cifrado en la caché de credenciales.

Cuando el usuario desea autenticarse a un servicio kerberizado más adelante, hay un intercambio de protocolos separado con la Concesión de Tickets Camarero. El cliente prepara un mensaje para el Servidor de Concesión de Tickets Consta de tres partes: una solicitud TGS, una copia del Ticket Concediendo Ticket adquirido antes, y un _autenticador_ que sirve para frustrar la repetición.

El autenticador consiste en una marca de tiempo, cifrada con el clave de sesión adquirida del intercambio de Servidores de Autenticación. El Authenticator garantiza que cada paquete de solicitud de ticket sea único, y también demuestra que el cliente tiene conocimiento de la clave de sesión compartida establecida durante el intercambio de Servidores de Autenticación. Sin el Autenticador, un atacante podría simplemente escuchar en la red para detectar un ticket enviado por el KDC a un cliente legítimo, haz una copia del y rejugar ese ticket al KDC (en el caso de un Ticket de Concesión de Tickets) o un servidor de aplicaciones (en el caso de un Ticket de servicio).

Al recibir la solicitud de ticket del cliente, el KDC formula un mensaje de respuesta que incluye un nuevo conjunto de claves de sesión, compartido entre el cliente y el servidor de aplicaciones. El cliente La copia de la nueva clave de sesión se cifra con la clave de sesión antigua, establecida durante el intercambio de Servidores de Autenticación. Esto garantiza que solo el cliente válido puede leer la nueva clave de sesión para su uso con el servidor de aplicaciones. La copia del servicio de la nueva clave de sesión es Incrustado dentro de un _servicio Ticket_ , cifrado con la clave a largo plazo del servicio. El cliente Añade este ticket de servicio y la nueva clave de sesión a su credencial Guarda en caché para recuperarlo más adelante. Cuando el cliente contacta con la aplicación servidor, el conocimiento de este ticket de servicio y la clave de sesión Demuestra al servicio que el cliente es auténtico. ### String-to-Key Transformation

Kerberos 4 requiere una transformación entre el texto contraseñas que la gente recuerda y la clave DES de 56 bits que en realidad es Usado para cifrar y descifrar los mensajes que se transmiten de vuelta y cuarto entre cliente, KDC y servidor de aplicaciones. Esta transformación se denomina función _de cadena a tecla_, normalmente abreviada simplemente _como string2key_ . La transformación es muy similar a las funciones se usaba para "cifrar" contraseñas en el archivo estándar _Unix /etc/passwd_. Es una función hash unidireccional que, en el caso de Kerberos 4, utiliza la contraseña del director como y emite una clave DES hexadecimal de 56 bits. Dado que la función es Una forma, es matemáticamente muy difícil (leído como imposible) invertir el algoritmo para deducir la contraseña a partir del DES generado clave. Sin embargo, dado que este algoritmo es público (y, de hecho, debe ser Ampliamente conocido para que diferentes implementaciones de Kerberos interoperar), se puede usar un ataque de fuerza bruta o de diccionario para intentar contraseñas para encontrar una clave DES correspondiente a un mensaje concreto.

Los detalles de la función string2key no son especialmente Importante para esta discusión. Si te interesa exactamente cómo se realiza la transformación, la función string2key se incluye en tanto las distribuciones MIT como kth-krb Kerberos 4. Además, KTH-KRB incluye un programa kstring2key que, dado una contraseña como entrada, que genera la clave hexadecimal DES resultante de la string2key Transformación.

### El número de versión clave

El _número_ de versión de la clave, comúnmente abreviado como kvno, distingue entre diferentes claves de cifrado que se almacenan para un principal dado. Por ejemplo, si un usuario cambia su contraseña, luego su director tiene una nueva clave de cifrado asociada con ella. Cuando el KDC de Kerberos almacena su nueva clave de cifrado en el Kerberos, incrementa el número de versión clave. De manera similar, si La clave a largo plazo de un servicio cambia, y también el número de versión de la clave cambios.

Los números de versión clave no son importantes cuando se trata con el usuario directores. Sin embargo, sí se vuelven importantes al trabajar con Servicios kerberizados. Para que los servicios kerberizados puedan Lee el contenido del ticket enviado por los clientes para autenticación, tanto el clave de cifrado y el número de versión de la clave que se almacena en el La pestaña de claves del servicio debe coincidir con la clave de cifrado y el número de versión de la clave que se almacena en la base de datos de Kerberos. Un desajuste en el La clave de cifrado o el número de versión de la clave provocarán el proceso de descifrado fracasar.

### Cambio de contraseña

Las especificaciones originales de Kerberos no incluían disposiciones que lo permitieran los usuarios para cambiar sus propias contraseñas. Sin embargo, la capacidad de los usuarios Cambiar sus contraseñas es un requisito para cualquier práctica esquema de autenticación, por lo que las implementaciones de Kerberos 4 se integraron Protocolos de cambio de contraseña. Como resultado, la mayoría de los paquetes Kerberos 4 Implementa el cambio de contraseña a través de un sistema administrativo separado el mismo protocolo que se utiliza para administrar remotamente el Base de datos Kerberos.

Tanto MIT como kth-krb pasan la contraseña por string2key función en el lado del cliente para evitar enviar incluso el texto cifrado Contraseña a través de la red. Esto tiene la ventaja de no exponer a un contraseña de texto plano a través de la red, pero tiene la desventaja de que todo Las comprobaciones de calidad de contraseña deben implementarse en el lado del cliente, por lo que una Un cliente malicioso que cambia contraseñas podría saltarse todas las comprobaciones de calidad.

Los protocolos administrativos para el MIT y kth-krb difieren, por lo que No hay interoperabilidad entre los servicios de cambio de contraseñas en tampoco. El programa kpasswd de uno no se conectará al Servicio de cambio de contraseña proporcionado por el otro.

## Kerberos 5

Si miras estrictamente el conjunto de características, Kerberos 5 es un evolución de Kerberos 4. El protocolo Kerberos 5 contiene todos los funcionalidad presente en el protocolo Kerberos 4, pero con muchas extensiones. Sin embargo, desde la perspectiva de la implementación, Kerberos 5 es un protocolo completamente nuevo, y no se parece en nada a Kerberos 4 en el dentro. En esta sección, examinaremos las nuevas características presentes en Kerberos 5, así como la nueva infraestructura proporcionada por el protocolo para Haz que estas funciones funcionen.

El protocolo Kerberos 4 tenía su parte de carencias: sí una estructura bastante obtusa (por ejemplo, en lugar de estandarizar sobre una Orden de bytes, tenía una bandera para especificar qué orden de byte se usaba para enviar un mensaje particular) y no era ampliable, ya que muchos de sus campos tenían tamaños fijos. Esta limitación provocó otros problemas, especialmente el dependencia de claves de cifrado de un solo DES. En la época en que se desarrolló Kerberos 4 desarrollado, un ataque de fuerza bruta contra DES seguía siendo prohibitivo caro tanto en recursos como en tiempo. Como velocidad de ordenador sigue creciendo exponencialmente, ahora está dentro del ámbito de adversarios bien financiados para lanzar un ataque de fuerza bruta contra el DES. Por lo tanto, un algoritmo de cifrado más seguro con un cifrado más largo Se necesita el tamaño de la llave. Desafortunadamente, dado que todos los campos en Kerberos 4 son de tamaño fijo, no hay forma de adaptar Kerberos 4 con otro algoritmo de cifrado.

Otra función que tanto usuarios como administradores exigían una nueva versión de Kerberos era el soporte para el envío y delegación de credenciales. Credencial El reenvío permite a los usuarios transferir sus tickets a un servidor remoto Una vez que estén autenticados. Por ejemplo, tomemos a un usuario que simplemente ha iniciaba sesión remotamente en un servidor de aplicaciones mediante telnet kerberizado. Usando Kerberos 4, si el usuario desea autenticarse, por ejemplo, en un servidor de archivos, Desde el servidor de aplicaciones, está prácticamente atascada. Debe volver a iniciar sesión a Kerberos desde el servidor remoto a través de kinit para adquirir un nuevo Ticket Concediendo el ticket en el servidor remoto. Esto introduce problemas de seguridad, ya que para volver a autenticarse a Kerberos, el usuario debe reescribirla contraseña, que en el caso de Telnet probablemente se está enviando en claro Mensajes por la red. Además, el sistema ya no proporciona Inicio de sesión único.

Kerberos 5 introduce soporte para el reenvío de credenciales para que en El ejemplo anterior, cuando el usuario inicia sesión en la aplicación remota su Ticket de Concesión de Tickets se transmite de forma segura al control remoto y puede ser utilizado por aplicaciones en ese servidor remoto hasta autenticarla de forma transparente para otros servicios de Kerberos.

Sin embargo, con estas mejoras y extensibilidad llegan complejidad. Para crear un protocolo extensible que pueda ser implementado en múltiples plataformas por varios proveedores, y asegurar que todas estas implementaciones pueden interoperar, el desarrollo de Kerberos el equipo eligió utilizar una tecnología conocida como ASN.1 para describir su nueva Protocolo Kerberos 5. ASN.1 permite a los diseñadores de protocolos crear protocolos con un lenguaje abstracto, automatizando los detalles de implementación y Permitiendo futuras extensiones. Hablaremos más sobre ASN.1 y cómo ASN.1 se utiliza para definir los mensajes del protocolo Kerberos 5 en un un poco.

Kerberos 5 se esfuerza por ser lo más compatible posible con clientes y aplicaciones antiguos servidores lo más posible. Para asegurar la compatibilidad con el antiguo software de Kerberos 4, Kerberos 5 proporciona el servicio de traductor de billetes Kerberos 5 a Kerberos 4 (comúnmente conocido como krb524). Este servicio acepta un ticket válido de Kerberos 5 como entrada (el único requisito es que los tipos de cifrado de tickets y claves de sesión son single-DES, ya que ese es el único cifrado tipo soportado en Kerberos 4) y crea un ticket válido de Kerberos 4 como salida. Utilizando el krb524 daemon, una organización puede incorporar servicios antiguos de Kerberos 4 en un sistema más moderno Infraestructura de Kerberos 5.

El protocolo Kerberos 5 está en constante revisión y desarrollo. La página principal de Kerberos en [http://www.kerberos.isi.edu](http://www.kerberos.isi.edu/) es la página oficial de las Aclaraciones de Kerberos, un nuevo conjunto de documentos que se están redactando para sustituyen al actual RFC 1510. Los documentos de Aclaraciones de Kerberos se considera la fuente definitiva de información sobre el Kerberos protocolo.

### El tutorial ASN.1 más corto del mundo

ASN.1 es un acrónimo de Abstract Syntax Notation One. Es define una metodología para describir definiciones de protocolos en un notación abstracta, y luego proporciona varios métodos para convertirlos definiciones abstractas en un flujo de bytes para transmisión sobre una red de comunicaciones. Varios protocolos utilizan ASN.1 para definir su protocolos; junto con Kerberos 5, SNMP y LDAP son protocolos populares que usan ASN.1.

Como vimos antes con la definición del protocolo Kerberos 4, La extensibilidad es un atributo importante al diseñar protocolos. No el protocolo permanece estático; es mucho más eficiente tanto para el implementador y usuarios si un protocolo tiene hacia adelante y hacia atrás compatibilidad desde el principio. Un diseño y código manuales el diseño de protocolos como el de Kerberos 4 es muy difícil de añadir a posterior, salvo que se tome un cuidado extremo durante el diseño de la Protocolo inicial. Además, la codificación manual de la codificación en red y los módulos de decodificación conducen a errores que luego provocan problemas con Interoperabilidad cuando las nuevas implementaciones deben adaptarse o adaptarse A errores en la implementación inicial. ASN.1 puede ayudar con ambos estos problemas.

ASN.1 proporciona una gramática con la que los diseñadores de protocolos pueden Describe el protocolo de una aplicación. ASN.1 también proporciona varios tipos incorporados como ENTERO, que representan un entero arbitrario y CADENA OCTETO, que representa una cadena de caracteres. Por encadenando estos tipos básicos para construir tipos más complejos, Los implementadores pueden diseñar lo que se denomina la _sintaxis_ abstracta de su protocolo, es decir, una descripción textual de El protocolo en una forma fácilmente analizable. La gramática utilizada para describir esta sintaxis abstracta es similar a la BNF (Forma Backus-Naur) comúnmente usada para describir lenguajes informáticos. Aquí tienes un ejemplo de definición de ASN.1:

```c#
   Realm ::=           GeneralString
   PrincipalName ::=   SEQUENCE {
                       name-type[0]     INTEGER,
                       name-string[1]   SEQUENCE OF GeneralString
   }
```
Estas son las dos definiciones ASN.1 en Kerberos 5 que definen las partes de un director de Kerberos 5. La definición de Reino es bastante justa directo; Un reino puede definirse como una cadena de caracteres. El PrincipalName consiste en un tipo (que indica un estilo de nombre—Querbero 5 define varios, incluyendo el tradicional nombres de estilo Internet en forma de user@REALM y X.500) y un secuencia ordenada de cadenas, que representa los componentes de la Director de Kerberos. Con Realm y PrincipalName definidos, futuro ASN.1 Las definiciones pueden usar estos tipos en estructuras más complejas, como una estructura de billetes o estructura del autenticador.

Ahora que tenemos esta sintaxis abstracta, necesitamos alguna forma transmitir y recibir datos que se ajusten a nuestra sintaxis. Por ejemplo, si queremos enviar y recibir un conjunto de PrincipalNames sobre el Necesitamos algún tipo de regla que especifique cómo codificar cadenas, enteros y secuencias de cadenas (queremos asegurarnos de obtener ¡Las cosas en el orden correcto también!). Resulta que hay varias diferentes estándares relacionados con la codificación de datos ASN.1 para transmisión, pero la que usa Kerberos es la Regla de Codificación Distinta, o DER. DER toma un ASN.1 estructura de datos—por ejemplo, un PrincipalName con sus campos rellenados por un aplicación—y lo convierte en _transferencia sintaxis_ , o una serie de bytes que pueden enviarse a otro que habla el mismo protocolo basado en ASN.1.

No te aburriré con detalles sobre cómo DER hace su trabajo sucio, pero funciona de forma sencilla principio: la llamada regla TLV. TLV se refiere al _tipo_, _longitud_, _valor_: las tres partes de información que se envía para cada campo de datos en una estructura ASN.1. El tipo se refiere a el tipo ASN.1 que representan los datos: se asigna una constante de byte a GeneralStrings como márcalas así, otro byte representa datos ENTEROS, y así sucesivamente. Además, los sellos se pueden añadir a los tipos de cada campo, como indican los corchetes arriba. El Las etiquetas aseguran que el orden de los datos se preserve y que el destinatario pueda Identifica cualquier dato opcional o faltante. La longitud de los datos codificados se envía a continuación, y Por último, los datos en sí. Al enviar toda esta información, un host receptor puede reconstruir la estructura de datos original a partir de la sintaxis de transferencia.

Con una sintaxis abstracta ASN.1 en su lugar, un ASN.1 especializado El compilador puede leer la sintaxis abstracta y generar código de programa que convierte una estructura de datos dada que coincide con la sintaxis abstracta en Transfiere la sintaxis, y viceversa. El compilador ASN.1 automatiza el proceso complicado de crear código para enviar y recibir codificación Mensajes de protocolo, dando al implementador más tiempo para escribir la lógica del programa dedicada a su protocolo.

### El servidor de autenticación y la concesión de tickets Servidor

La idea detrás de los intercambios AS y TGS permanece sin cambios en Kerberos 5. El nombre del Servidor de Concesión de Tickets cambia ligeramente, gracias a las diferentes convenciones principales de nombres en Kerberos 5. Por ejemplo, el nombre principal del servidor de concesión de tickets en Kerberos 5 para el reino WEDGIE.ORG es _krbtgt/WEDGIE. ORG@WEDGIE.ORG_.

Hay algunos detalles a nivel de protocolo que se han modificado en Kerberos 5, sin embargo. Ya hemos hablado de la más importante, es decir, el uso de ASN.1 para describir y codificar formalmente el nuevo protocolo. Además, el otro cambio a nivel de protocolo que se realizó durante el desarrollo de Kerberos 5 se suponía eliminar el doble cifrado que ocurre durante el Servidor de Autenticación y el Ticket Concediendo respuestas KDC del servidor. Recuerda la discusión de la En el protocolo Kerberos 4 mencionado anteriormente, había esencialmente dos capas de cifrado en una respuesta AS o TGS; El ticket, cifrado con la clave del servicio está contenida en un mensaje de respuesta cifrado con la clave del usuario.

Este doble cifrado resulta innecesario, así que Kerberos 5 concatena los dos mensajes cifrados uno tras otro en lugar de Anidando el ticket dentro del mensaje de respuesta. Este paso mejora eficiencia y rendimiento, y no reduce la seguridad de la mensajes. Como los mensajes siguen cifrados con su claves respectivas, son ilegibles para atacantes que no disponen de la claves de cifrado relevantes para descifrar los mensajes.

### Nuevas opciones de cifrado

El nuevo soporte para múltiples tipos de cifrado en Kerberos 5 también significa que puede haber más de uno tipo de cifrado utilizado en una transacción determinada del protocolo Kerberos. A Se puede usar un tipo de cifrado separado en cada uno de los siguientes Mensajes:

> [!Ticket]
> El tipo de cifrado asociado al ticket es el tipo de cifrado utilizado para cifrar el ticket de servicio en el Responde TGS o AS. Dado que el ticket solo puede ser descifrado por el servicio, ya que está cifrado con la clave de cifrado del servicio, El tipo de cifrado de tickets se determina por la mayor intensidad Cifrado soportado por el servicio para el que se encuentra el ticket emitido.

> [!Response]
> El tipo de cifrado de la respuesta del KDC a la cliente se refiere a la parte de la respuesta cifrada con la del usuario Clave de cifrado. Dado que el cliente debe descifrar la respuesta, el El tipo de cifrado de respuesta se determina por la mayor intensidad cifrado que soporta el cliente.

> [!Clave de sesión]
> Dado que la clave de sesión se comparte entre el cliente y el servidor de aplicaciones, el tipo de cifrado de la sesión clave es el algoritmo de cifrado de máxima potencia, es decir, Apoyado tanto por el servicio como por el cliente. Por ejemplo, si el cliente soporta DES simple y triple, pero solo el servicio soporta un solo DES, luego el KDC emitirá una sola sesión DES Llaves para este servicio.

### Opciones de entradas

Kerberos 5 incluye funciones avanzadas que permiten a los usuarios más control sobre sus entradas para Kerberos. Las siguientes banderas han se ha añadido a Kerberos 5:

> [!Forwardable tickets]
> Un usuario puede solicitar un ticket _reenviable_. Un ticket reenviable puede reenviarse a otro host más adelante—de ahí el nombre—y el ticket es válido para Úsalo en el nuevo anfitrión. Un caso especial común es el trasladable Multa para conceder multas. Se puede reenviar un TGT reenviable a otro anfitrión, y el TGT original puede usarse para adquirir un nuevo TGT en el host objetivo, sin que el usuario tenga que introducir su Contraseña de nuevo. Por ejemplo, si un usuario inicia sesión en un host usando la autenticación Kerberos, el usuario ahora debe adquirir una nueva TGT antes de usar el software Kerberos en el host objetivo. Si, en su lugar, el usuario tiene un ticket reenviable y reenvía su TGT al host objetivo como parte del proceso de inicio de sesión, el usuario ahora tiene una copia de su TGT válida para cualquier billete posterior a Kerberos peticiones del nuevo anfitrión. Solicitando un TGT reenviable, Los usuarios pueden disfrutar de los beneficios del inicio de sesión único, incluso cuando anidando delegaciones de credenciales arbitrariamente.

> [!Proxiable tickets]
> También puedes poner la bandera _de proxiable_ en un ticket. Los tickets proxiables son similares a tickets reenviables en los que pueden transferirse a otro anfitrión. Sin embargo, un TGT proxy solo puede usarse para adquirir más billetes de servicio; no puede usarse para adquirir un nuevo TGT en el host objetivo. En este sentido, los tickets por poder son menos potentes que sus contrapartes forwardables, y no lo son se usa a menudo en la práctica.

> [!Renewable tickets]
> En Kerberos 4, la duración de las entradas se limitaba a reducir la ventana de vulnerabilidad en caso de que las credenciales del usuario fueron robados. Kerberos 5 introduce un esquema de por vida de dos niveles que combina los beneficios de una vida útil más larga con la seguridad de vidas más cortas. Cuando un usuario solicita un ticket renovable, Le conceden una multa con una duración estándar de por vida y renovable Toda la vida. El billete es válido solo durante la duración del de por vida estándar, pero puede enviarse de nuevo al KDC para renovación en cualquier momento antes de que expire la multa (al final de la duración estándar de la vida). El KDC puede negarse a validar el ticket, si, por ejemplo, se ha reportado comprometido en la media tiempo. De lo contrario, el KDC valida el ticket y lo devuelve Otra multa. Este proceso puede repetirse hasta que el ticket se La vida útil renovable finalmente expira.

> [!Postdated tickets]
> Un ticket con fecha posterior es aquel que no es válido hasta que alguna fecha concreta en el futuro. Si un billete con fecha posterior es presentado para validación antes de la fecha de inicio incrustada en el Será rechazado. Las entradas con fecha posfechada son útiles para trabajos programados para ejecutarse en algún momento futuro que requieren Autenticación Kerberos, como trabajos por lotes o de clúster. Esto La opción no se usa comúnmente en la práctica, y de hecho algunos implementaciones, como la de Microsoft, no soportan la emisión de entradas con fecha posterior.

### Traducción de billetes Kerberos 5 a 4

Para proporcionar compatibilidad con los servicios antiguos de Kerberos 4, Kerberos 5 especifica un servicio de traducción de tickets Kerberos 5 a 4. Este servicio, conocido como krb524, ofrece una forma en que los clientes de Kerberos 5 puedan comunicarse con los servicios antiguos de Kerberos 4. No ofrece una forma para que los clientes de Kerberos 4 se comuniquen con los servicios de Kerberos 5 o KDCs.

Cuando un cliente de Kerberos 5 desea contactar con un servicio que solo entiende los tickets de Kerberos 4, las bibliotecas de Kerberos contactan con un máquina ejecutando el daemon krb524 para proporcionar compatibilidad con Kerberos 4 credenciales para presentar al servicio. Cuando el demonio krb524 recibe una solicitud de un cliente, descifra el ticket de servicio con el extrae la clave de sesión contenida en su interior y crea un nuevo ticket de Kerberos 4 para el mismo servicio y cliente, pegando la clave de sesión del ticket original de Kerberos 5.

Nótese que en este proceso, la clave de sesión contenida dentro de el ticket original de Kerberos 5 debe ser una sola clave DES. El krb524 Daemon no creará una nueva clave de sesión; en su lugar, solo copia el clave de sesión del ticket actual a un nuevo ticket de Kerberos 4. Ya que Kerberos 4 solo puede manejar tipos de clave DES individuales, esta clave de sesión debe Debe ser una única clave DES.

Además, la máquina que ejecuta el demonio krb524 no lo hace necesariamente tiene que ser un KDC de Kerberos. El demonio krb524 sí, sin embargo, necesitas acceso a la clave secreta de los servicios de Kerberos 4 involucrado. Esto se puede lograr si el demonio krb524 está funcionando en la misma máquina que uno de los KDC de Kerberos. Sin embargo, si esto no es posible, por ejemplo, si tu KDC es un controlador de dominio de Windows, que no soporta la traducción de tickets Kerberos 5 a 4, entonces el krb524 Daemon puede ejecutarse en una máquina separada. Las claves de servicio para cualquier Los servicios de Kerberos 4 pueden extraerse a una keytab situada en el máquina que ejecuta el demonio krb524, para poder descifrar el Kerberos 5 tickets y crear un nuevo ticket de Kerberos 4 para el servicio.

### Pre-autenticación

El protocolo original Kerberos 4 era susceptible a diccionario offline y ataques de fuerza bruta, como veremos en [el capítulo 6](https://learning.oreilly.com/library/view/kerberos-the-definitive/0596004036/ch06.html "Chapter 6. Security"). Esta vulnerabilidad proviene desde el hecho de que el KDC emite un TGT cifrado a cualquier cliente para cualquier principal (dado que el principal solicitado existe en el Base de datos Kerberos). Ya que el KDC proporciona encantado un ticket cifrado Con la clave secreta de los principales para cualquier solicitante, un ataque offline puede montarse para determinar la clave secreta del director. Esto La vulnerabilidad se agrava por el hecho de que los usuarios suelen elegir Contraseñas malas.

Para dificultar este ataque, Kerberos 5 introduce _la preautenticación_ (véase [la figura 3-11](https://learning.oreilly.com/library/view/kerberos-the-definitive/0596004036/ch03s03s06.html#kerberos-CHP-3-FIG-11 "Figure 3-11. AS exchange with pre-authentication")). La pre-autenticación requiere que los solicitantes demuestren su antes de que el KDC emita un ticket para un caso concreto director. Existen varios tipos de preautenticación definidos por el documento de aclaraciones de Kerberos. Sin embargo, solo la marca de tiempo cifrada (PA-ENC-TIMESTAMP) El método de preautenticación es comúnmente implementado.


![[../../assets/Pasted image 20260522040055.png]]
Figuras 3-11. Intercambio AS con pre-autenticación

La pre-autenticación está controlada por la política del KDC. Si un usuario intenta conseguir los billetes iniciales a través del intercambio AS, pero el El KDC requiere preautenticación, entonces el KDC enviará un mensaje KRB_ERROR en lugar de un AS_REP en respuesta a la Solicitud de AS del cliente. Este KRB_ERROR mensaje le indica al cliente que Se requiere preautenticación. El cliente genera el requisito datos de pre-autenticación, y reenvía su mensaje AS_REQ con el se añadieron datos previos a la autenticación. Si los datos de preautenticación son aceptado por el KDC, responde con una respuesta AS que incluye el El ticket inicial del cliente. De lo contrario, el KDC devolverá otro KRB_ERROR mensaje que indica que la preautenticación falló, y el el cliente no recibirá un ticket inicial de concesión de tickets.

Exploraremos los aspectos prácticos de seguridad de pre-autenticación con más detalle en [el capítulo 6](https://learning.oreilly.com/library/view/kerberos-the-definitive/0596004036/ch06.html "Chapter 6. Security").

### Transformación de cadena a tecla

Al igual que Kerberos 4, Kerberos 5 requiere una función que cumpla transformar una contraseña de cadena legible por humanos en una clave de cifrado para uso interno. Sin embargo, Kerberos 5 introduce varios cambios en esto proceso, siendo el más importante resultado del hecho de que Kerberos 5 soporta cualquier número de algoritmos de cifrado con tamaños de clave arbitrarios. Además, Kerberos 5 impone el uso de una _sal_, un trozo de Datos añadidos a la contraseña del usuario para hacerla más resistente A la fuerza bruta. Normalmente, esta sal es el principio completo el nombre — pero otras sales pueden ser especificadas por el KDC.

### Cambio de contraseña

Estado actual de los protocolos de cambio de contraseña en Kerberos 5 es similar al de Kerberos 4; desafortunadamente, como en Kerberos 4, cambiar contraseña se ha tratado como una idea secundaria. El las especificaciones originales de Kerberos 5, según la definición del RFC 1510, no Defina un medio por el cual los clientes pueden cambiar sus propias contraseñas. Más antigua las implementaciones de MIT Kerberos 5 utilizaron el protocolo administrativo para realizar cambios de contraseña, pero esto no es interoperable entre implementaciones ya que cada implementación utiliza una diferente Protocolo administrativo. Un protocolo estándar para la contraseña de Kerberos 5 el cambio se propuso como borrador de Internet en 1998, conocido como protocolo de cambio de contraseña de Horowitz. Las versiones más recientes de MIT (1.2 y superiores) y Heimdal Kerberos, así como Windows Active Director, basado en 2000 y 2003, soporta el Horowitz Protocolo de cambio de contraseña. Otras implementaciones, como la de Solaris SEAM, no soportan este protocolo y, por tanto, no son interoperables con cualquier otra implementación para cambios de contraseña.

Ahora se está debatiendo un nuevo proyecto de propuesta para sustituir al Protocolo de cambio de contraseña de Horowitz. Esta propuesta, la Versión 2 de Kerberos Set/Change Password, es la actual Borrador de la propuesta de Internet para el cambio de contraseña de Kerberos. Esta nueva La propuesta tiene varias ventajas sobre el cambio de contraseña de Horowitz protocolo. Primero, proporciona la capacidad para que los administradores restablecer las contraseñas de otros usuarios, así como permitir que los usuarios cambien sus propias contraseñas. Además, esta propuesta permite más información detallada que debe ser devuelta al cliente en el caso de un Contraseña rechazada. Dado que esta propuesta aún está en desarrollo, lectores interesados en los detalles del nuevo conjunto/cambio de Kerberos El protocolo Password Versión 2 puede encontrar más información en [http://www.kerberos.isi.edu](http://www.kerberos.isi.edu/).

## La sopa de letras de los protocolos relacionados con Kerberos

Por último, existen varios protocolos que, aunque estrictamente hablando no están directamente relacionados con Kerberos, se encontrarán cuando implementando un sistema de autenticación Kerberos.

### La API de Servicios Genéricos de Seguridad (GSSAPI)

La API de Servicios de Seguridad Genérica, como su nombre indica, es No es específico de ninguna técnica de autenticación. Por lo tanto, su mención en un libro sobre Kerberos puede parecer un poco fuera de lugar. Sin embargo, GSSAPI sí ampliamente utilizado por los implementadores de protocolos como medio para implementar Kerberos 5 soporte en sus aplicaciones. Al usar GSSAPI, un protocolo obtiene la la capacidad de usar otros métodos de autenticación fuerte "de forma gratuita", y el La capa GSSAPI también protege a los implementadores de las complejidades del API raw de Kerberos 5.

GSSAPI está orientado a desarrolladores de aplicaciones cliente/servidor que desean añadir soporte fuerte de autenticación a sus protocolos. Es proporciona una interfaz genérica y un formato de mensaje que puede encapsular la autenticación intercambia desde cualquier método de autenticación que tenga un Biblioteca compatible con GSSAPI. GSSAPI aísla a los programadores de aplicaciones de la interfaz de programación específica para una autenticación particular métodos. GSSAPI también proporciona un formato estándar de mensaje para que Los protocolos pueden soportar muchos métodos de autenticación diferentes sin Cambiando el protocolo en sí. GSSAPI no define un protocolo, autenticación, o mecanismo de seguridad en sí; En cambio, lo hace Más fácil para los programadores de aplicaciones soportar autenticación múltiple mecanismos proporcionando una API uniforme y genérica para la seguridad servicios.

La mayoría de las implementaciones de Kerberos 5 también incluyen una biblioteca GSSAPI. Esto significa que todas las aplicaciones que soportan GSSAPI también lo soportan Kerberos 5. La excepción notable es el Kerberos de Windows implementación, que no incluye soporte para GSSAPI sino que en su lugar incluye una API específica de Microsoft, el Proveedor de Soporte de Seguridad Interfaz (SSPI). SSPI no es compatible con la API de GSSAPI; es decir, los programas escritos para GSSAPI no se compilarán con SSPI. En cambio, las aplicaciones escritas para SSPI pueden hacerse compatibles con cable Aplicaciones GSSAPI. Por lo tanto, un cliente SSPI puede comunicarse con un Servidor GSSAPI. Microsoft proporciona algunos ejemplos de código que demuestran Cómo lograr esta interoperabilidad a nivel de mensaje de red.

Aunque GSSAPI está mayormente estandarizado, todavía hay algunos diferencias entre las encunaciones en lengua C de los disponibles implementaciones, particularmente las implementaciones MIT y Heimdal de GSSAPI. Durante la fase de configuración, la mayoría del software de código abierto lo hará detecta qué implementación de GSSAPI tienes y compila el código apropiado para trabajar con él, pero algunos programas pueden funcionar solo con una u otra. El trabajo para unificar estas APIs sigue en curso.

Los documentos de normas relevantes que definen GSSAPI incluyen RFC 2743, que documenta los tipos básicos de mensajes GSSAPI, RFC 1509, que define los enlaces y API del lenguaje C, y RFC 1964, que define el mecanismo Kerberos 5 GSSAPI.

### El mecanismo de negociación GSSAPI simple y protegido (SPNEGO)

GSSAPI resuelve el problema de proporcionar una única API para Mecanismos de autenticación diferentes. Sin embargo, no resuelve la Problema de negociar qué mecanismo usar. De hecho, para GSSAPI las dos aplicaciones que se comunican entre sí deben conocer y Acordar de antemano qué mecanismo de autenticación planean utilizar. Ya que la mayoría de las implementaciones de GSSAPI solo soportan un mecanismo de todos modos (concretamente, Querbero 5), esto normalmente no es un problema. Sin embargo, si hay hay múltiples mecanismos para elegir, se necesita un método para asegurar negociar un mecanismo de autenticación que sea mutuamente compatible entre cliente y servidor. SPNEGO, documentado en el RFC 2478, realiza esta función.

Microsoft incluye una implementación de SPNEGO en su Kerberos y la implementación de SSPI en Windows 2000 y versiones posteriores. Actualmente hay no existe una implementación ampliamente aceptada de SPNEGO de código abierto para Unix, sino Se está trabajando para producir uno. Además, Microsoft tiene algunas muestras código en su sitio web que proporciona una forma sencilla de analizar SPNEGO como parte de su artículo en tres partes sobre autenticación HTTP a través del protocolo Negotiate, disponible en [http://msdn.microsoft.com/library/default.asp?url=/library/en-us/dnsecure/html/http-sso-1.asp](http://msdn.microsoft.com/library/default.asp?url=/library/en-us/dnsecure/html/http-sso-1.asp). Muchos productos basados en Microsoft, incluyendo Exchange SMTP, ofrecen servicios de archivos a través de SMB y autenticación web con IE e IIS, se utiliza SPNEGO para Negociar un mecanismo de autenticación.
