La combinación de software complejo, la interoperabilidad entre Kerberos implementaciones y sistemas operativos diversos, y errores concisos (en el mejor de los casos) Los mensajes tienden a provocar calvicie prematura entre los administradores responsables para el buen funcionamiento de sus sistemas. Sin embargo, trabajar con Kerberos No tiene por qué ser tan frustrante.

Para proporcionar un enfoque sistemático para resolver problemas en Kerberos, Este capítulo comienza con una discusión sobre las distintas herramientas de depuración y técnicas, incluyendo un ejemplo de árbol de decisiones para seguir al enfrentarse a una nueva problema. Familiarizarse con estas herramientas y técnicas antes de un desastre Las huelgas serán útiles cuando surja el problema inevitable. La segunda Section usará esas herramientas y técnicas para diagnosticar algunos aspectos típicos problemas que ocurren en un sistema Kerberos. Describirá los síntomas de estos problemas comunes y luego muestran posibles soluciones para resolver ellos.

## Un árbol de decisiones rápido

Así que tienes un problema con tu instalación de Kerberos. El primer paso para resolver este problema, como depurar cualquier otro problema, es acotar la causa raíz. Determinaremos si el problema surge en tres categorías distintas, y continuamos nuestro análisis desde Ahí está.

Una forma sencilla de categorizar un error que involucra a Kerberos La autenticación se realiza a través de los tickets que el cliente puede adquirir para un servicio. Veamos las tres categorías principales:

- El cliente no puede conseguir un Ticket inicial para conceder multas. Lo más probable es que sea un Problema específico del cliente, especialmente si inicias sesión con el usuario Principal y contraseña funcionan en otros clientes. Por supuesto que podría también significa que la contraseña introducida para el usuario principal es incorrecto.
    
    Los culpables más probables incluyen problemas de sincronización temporal y problemas que llegan al servidor Kerberos debido a una mala configuración de El cliente. También es posible que el cliente no comparta un tipo de cifrado compatible para la clave secreta de los usuarios con el KDC. Esto puede ocurrir, por ejemplo, al intentar interoperar entre un cliente Unix y un controlador de dominio de Windows. Por defecto, Los controladores de dominio de Windows crean entradas de usuario con un RC4-HMAC tipo de cifrado, que la mayoría de las implementaciones de Unix Kerberos no tienen Entiendo. Las versiones más recientes de Heimdal y MIT Kerberos 5 sí soportan este tipo de cifrado.
    
- El cliente tiene un TGT válido pero recibe Error antes de que se adquiera un ticket de servicio. Una vez más, Lo más probable es que esto sea un problema del cliente. Los sospechosos habituales en este escenario incluye una mala configuración de Kerberos en el cliente, que Lo trataremos en una sección posterior.
    
    Otra posibilidad es que el principal de servicio que el Simplemente no existe el cliente solicitado. Examinando los archivos de registro del KDC es una buena forma de determinar si el cliente está llegando al KDC y si Así que, si intenta conseguir entradas para un principal, eso sí no existen, o están en un reino diferente.
    
- El cliente tiene un TGT y un servicio válidos pero reporta error en la conexión con Kerberized servicio. Lo más probable es que haya un problema con el servidor. En este punto, el cliente ha recibido un ticket por el servicio y Lo presentó al servicio para su autenticación. Los más comunes La causa de un fallo en este punto es una descoordinación en el cifrado tipos o números de versión clave para el servicio Kerberos entre los Keytab del servicio y el KDC. El KDC pudo haber emitido una multa con un tipo de cifrado que el servicio no entendía, o quizás La pestaña de claves del servicio contiene una clave de cifrado incorrecta. El El servicio puede no ser capaz de leer su tecla tecla en absoluto; asegurar que el la tecla del servicio es legible por el usuario con el que el servicio se ejecuta, y que la configuración adecuada esté en su lugar para apuntar al servicio hasta la ubicación de la tecla de teclado.
    
    Otra posibilidad es que el DNS del servidor o Kerberos El archivo de configuración no está configurado correctamente. Asegúrate de que el El nombre de host del servidor objetivo puede resolverse correctamente usando Herramientas de diagnóstico como ping y nslookup.
    

Las causas generales que deben investigarse incluyen el tiempo sincronización y ajustes correctos de nombre de host y DNS en todos máquinas.

Por último—esto puede parecer obvio—es fácil pasar por alto la final Paso: registrar el error y la solución utilizada para resolver el problema. Demasiado a menudo, especialmente con algunos de los errores más esotéricos que Kerberos puede producir, los administradores experimentan un error algún día, resolver el problema, luego experimentar el mismo error una semana después, y tener para volver a encontrar la causa raíz, solo para descubrir que la solución es vagamente familiar.

## Errores y soluciones

Con las herramientas de depuración presentadas arriba, repasaremos algunas escenarios problemáticos, desde los síntomas iniciales de un problema hasta su solución.

### Errores al obtener un ticket inicial

Pueden ocurrir varios errores al intentar obtener un Ticket inicial de concesión de billetes de un KDC de Kerberos. Ya que hay muchas formas de obtener un TGT, como mediante inicio de sesión integrado con un PAM Módulo Kerberos, la mejor manera de reducir problemas es utilizando el Programa Unix Kinit manualmente. Esto funcionará incluso si tu KDC es un El controlador de dominio de Windows, dado que el principio que estás probando tiene se ha configurado para cifrado DES ([véase el Capítulo 8](https://learning.oreilly.com/library/view/kerberos-the-definitive/0596004036/ch08.html "Chapter 8. Advanced Topics")).

Veamos algunos ejemplos:

```
> kinit
Password for jgarman@WEDGIE.ORG:
kinit(v5): Preauthentication failed while getting initial credentials
```

Si tu reino requiere preautenticación (véase [el Capítulo 6](https://learning.oreilly.com/library/view/kerberos-the-definitive/0596004036/ch06.html "Chapter 6. Security")), entonces este mensaje es normalmente solo en términos de Kerberos para "contraseña incorrecta". Ten en cuenta que Los controladores de dominio de Windows requieren preautenticación por defecto. También Ten en cuenta que este mensaje puede deberse a un cliente que no soporta el tipo de preautenticación requerido por el KDC. Sin embargo, todos los Las implementaciones de Kerberos que cubrimos aquí soportan la marca temporal cifrada (PA-ENC-TIMESTAMP) método de pre-autenticación. Por supuesto, si lo eres interoperando con una implementación de Kerberos que no soporta Pre-autenticación, y tu reino la requiere, tendrás que hacerlo desactivar la pre-autenticación en la política KDC.

A continuación, existe la posibilidad de que el KDC no haya encontrado un clave de cifrado adecuada con la que cifrar la respuesta. Cuando un El cliente Kerberos 5 contacta con un KDC a través del intercambio AS para un Ticket inicial de Concesión de Tickets, el cliente envía una lista de cifrado Tipos que entiende. Si el KDC no encuentra una clave secreta asociado a uno de los tipos de cifrado incluidos en la solicitud, Devolverá un error.

También pueden ocurrir desajustes de tipo de cifrado más adelante en la Intercambio de Kerberos, y lo trataremos en una sección posterior. Errores la obtención de un ticket inicial también puede ser causada por el nombre de host/DNS configuración incorrecta, o una configuración de Kerberos ausente o incorrecta archivo. Estas posibilidades también se abordarán pronto en un futuro sección.

Finalmente, otro error común que puede causar el El mensaje de fallo previo a la autenticación es un problema de sincronización de reloj (que también puede causar todo tipo de otros problemas extraños), A continuación.

### Relojes no sincronizados

Otra causa raíz común de los problemas de Kerberos es la falta de sincronización de reloj entre todos los hosts participantes. Normalmente El mensaje de error que se produce cuando hay una descoordinación en el reloj es Es autoexplicativo. Por ejemplo:

```
krb5_rd_req failed: Clock skew too great
```

Se recomienda que todos los anfitriones participantes en un Kerberos reino sincronizado con una fuente de tiempo central. El horario de la red El protocolo (NTP) cumple perfectamente con este requisito. NTP se discute brevemente en [la Sección 4.3](https://learning.oreilly.com/library/view/kerberos-the-definitive/0596004036/ch04s03.html "Before You Begin") del [Capítulo 4](https://learning.oreilly.com/library/view/kerberos-the-definitive/0596004036/ch04.html "Chapter 4. Implementation"), y se puede obtener más información se encuentra en la página principal de NTP en [http://www.ntp.org](http://www.ntp.org/).

Dado que NTP y Kerberos utilizan Tiempo Coordinado Universal (UTC) para comparar relojes, el tiempo las diferencias de zona no afectan al funcionamiento de Kerberos.

### Configuración incorrecta o ausente de Kerberos

Todo cliente necesita saber dos cosas: el ámbito que a cada host con el que desea comunicarse pertenece, y a los KDC que son responsables de esos reinos. Por lo tanto, un cliente requiere un mapeo entre nombres de dominio y reinos, así como entre reinos y sus KDCs. Tradicionalmente, estos mapeos se codifican directamente dentro de un archivo de configuración, _/etc/krb5.conf_ , en hosts Unix. Sin embargo, con la llegada de Windows 2000, el DNS realm y el mapeo KDC están ganando popularidad, ya que Windows En 2000 y superiores usan DNS para encontrar información de reino y KDC mediante por defecto.

De cualquier manera, tu reino (y otros reinos que tus anfitriones pueden ser comunicar con) maneja su configuración de Kerberos, incorrecta o La falta de información de configuración de Kerberos provocará solicitudes de Tickets to fail, a veces de forma silenciosa—sin dar mensajes de error a señalar hacia la causa del fallo, o peor aún, mensajes de error engañosos que no dan indicios de la causa raíz del fallo.

Empecemos con algunos ejemplos sencillos de un cliente Unix que ejecuta MIT. Nuestro cliente no tiene ningún archivo _/etc/krb5.conf_. Si existe un preexistente Caché de credenciales (apuntando por la variable de entorno KRB5CCACHE, por _defecto /tmp/krb5cc_UID_ donde UID es Unix UID del usuario actual), entonces kinit solicitará un ticket como ese director del KDC. Cuando no existe una credencial previa cache, MIT kinit forma el usuario principal usando el nombre de usuario Unix como la parte de nombre de usuario del principal, y el reino se determinan por la variable default_realm en la estrofa libdefaults de _/etc/krb5.conf_. Dado que, en este caso, no existe el _archivo /etc/krb5.conf_, kinit se quejará de:

```
> whoami
jgarman
> kinit
kinit(v5): Configuration file does not specify default realm when parsing name jgarman
```

Ahora creemos un archivo _minimalista /etc/krb5.conf_:

```
[libdefaults]
        default_realm = WEDGIE.ORG
```

Con esto en marcha, MIT Kerberos puede ahora determinar el valor por defecto reino. Ten en cuenta que incluso si un mapeo DNS correcto entre el nombre de dominio y el reino es disponible en DNS, MIT sigue requiriendo una entrada default_realm en _/etc/krb5.conf_ para funcionar correctamente. Además, sin un Definido por defecto en el ámbito de reino, algunas aplicaciones GSSAPI también pueden comportarse Incorrectamente, dando mensajes de "error genérico".

Ten en cuenta que este archivo _minimalista /etc/krb5.conf_ solo funcionará si tienes entradas DNS correctas para tu Kerberos reino, tal como se discute en [la Sección 4.5](https://learning.oreilly.com/library/view/kerberos-the-definitive/0596004036/ch04s05.html "DNS and Kerberos") en [el capítulo 4](https://learning.oreilly.com/library/view/kerberos-the-definitive/0596004036/ch04.html "Chapter 4. Implementation"). Ahí tiene que ser una forma para que el cliente encuentre su KDC, ya sea mediante estática archivos de configuración o a través de DNS. Si el cliente no encuentra el KDC Para un reino dado, informará con precisión:

```
kinit(v5): Cannot resolve network address for KDC in requested realm while getting 
initial credentials
```

> [!tip]
> MIT Kerberos tiene un error en el que un KDC devuelve un mensaje de error afirmando que no tiene soporte para el tipo de cifrado solicitado para todas las solicitudes de tickets si el KDC no tiene archivo _/etc/krb5.conf_. Crear un archivo _/etc/krb5.conf_ en el KDC, aunque sea En blanco, solucionará este problema.

Heimdal Kinit también utiliza una caché de credenciales existente Presenta, si existe, para determinar el principal que Kinit hará Consigue entradas para. Si no hay archivo _/etc/krb5.conf_, o si no especifica un reino por defecto, usará el componente de nombre de dominio del local nombre de anfitriones como el reino. Heimdal también consultará DNS para DNS Mapeo de nombre host-a-reino de Kerberos, así como ubicación de KDC, o uso Configuración estática en _/etc/krb5.conf_.

En todos los casos, la configuración estática en _/etc/krb5.conf_ cortocircuitará la ubicación de KDC y mapeos de dominio-reino. Si la información estática está ubicada en el archivo de configuración, las entradas estáticas anularán cualquier DNS Información disponible.

Si los problemas persisten, podría haber un problema con tu DNS mapeo de nombre de dominio a reino de Kerberos. Esto es especialmente evidente cuando el nombre de dominio DNS y los nombres de reino Kerberos no coinciden. Cada cuando un cliente adquiere un ticket para comunicarse con un Kerberizado servidor de aplicaciones, necesita determinar el ámbito que el Pertenece al servidor de aplicaciones a. Esta aplicación está controlada por el domain_realm estrofa en el archivo _/etc/krb5.conf_, o entradas TXT en el DNS (como se describe en [la Sección 4.5](https://learning.oreilly.com/library/view/kerberos-the-definitive/0596004036/ch04s05.html "DNS and Kerberos") del [Capítulo 4](https://learning.oreilly.com/library/view/kerberos-the-definitive/0596004036/ch04.html "Chapter 4. Implementation")). No encontrar un entrada apropiada, ya sea en el archivo de configuración o en el DNS, el Las librerías Kerberos intentarán usar el nombre de dominio DNS del anfitrión, convertido a mayúsculas, como nombre del reino. Problemas relacionados con el dominio El mapeo de nombre a reino de Kerberos puede diagnosticarse reduciendo el problema a un dominio o anfitrión problemático particular.

Desafortunadamente, este problema puede causar fallos misteriosos con No hay mensajes de error. La forma más directa de saber si existen mapeos desajustados de realm-DNS es para comprobar los registros KDC para el el reino predeterminado del cliente. Si el cliente intenta contactar con un kerberizado Que considere que está en otro ámbito, intentará un autenticación entre reinos a ese otro reino.

Por ejemplo, estamos en _slave.wedgie.org_, autenticado como _jgarman@WEDGIE.ORG_ y intentando un telnet kerberizado para alojar _freebsd.wedgie.org_, que el esclavo piensa que está en el reino BOGUS.COM, debido a un error de configuración. Por lo tanto, es Intentando conseguir tickets de servicio para _anfitrión/slave.wedgie.org@BOGUS.COM_, pero primero necesitas para conseguir entradas inter-reinos para BOGUS.COM. En este ejemplo, el Las siguientes entradas de registro se encuentran en el archivo de registro del KDC Responsable de WEDGIE.ORG:

```
Feb 26 21:32:20 freebsd krb5kdc[520]: TGS_REQ (3 etypes {16 3 1}) 192.168.0.5(88
): UNKNOWN_SERVER: authtime 1046294981,  jgarman@WEDGIE.ORG for krbtgt/BOGUS.COM
@WEDGIE.ORG, Server not found in Kerberos database
```

La solución a una discrepancia entre DNS y reino es asegurar que todos Los clientes tienen los mapeos correctos en su lugar. En este caso bastante forzado por ejemplo, el comportamiento por defecto de Kerberos es suficiente, ya que todo las máquinas en el dominio DNS _wedgie.org_ pertenecer a el reino WEDGIE.ORG Kerberos. Sin embargo, otras organizaciones pueden tener un nombre de reino diferente de su nombre de dominio DNS, y es esto situación que requiere cuidados especiales.

```

Por lo tanto, el servidor ftp recibe la conexión en el Interfaz de loopback. Cuando el daemon ftp genera el servicio El principio que usará para validar el ticket del usuario, realiza una consulta de IP a nombre en la interfaz en la que recibió el Petición. Por lo tanto, si examinamos los registros de solicitudes del KDC, veremos un Solicitud fallida para el inexistente FTP_/localhost@WEDGIE.ORG_ principal:

```
Jan 29 04:52:21 freebsd krb5kdc[35553]: TGS_REQ (3 etypes {16 3 1}) 192.168.0.5(88): 
UNKNOWN_SERVER: authtime 1043800211,  jgarman@WEDGIE.ORG for ftp/localhost@WEDGIE.
ORG, Server not found in Kerberos database
```

Una vez corregido el _archivo /etc/hosts_ con el mapeo correcto de IP a nombre de host para nuestro host, obtenemos el Resultado previsto:

```
> ftp freebsd
Connected to freebsd.wedgie.org.
220 freebsd.wedgie.org FTP server (Version 5.60) ready.
334 Using authentication type GSSAPI; ADAT must follow
GSSAPI accepted as authentication type
GSSAPI authentication succeeded
Name (freebsd:jgarman): 
232 GSSAPI user jgarman@WEDGIE.ORG is authorized as jgarman
```

Este ejemplo ilustra la importancia de un resolver consistente y la información DNS para el correcto funcionamiento de Kerberos. Esto El problema puede manifestarse de muchas maneras, pero todas con la misma raíz causa de datos incorrectos en DNS o en bases de datos locales del anfitrión. El particular el escenario descrito arriba puede ocurrir con la mayoría de las distribuciones de Linux, que, de serie, se asocia con el nombre de host de la máquina a la Dirección de loopback de la máquina. Escenarios similares ocurren con Solaris máquinas, que, por defecto, crean archivos _/etc/hosts_ que listan primero el nombre de host "corto", antes del FQDN que Kerberos debe formar el principio de servicio correcto.

Garantizar que los servicios kerberizados puedan construir un servicio adecuado Principales, la base de datos local de anfitriones necesita una entrada como la Siguiente:

```
192.168.0.5  freebsd.wedgie.org  freebsd
```

Ten en cuenta que el nombre de host está asignado a la dirección IP de la interfaz adecuada (en contraposición a la dirección IP de loopback), y que el FQDN tiene precedencia sobre el nombre de host corto.

Aquí hay un mensaje de error similar que resulta de DNS y Error de configuración de hostname:

```
Hostname cannot be canonicalized while verifying initial ticket
```

Esencialmente, esto ocurre cuando la aplicación intenta encontrar su nombre principal de servicio realizando una búsqueda inversa en el la dirección IP de la interfaz en la que se recibió esta solicitud. Si esa IP la dirección no se resuelve a un nombre de host, este mensaje ni el anterior Se generará el mensaje "no se puede encontrar el principal de servicio".

Hosts multi-homed que tienen un nombre de host diferente para cada también supone un problema para Kerberos. Dependiendo de qué Una interfaz en la que llega la solicitud de un cliente, un nombre de host de servidor diferente puede estar asociado a esa solicitud. Por lo tanto, cada interfaz que tiene un nombre de host diferente y un conjunto distinto de principios de servicio basado en ese nombre de host, lo que puede causar un problema si solo hay uno conjunto de principios de servicio definidos para el anfitrión. Se recomienda que los hosts multihomed tienen una única FQDN asociada a todas las interfaces en La máquina.

### Desajustes de tipos de cifrado

El soporte extensible para tipos de cifrado en Kerberos 5 sí puede resultan en algunas interacciones extrañas al mezclar diferentes Kerberos 5 implementaciones. La mayoría de las veces, el KDC puede determinar automáticamente el conjunto óptimo de tipos de cifrado para un intercambio de protocolos dado; Sin embargo, a veces necesita un poco de ayuda manual.

Esto es necesario cuando tienes llaves almacenadas para "más fuerte" los tipos de cifrado en el KDC para un servicio dado, pero el servicio puede Solo maneja tipos de cifrado más débiles. Ya que no hay una relación directa comunicación entre el servicio y el KDC, no hay forma de que el para comunicar su soporte de tipo de cifrado al KDC. En su lugar, cuando el KDC devuelve un ticket al cliente para su uso con el el KDC usará el tipo de cifrado más fuerte que tenga en su base de datos del servicio. Tomemos un ejemplo.

Tenemos un _freebsd.wedgie.org_ KDC en funcionamiento el MIT KDC y un servidor de aplicaciones, _slave.wedgie.org_, que ejecuta una red telefónica kererizada Daemon con las bibliotecas cliente del MIT. Hemos creado una pestaña de teclas para el host _slave.wedgie.org_, y Lo copié en _/etc/krb5.keytab_ de ese anfitrión. El La base de datos KDC y la pestaña de teclas incluyen claves tanto para triple DES como para tipos de cifrado DES individuales, como se ilustra a continuación:

```

La tecla de teclas _en slave.wedgie.org_ contiene ambos tipos de cifrado y, en consecuencia, el telnet kerberizado funciona bien Entre los dos presentadores:

Ahora, veamos qué ocurre cuando borramos el triple DES Clave de cifrado desde la pestaña de claves del esclavo. Usaremos esto para simular un servicio que no soporta tipos triples de cifrado DES. Después de que editamos la keytab para eliminar la clave triple de cifrado DES, intentamos Otro telnet convertido en esclavo:

Este mensaje de error puede ser algo engañoso; Al fin y al cabo, sí tener una entrada en la tabla clave para _host/slave.wedgie.org_; sin embargo, la entrada keytab contiene una única clave DES, cuando el KDC tiene emitió al cliente un ticket de servicio cifrado con triple DES. Ya que El servicio no puede encontrar una clave de cifrado adecuada para descifrar el Ticket, se rinde y devuelve este mensaje de error.

La solución aquí es identificar qué tipos de cifrado son soporte de servicio y aseguran que la base de datos de Kerberos solo contenga esos tipos de cifrado de claves para ese servicio. Por ejemplo, en este en el caso de que nuestro servidor telnet solo soporte cifrado DES único, nosotros hay que eliminar la clave de cifrado triple DES del KDC de Kerberos, así que que el KDC solo emitirá tickets para ese servicio cifrado con DES. En general, todas las implementaciones de Kerberos 5 deben soportar cifrado DES único, así que si hay sospecha de tipo de cifrado incompatibilidades, se recomienda que recrees lo relevante principales con un único tipo de cifrado DES. Desafortunadamente, esto reduce la seguridad de esos principios.

Para resolver este problema, eliminamos la clave host para slave.wedgie.org, recréalo con un solo tipo de cifrado DES, y extrae esa tecla de teclado al host. Dado que el KDC ahora solo tiene un Disponible una única clave de cifrado DES, cifrará el servicio billete con la única clave DES.

El proceso de crear principios con un subconjunto de cifrado Los tipos varían de una implementación a otra.
