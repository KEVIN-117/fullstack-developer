## Cross-Realm Authentication

Toda la discusión sobre Kerberos hasta ahora ha supuesto que todos los usuarios y recursos de tu red están ubicados en un solo Kerberos reino. Sin embargo, ¿qué pasa si hay varios departamentos, ubicaciones o otras divisiones que están bajo diferentes controles administrativos, cada una ¿con su propio reino Kerberos? Estos usuarios quieren acceder no solo recursos en su reino local de Kerberos, pero también recursos en el otro Reinos también, con un mínimo de complicaciones. Reino cruzado de Kerberos La autenticación puede resolver este problema.

En Kerberos, el cross-realm se implementa compartiendo un cifrado clave entre dos reinos. La clave que se comparte es la Concesión de Tickets Llave del director de servicio. Un principio típico del Servicio de Concesión de Multas para Un solo reino se presenta así:

```
krbtgt/WEDGIE.ORG@WEDGIE.ORG
```

Ten en cuenta que la instancia es la misma que el nombre del reino. En En el reino interregional, se crean dos principales en cada reino participante. Para Dos reinos, ONE.COM y TWO.COM, estos principios serían:

```
krbtgt/TWO.COM@ONE.COM
krbtgt/ONE.COM@TWO.COM
```

Estos principios deben crearse en ambos reinos y son conocidos como principales servidores remotos de concesión de tickets. El fideicomiso Kerberos puede ser de una forma o de ambas formas; ya que hay dos claves separadas y compartidas Involucrados, un reino puede elegir confiar en los tickets del otro reino, pero No al revés.

Cuando un usuario que está en el ámbito ONE.COM desea comunicarse con un servicio kerberizado en TWO.COM, el programa cliente solicita primero un ticket para el Servidor de Concesión de Tickets del reino remoto, el _krbtgt/TWO. COM@ONE.COM_ director mencionado arriba. Usando eso Ticket intermedio de concesión de billetes, el cliente puede entonces adquirir un ticket de servicio directamente para el servicio solicitado en el TWO.COM reino. Esto se _llama reino cruzado directo y_ es el único tipo de fideicomiso inter-reino que se apoya en el antiguo protocolo Kerberos 4. En la confianza directa entre reinos, cada dos los reinos que deseen comunicarse deben compartir un conjunto separado de claves. De Por supuesto, esto puede volverse bastante engorroso a medida que crece el número de claves compartidas exponencialmente con el aumento del número de reinos. Esto se puede gestionar En cierto modo, construyendo una _ruta de certificación_ entre varios reinos, una característica introducida con el Protocolo Kerberos 5. Una ruta de certificación define reinos que pueden ser Utilizados como intermediarios al adquirir billetes de servicio en territorios extranjeros. El interámbito directo requiere que todo reino extranjero esté directamente conectado, a través de una clave compartida, hacia el reino local, creando una malla completa Configuración entre los Reinos. Las rutas de certificación permiten múltiples para usar otro reino como intermediario, creando hub-and-spoke sistemas en los que múltiples reinos comparten una clave con un único intermediario reino.

Tomemos un ejemplo. Hay varias universidades colaborando en un proyecto para producir fusión fría viable junto con una agencia gubernamental ficticia, la Directiva Nacional de Investigación Energética (NERD). Obviamente, estas organizaciones quieren aprovecharse mutuamente recursos, y a los investigadores no les gusta memorizar numerosos inicios de sesión y por lo que se propone Kerberos entre reinos como solución a la Necesidades de autenticación de todas las organizaciones implicadas. Sin embargo, directo El cruce entre todas estas organizaciones requeriría aproximadamente n2 tonalidades diferentes, donde n es el número de participantes Reinos de Kerberos. Esto es una pesadilla para la gestión, especialmente si, en esto Por ejemplo, con el tiempo se añaden más universidades al proyecto. Con confianza jerárquica, todos los reinos participantes en el La confianza entre reinos son subdominios de un reino más amplio. Por ejemplo, un la compañía tiene un reino Kerberos llamado COMPANY.COM. La empresa cuenta con varios oficinas con sus propios reinos de Kerberos, llamados NEWYORK.COMPANY.COM, PARIS.COMPANY.COM, etc. Cada uno de estos reinos comparte una clave con el "reino de padres", COMPANY.COM.

Como NEWYORK.COMPANY.COM confía en el progenitor, COMPANY.COM (ellos comparte una clave entre ellos), y luego NEWYORK.COMPANY.COM confía implícitamente PARIS.COMPANY.COM también, aunque no se comparta ninguna clave explícita entre los reinos de Nueva York y París. Esto es simplemente un caso especial de la Camino de certificación descrito anteriormente; el sufijo DNS común entre los dos reinos de Kerberos crean una ruta implícita de certificación entre todos reinos subordinados y el reino de origen.

## Problemas con Windows

Aunque la implementación de Windows de Kerberos es compatible con la especificaciones en la RFC 1510, la implementación de Microsoft de Kerberos varía significativamente desde las implementaciones del MIT y Heimdal hasta merece su propia explicación. Para proporcionar el adicional funcionalidad requerida para Windows Active Directory, así como compatibilidad hacia atrás con estaciones de trabajo Windows NT antiguas, el Windows El entorno Kerberos difiere en varias áreas importantes de su Unix Contraparte.

### Soporte para algoritmos de cifrado

El tipo principal de cifrado utilizado en Windows se basa en el cifrado de flujo RC4, con un Algoritmo MD5-HMAC utilizado para el campo de suma de comprobación. Este tipo de cifrado se denomina RC4-HMAC, y tiene una longitud de clave variable para soportar ambos longitudes de clave de calidad "exportación" más débiles, así como una clave de 128 bits más fuerte longitudes.

La razón detrás de esta decisión de Microsoft es doble: primero, para compatibilidad con dominios antiguos de Windows NT; y segundo, por razones políticas. Durante el diseño inicial de Windows 2000, ni el DES ni el triple DES fueron aprobados para exportación desde Estados Unidos Estados. Microsoft quería fomentar el despliegue de Windows 2000; por lo tanto, se eligió el cifrado RC4-HMAC como Kerberos por defecto tipo de cifrado ya que es el mismo cifrado usado para generar el más antiguo Hashes de contraseñas NT4. De este modo, cuando se migre un dominio NT4 antiguo a un dominio de Active Directory, las contraseñas de los usuarios siguen funcionando Sin intervención manual.

Microsoft añadió soporte DES a Windows 2000 antes de que y los usuarios creados en Windows Active Directory tienen ambos RC4 y claves de cifrado DES asociadas a su cuenta. Sin embargo, ahí son dos situaciones en las que una clave DES no está disponible para una cuenta en el Active Directory. La primera situación es la que se ha discutido antes, en el que un dominio NT4 se convierte en un Active Directory de Windows dominio. Como el algoritmo de hashing solo funciona de una manera, no existe forma para que Windows convierta las claves de cifrado RC4 de los usuarios existentes en claves DES. La segunda situación especial es cuando un nuevo Windows Se crea el dominio 2000. Como parte del procedimiento de creación de dominio, un La cuenta de administrador se crea como el nuevo Administrador de Dominio. Esto la cuenta solo tiene una clave RC4 cuando se crea inicialmente.

Para añadir claves DES a las cuentas de los usuarios en ambos puntos anteriores Simplemente cambia la contraseña del usuario. Cuando la contraseña de un usuario si cambia, el KDC generará tanto claves de cifrado RC4 como DES para ese usuario.

Ten en cuenta que incluso sin el "Usar tipos de cifrado DES para esto cuenta" marcada para un usuario, las claves DES sí existen en el Base de datos Active Directory (sujeta a las limitaciones de la anterior dos escenarios), pero no son utilizadas por el KDC al responder a tickets Solicitudes a menos que la casilla esté activada.

Una mejor solución a esto es para otras implementaciones de Kerberos para adoptar también el tipo de cifrado RC4-HMAC en su código. Heimdal recientemente ha añadido este soporte a su distribución, y el MIT lo ha hecho incorporó soporte completo para RC4-HMAC en su versión Kerberos 5 1.3. Con soporte de tipos de cifrado RC4, interoperabilidad entre Unix y Los reinos Kerberos de Windows pueden ocurrir sin necesidad de degradar el cifrado Claves usadas para un solo DES.

También ten en cuenta que Windows no soporta sales distintas al estándar Sal de Kerberos 5. Si tienes un KDC Unix que tiene claves de cifrado con otras sales (como la sal Kerberos 4 o la sal AFS) para interoperabilidad Con clientes mayores, puede que tengas problemas al intentar interoperar con Windows. Reordenación cuidadosa de los tipos de cifrado en el archivo de configuración del KDC de Unix puede ayudar a aliviar esto problema, pero se recomienda usar solo sal Kerberos 5 y tipos de cifrado al interactuar con Windows.

### Credenciales de inicio de sesión en caché

Muchos ordenadores con Windows son móviles y no tienen un sistema fijo Conexión de red. Por ejemplo, los portátiles pueden dedicar la mayor parte de su tiempo desconectado de una red; Sin embargo, los usuarios finales esperan la capacidad de registrar en sus propios ordenadores, incluso cuando no hay conexión de red. Tradicionalmente, sistemas que requieren autenticación Kerberos exitosa para acceso local, como ocurre con Active Directory, se requiere una red estable para operar, ya que la comunicación con el KDC es necesaria para Autorizar el inicio de sesión. Microsoft permite iniciar sesión desconectado al dominio cuentas a través de una función de credenciales en caché.

Cuando un usuario inicia sesión en un host de Windows 2000, XP o 2003, el La Autoridad de Seguridad Local (LSA) deriva un verificador de contraseñas y guarda Este verificador entra en el registro local de la máquina. Más tarde, si el usuario es desconectado de la red o del controlador de dominio es lo contrario no disponible, el sistema local autorizará el acceso si el nombre de usuario y que la contraseña coincida con las credenciales guardadas almacenadas en el local Disco.

Las credenciales en caché se almacenan en las máquinas locales registro dentro de la clave HKEY_LOCAL_MACHINE\Security\Cache, que contiene subclaves de NL$1 a NL$10. El nombre de usuario de los últimos 10 usuarios y los verificadores de contraseña se almacenan como los valores de cada uno de estos Llaves.

Fíjate que me he referido a una _contraseña verificador_, y no contraseña o hash de contraseña. La contraseña El verificador es un hash del hash de la contraseña, es decir, el verificador de contraseñas no puede usarse para derivar ni la contraseña original ni una contraseña Hachís. Por tanto, el verificador contiene los datos justos para que sea capaz Para que el proceso local de inicio de sesión reciba una contraseña, ejecuta un hash Algoritmo sobre él dos veces y compáralo con el verificador.

> [!tip]
> Por razones de seguridad, Windows restringe el acceso a esto clave del registro para la cuenta local del SISTEMA. Para ver estas claves como Administrador, inicia la aplicación regedt32, navega a HKEY_LOCAL_MACHINE\Seguridad, y selecciona Permisos → Seguridad. Marca la casilla para permiso de lectura para el grupo de Administradores.

Desafortunadamente, ciertas situaciones hacen que Windows no proporcione indicación al usuario final cuando el sistema autentica al usuario A través de un verificador de credenciales en caché. Cuando un usuario es verificado contra un verificador de contraseñas ubicado en la caché, el proceso de inicio de sesión no puede Adquirir cualquier ticket inicial para el usuario. Mientras que Windows lo notará cuando un controlador de dominio de Windows vuelve a estar disponible y Adquirir tickets de forma transparente, las credenciales de acceso en caché pueden ser especialmente problemático cuando Windows está configurado para autenticarse contra un KDC que no sea Microsoft, ya sea directamente o a través de un multi-reino confiar en un dominio de Windows.

#### Desactivar la función de credenciales en caché

El inconveniente, por supuesto, de desactivar la caché La característica de credenciales es que si la máquina pierde su red y ya no puede acceder al controlador de dominio, a ningún local Las solicitudes de inicio de sesión en ese dominio fallarán. El número de inicios de sesión en caché puede forzarse a cero usando una Política de Seguridad de Dominio. Set "Número" de inicios de sesión previos en caché (en caso de que el controlador de dominio no lo esté disponible)", que se encuentra en Configuración → Configuración del Ordenador → Políticas Locales → Opciones de Seguridad, a cero. Este cambio afecta a la clave de registro CachedLogonsCount en cada Máquina miembro en el dominio. Este valor de registro puede encontrarse dentro de la clave de registro HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\WinLogon.

En 2002, Microsoft publicó un resumen del PAC de Windows 2000 especificación, que está disponible en [http://msdn.microsoft.com/library/default.asp?url=/library/en-us/dnkerb/html/MSDN_PAC.asp](http://msdn.microsoft.com/library/default.asp?url=/library/en-us/dnkerb/html/MSDN_PAC.asp), y también envió un borrador de Internet al IETF, actualmente disponible A [http://www.ietf.org/internet-drafts/draft-brezak-win2k-krb-authz-01.txt](http://www.ietf.org/internet-drafts/draft-brezak-win2k-krb-authz-01.txt).

El PAC es generado por el KDC durante el Servidor de Autenticación y contiene datos de autorización sobre el cliente, incluyendo el SID (un identificador numérico único para usuarios y grupos) asociado con el usuario que solicitó el ticket y cualquier grupo en el que se encuentre Un miembro de. Estos datos se cifran para garantizar la integridad y autenticidad, para que los servicios de Windows puedan confiar en la información para crear Decisiones de autorización basadas en el contenido de los tickets de servicio presentado para validación. Estos datos de autorización también están disponibles por realizando consultas LDAP contra los servidores de Active Directory, pero es incluido aquí como una optimización, para reducir el número de viajes de ida y vuelta entre los clientes y los Controladores de Dominio. Sin embargo, la mayoría Los servicios basados en Windows no realizarán este paso adicional si el El campo de autorización falta en los tickets presentados por los clientes, Negar el acceso a esos clientes.

En general, los clientes que no son Microsoft Kerberos ignoran el PAC el campo está incluido con los tickets emitidos por un Microsoft KDC. Existe, Sin embargo, un caso en el que pueden surgir algunos problemas de interoperabilidad: si un el usuario es miembro de un gran número de grupos, entonces el PAC puede crecer lo suficientemente grande como para que la respuesta KDC no capa en un solo paquete UDP. Si esto ocurre, el KDC de Windows pide al cliente que intente la solicitud de nuevo usando TCP. Versiones anteriores de MIT Kerberos 5 (antes de la 1.3) y algunas otras implementaciones de Kerberos no pueden volver a intentarlo con TCP, y lo harán Fracaso.

## Interoperabilidad entre Windows y Unix

En los capítulos anteriores, nos centramos principalmente en el diseño y la implementación de una red Kerberos homogénea. Sin embargo, la verdad el atractivo de pasar a un esquema de autenticación basado en Kerberos a nivel de red es permitir la autenticación centralizada y, más importante aún, inicio de sesión único en todas las plataformas. El inicio de sesión único multiplataforma es se considera una panacea de la autenticación de red, e incluso con Kerberos puede ser muy difícil de conseguir debido a la gran variedad entre implementaciones de Kerberos. El objetivo final es que los usuarios tengan Solo un conjunto de credenciales, un par nombre de usuario/contraseña que habilitará Ellos para acceder a todos los recursos de la red independientemente de las plataformas, estos los servicios pueden residir en.

Estos escenarios de interoperabilidad también se abordan en un Microsoft documento, la Guía Paso a Paso para la Interoperabilidad de Kerberos 5, disponible en [http://www.microsoft.com/windows2000/techinfo/planning/security/kerbsteps.asp](http://www.microsoft.com/windows2000/techinfo/planning/security/kerbsteps.asp).

### Uso de un KDC no Microsoft para clientes Windows

Esta sección describe los dos métodos por los cuales un La red Windows puede autenticarse contra un KDC que no sea Microsoft. El primera opción, confianza entre reinos entre un dominio de Windows y un KDC no Microsoft, se utiliza mejor cuando hay una red extensa de Máquinas Windows que requieren administración centralizada y ya tiene un dominio de Windows establecido. La segunda opción es mejor aplicar redes que tienen pocos ordenadores Windows que no son ya miembros de un dominio Windows. Estos escenarios son útiles cuando un grande, se ha instalado un ámbito Kerberos no Microsoft y se está moviendo a los usuarios sería difícil un nuevo dominio de Active Directory.

Cada usuario que acceda a la caja o dominio de Windows debe seguir teniendo que se creen en Active Directory (para el fideicomiso entre reinos opción) o en el equipo local con Windows (para el Windows independiente opción de máquina). Esto se hace para crear un SID para fines de autorización para usuarios autenticados a través del reino Kerberos no Microsoft. Los mapeos se organizarán en cualquier caso para asociar los principales en la base de datos de Kerberos con estas ventanas nombres de usuario. Windows seguirá requiriendo estos usuarios en la base de datos de AD o una base de datos de seguridad local para tener contraseñas válidas, y estas Las contraseñas deben ser seguras, ya que pueden usarse para eludir el Reino Kerberos no Microsoft e iniciar sesión directamente en Windows máquina.

La interoperabilidad presentada aquí solo funciona para Windows servicios que utilizan autenticación Kerberos. Hay varios aplicaciones, especialmente Microsoft Exchange (2000 y posteriores), que aún usar la autenticación antigua de estilo NTLM que ofrece Windows. La aplicación debe ser reescrita para que se use Autenticación de Kerberos. Además, como se ha comentado anteriormente en el sección en el PAC, algunos servicios de Windows no aceptan tickets que no tienen un PAC generado por un controlador de dominio de Windows. Además, sistemas operativos Microsoft antiguos, lanzados antes que Windows 2000, XP y 2003, no pueden participar en los reinos de Kerberos, incluso si forman parte de un dominio Windows, como hacen esos sistemas operativos antiguos no incluir el soporte de Kerberos. Si es compatible con Windows antiguo los sistemas operativos o aplicaciones que utilizan la autenticación NTLM son requeridas, las contraseñas en el dominio de Windows o en la seguridad local la base de datos debe sincronizarse con el reino de Kerberos mediante el ámbito externo significa.

La herramienta Microsoft ksetup

La utilidad ksetup es un programa que establece algunos entradas en el registro de Windows que describen los que no son Windows Reino de Kerberos y KDCs. Las entradas del registro que modifica ksetup se puede encontrar en _HKLM\SYSTEM\CurrentControlSet\Control\Lsa\Kerberos\Domains_, que puede compararse con el archivo _/etc/krb5.conf_ en un host cliente MIT o Heimdal Kerberos. Siempre que Windows machine participa en un reino Kerberos que no es Microsoft mediante confianza entre reinos con un dominio Windows, o directamente con los KDC no de Microsoft, ksetup se utiliza para crear los adecuados Entradas de configuración en el registro. Desafortunadamente, ksetup sí no se instala por defecto con Windows, pero puedes encontrar una copia en el subdirectorio _support\tool_ del Windows CD de instalación de servidor de 2000.

Ten en cuenta que siempre que se cambie algún ajuste de Kerberos, también Directamente a través de la entrada del registro de arriba o a través del kSetup herramienta, la máquina tendrá que reiniciarse para que los cambios se realicen efecto.

La herramienta ksetup reconoce las siguientes banderas:

- /SetDomain

	Esta bandera designa el reino Kerberos que no es Microsoft con la que el equipo Windows se comunicará.

- /MapUser

	Esta bandera crea un mapeo de usuario entre nombres de usuario en la base de datos de usuarios local de Windows y los nombres principales en el Reino de Kerberos. MapUser toma dos parámetros: el primero el parámetro es un nombre principal de Kerberos, y el segundo es el nombre de usuario local en el host de Windows que el El principal será autorizado como. Un asterisco puede usarse en cualquiera de los dos campos para coincidir con todos los nombres principales posibles y nombres de usuario, respectivamente. Por ejemplo, /MapUser * * mapeará todos los principales de Kerberos con el nombre de usuario correspondiente en la máquina o dominio de Windows.

- /AddKdc

	Esta bandera crea un mapeo entre el reino de Kerberos nombres y un KDC que sirva al reino. Esta bandera puede ser especificado varias veces en diferentes comandos ksetup en para seleccionar múltiples KDC por reino.

- /AddKpasswd

	Esta bandera crea un mapeo entre un reino de Kerberos y el KDC maestro que se utiliza para cambiar contraseñas de usuario en El reino.

- /SetMachPassword

	Esta bandera establece la contraseña en la clave de host para el Máquina con Windows. El argumento necesario para esta bandera es el contraseña asociada al host del equipo con Windows principal en la base de datos Unix KDC.


Ahora la información sobre el reino Kerberos no Windows debe se configura en el host de Windows; Esto se logra a través de la Utilidad ksetup. Aunque los sistemas Windows no tienen problemas para usar el DNS encontrar los Controladores de Dominio apropiados para Active Directory dominios, no pueden usar DNS para encontrar las direcciones de los KDC para reinos de Kerberos que no son Windows.

Para nuestro ejemplo, los siguientes comandos tendrán que ser introducido en el host de Windows para crear el correspondiente Configuración:

```
D:\>ksetup /setdomain WEDGIE.ORG
D:\>ksetup /addkdc WEDGIE.ORG freebsd.wedgie.org
D:\>ksetup /addkdc WEDGIE.ORG slave.wedgie.org
D:\>ksetup /addkpasswd WEDGIE.ORG freebsd.wedgie.org
D:\>ksetup /setmachpassword host principal's password
```

Estos comandos crean las entradas de configuración en Windows el registro de anfitriones para el reino WEDGIE.ORG Kerberos. El registro Las entradas funcionan de forma similar al archivo _krb5.ini_ utilizado por MIT Kerberos para definir la información del KDC para Kerberos Reinos. Además, la contraseña de la máquina establecida aquí debe corresponder A la contraseña principal del host establecida antes en kadmin.

A continuación, deben establecerse mapeos entre el principal de Kerberos nombres y nombres de usuario locales en el host de Windows. Estos mapeos son Utilizado para fines de autorización durante el proceso de inicio de sesión. El Los mapeos se crean con el argumento de línea de comandos de la herramienta kSetup.`MapUser`

El comando puede mapear un principal particular de Kerberos para un nombre de usuario dado de Windows por especificando explícitamente sus identidades en el usuario del mapa Orden:`ksetup`

```
D:\>ksetup /mapuser fgump@WEDGIE.ORG guest
```

Este comando asigna el _fgump@WEDGIE.ORG_ principal de Kerberos al nombre de usuario de Windows, guest. Como puedes ver, el nombre principal y el nombre de usuario de Windows no tienen A juego. Hay un acceso directo disponible para mapear todos los principales de Kerberos en un reino al homónimo en la base de datos de usuarios de Windows. Esto puede especificarse usando un asterisco para ambos parámetros de La discusión. Para Ejemplo:`MapUser`

```
D:\>ksetup /mapuser * *
```

Si existe un principal Kerberos con un componente de usuario de _fgump_, y un usuario de Windows llamado _fgump_, el mapeo autorizará al usuario a Inicia sesión en la cuenta _de Windows de FGUMP_ a través de su Credenciales de Kerberos en el ámbito Kerberos no Microsoft.
