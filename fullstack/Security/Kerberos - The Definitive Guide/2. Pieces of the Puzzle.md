## Las tres A

Empezaremos nuestra discusión con un tema que muchos Los profesionales de la red trabajan a diario con las tres A. _Autenticación_, _autorización_, y _la auditoría_ es una parte crucial de cualquier red sin embargo, la diferencia entre ellos suele ser poco clara. Cada uno Uno de estos componentes cumple una función distinta y distinta en una red Plan de seguridad. En particular, nos centraremos en la autenticación y y cómo se relacionan entre sí.

### Autenticación

En pocas palabras, _la autenticación_ es el proceso de verificar la identidad de un usuario particular. Para autenticar a un usuario, se le pide información que probaría su identidad. Esta información puede caer en una o más de tres categorías: lo que sabe, lo que tiene o lo que es. Estas categorías se denominan _factores_ .

El primer factor, lo que él sabe, es el más común En autenticación hoy. Se genera una contraseña secreta cuando el usuario se le concede acceso a una máquina o red. Ese secreto puede ser generados por el propio usuario, eligiendo su propia contraseña y dando se lo lleva al administrador del sistema cuando concede acceso al usuario, o automáticamente a través de algún proceso que genera aleatorios Contraseñas.

El segundo factor, lo que tiene, es menos común pero más seguro alternativa. Un ejemplo de este tipo de autenticación es la ampliamente Implantado el token RSA SecurID. El token SecurID es un pequeño dispositivo electrónico dispositivo que tiene una clave de cifrado integrada y una pantalla LCD. Cada minuto, un algoritmo se ejecuta dentro del dispositivo y actualiza la pantalla LCD pantalla con una nueva combinación de seis dígitos. Solo la persona que posee el dispositivo que puede saber cuál es la contraseña correcta. Otros Sistemas, como los sistemas de tarjetas inteligentes, funcionan con sistemas similares principios.

El tercer factor, lo que es, entra en el ámbito de la biometría. Ya que todos los humanos tienen distintivos características, la biometría mide las propiedades físicas de algunos parte de nuestro cuerpo y utiliza esa información para autenticar usuarios. Los sistemas biométricos actuales incluyen escaneo de huellas dactilares y retina escaneo, reconocimiento de huellas de voz y reconocimiento facial. Biometría aún no disfruta de un mercado amplio por varias razones: los productos son Aún inmaduros para su uso generalizado, algunos son muy caros (como escaneo de retina), y, quizá la razón más importante de todas, allí actualmente apenas hay soporte de software para estos dispositivos.

Por supuesto, un sistema de autenticación puede combinar estos factores. Por ejemplo, el proceso de inicio de sesión de RSA SecurID implica no solo el Token SecurID pero también un PIN numérico. Por lo tanto, SecurID combina los Primero, dos factores: lo que tienes y lo que sabes. Obviamente, un un sistema que combina más de un factor es más seguro que un sistema Que depende solo de uno.

El propio protocolo Kerberos no especifica cuál Deben utilizarse factores de autenticación. Aunque la mayoría de las implementaciones usan Un sistema basado en contraseñas, existen implementaciones, como la One presentes en Windows 2000 y versiones posteriores de Microsoft, que permiten Kerberos Inicio de sesión vinculado a usar tarjetas inteligentes. Las tarjetas inteligentes, que trataremos más a fondo en [el capítulo 10](https://learning.oreilly.com/library/view/kerberos-the-definitive/0596004036/ch10.html "Chapter 10. Kerberos Futures"), evitan el uso de las contraseñas como único factor de autenticación. Por lo tanto, hacen El proceso de inicio de sesión es más sencillo para los usuarios, además de proporcionar una mayor seguridad mecanismo de autenticación.

Una vez que el servidor recibe la información del usuario que prueba su identidad, el servidor determina si esa información es Correcto. ¿La contraseña que introdujo el usuario coincide con la que aparece ¿En la base de datos de contraseñas? Si es así, entonces el usuario queda autenticado. Si No, entonces la solicitud es denegada.

Normalmente se realizan ataques contra sistemas de autenticación de forma de fuerza bruta, donde un atacante utiliza un ordenador que prueba combinación tras combinación hasta que el usuario Se ha encontrado la contraseña. Se pueden emplear diferentes pólizas durante autenticación para evitar que un atacante intente continuamente una gran lista de contraseñas, y las discutiremos en [el Capítulo 6](https://learning.oreilly.com/library/view/kerberos-the-definitive/0596004036/ch06.html "Chapter 6. Security").

### Autorización

_La autorización_ se refiere a conceder o denegar el acceso a una entidad específica recursos basados en la identidad del usuario solicitante. Este paso es realizada después de que un usuario sea identificado mediante autenticación. La autorización suele realizarse a través de listas de control de acceso, que Asocia las identidades de usuario con derechos específicos. La autorización incluye información como la membresía de un grupo de usuario, políticas de usuario y Otra información que determina el nivel de acceso que tiene ese usuario a recursos informáticos o de red.

Es importante señalar que la capacidad de hacer la correcta Las decisiones de autorización se basan únicamente en una autenticación sólida mecanismo. La única forma de tomar una decisión correcta de autorización es Hecho es si el usuario ya ha sido correctamente autenticado. La autorización deja de funcionar si el método de autenticación no puede funcionar De confianza. Si el mecanismo de autenticación devuelve una identidad falsa a el mecanismo de autorización, entonces no hay forma de que el mecanismo de autorización para corregir esto, y puede permitir que un atacante para hacerse pasar por un usuario legítimo.

Como resultado, mecanismos sólidos de autorización dependen de un Sistema de autenticación efectivo. Sistemas que dependen de débiles La autenticación fallará, por muy sofisticada que sea puede serlo. Un ejemplo es el protocolo estándar NFS. NFS exige que los servidores confíen en los clientes, ya que los usuarios son "autenticados" por un UID en texto plano enviado por el cliente. Claramente, este mecanismo hace trivial suplantar cualquier nombre de usuario en un Servidor NFS. La facilidad para eludir la autenticación anula cualquier sofisticado mecanismo de autorización de la Lista de Control de Acceso que puede ser empleado en el servidor, ya que un atacante puede fácilmente hacerse pasar por cualquiera otro ID de usuario dado al control de una máquina cliente.

### Auditoría

La última A en las tres A es _auditing_. La auditoría obtiene los resultados de la autenticación y Autorización y registro de estos resultados en un registro de auditoría. La auditoría El registro registra todas las acciones realizadas por la autenticación y la autorización Pasos para futura revisión por parte de un administrador. Mientras la autenticación y las autorizaciones son sistemas preventivos en los que el acceso no autorizado es Prevenido, la auditoría es un sistema reactivo. La auditoría no impedirá que un atacante que no acceda a tu red; en cambio, dará Tienes un registro detallado de cuándo, dónde y cómo penetró el atacante tus sistemas.

Todas las implementaciones de Kerberos que vamos a tratar tienen la capacidad de Eventos de registro que tienen lugar durante las solicitudes de autenticación. Nos llevamos un análisis muy detallado de la auditoría en [el capítulo 6](https://learning.oreilly.com/library/view/kerberos-the-definitive/0596004036/ch06.html "Chapter 6. Security"), donde revisaremos qué el registro puede activarse en las distintas implementaciones de Kerberos y cómo para ver esos registros.

## Directorios

Un concepto erróneo común sobre Querbero y otros las tecnologías de autenticación son que de alguna manera reemplazan los directorios, como el archivo _Unix /etc/passwd_, NIS, NetInfo o LDAP. En la misma línea, otro concepto erróneo común es que Los directorios son buenos sistemas de autenticación por sí mismos. Por lo tanto, una Es necesario distinguir entre autenticación, autorización y directorios. Para una analogía real de qué roles tiene cada uno de estos componentes reproducidos, consulta la barra lateral [Autenticación confusa, Autorización y directorios](https://learning.oreilly.com/library/view/kerberos-the-definitive/0596004036/ch02s02.html#kerberos-CHP-2-SIDEBAR-1 "Confusing Authentication, Authorization, and Directories").

Los directorios contienen datos que describen recursos, como ordenadores, impresoras y cuentas de usuario que están contenidas dentro de un determinado Networking. Los directorios pueden ser tan simples como un archivo de texto, como los _archivos /etc/passwd_ y _/etc/group_ en sistemas Unix tradicionales, que listan las cuentas de usuario activas y sus permisos de grupo. O un directorio puede ser un LDAP complejo estructura de directorios, como Active Directory de Microsoft.

Los directorios pueden contener datos de autenticación. Autenticación "contra" un directorio adopta dos formas: una máquina cliente puede contactar con un directorio, obtener el versión hashada de la contraseña del usuario, hash la contraseña proporcionada por el Usuario, y comparar ambos. Este método es utilizado por NIS, por ejemplo. El otra forma, empleada por la mayoría de los mecanismos de autenticación LDAP, es intentar vincular al directorio LDAP usando las credenciales que el Proporcionado por el usuario. Si al usuario se le concede acceso al directorio, el La autenticación es exitosa. El módulo PAM de pam_ldap utiliza este último método para autenticarse contra un directorio LDAP.

Usar Kerberos para gestionar la autenticación es superior a estos métodos para varios Motivos:

- Usando los tickets de Kerberos, los usuarios pueden obtener acceso único acceso a todos los recursos de red sin necesidad de la máquina cliente para almacenar en caché la contraseña del usuario. Los tickets de Kerberos son criptográficos mensajes que solo son válidos durante un periodo relativamente corto, Normalmente entre 8 y 24 horas. El compromiso de la contraseña de un usuario, en el por otro lado, proporciona al atacante la capacidad de hacerse pasar por el Usuario legítimo durante un periodo mucho más largo—específicamente, hasta que La contraseña cambia o caduca.
    
- Con Kerberos, la contraseña del usuario nunca se envía en claro a través de la red durante el proceso de inicio de sesión.
    
- Kerberos define un protocolo ampliamente adoptado y estandarizado que sea adecuado para la autenticación.
    

Por lo tanto, mientras que un directorio puede contener autenticación información (por ejemplo, Active Directory de Microsoft almacena el Base de datos Kerberos en su almacén LDAP), es preferible usar Kerberos para realizar la autenticación en lugar de usar el directorio para autenticación directa.

Autenticación confusa, autorización y Directorios

Muchos sistemas de autenticación también incluyen autorización funciones, por lo que estos conceptos pueden confundirse fácilmente entre sí. Por ejemplo, el archivo `tradicional Unix /etc/passwd` contiene tanto datos de autenticación como de autorización. Para hacer ¡Y lo peor aún, también funciona como directorio! Así que es muy fácil Te confunde al leer sobre las diferencias entre todos estos conceptos cuando la distinción nunca se ha hecho en el pasado.

Para ayudar a dejar clara la distinción, digamos que quieres Entra en la discoteca local más popular. Analizaremos qué pasos te pide Hay que hacerlo para acceder al colegio de abogados.

Cualquiera Poseer tu billete puede hacerse pasar por ti, siempre que el billete sigue siendo válido (los billetes de Kerberos tienen una vida limitada, como haremos discutirlo más adelante; normalmente, la vida dura un día).

### Cifrado

La palabra _criptografía_ moderna deriva de dos palabras griegas antiguas: _cryptos_, que significa oculto o secreto, y _graphein_, o escritura. Kerberos utiliza criptografía proporcionar cifrado y descifrado de sus mensajes a través de la red. Por lo tanto, el cifrado se refiere al proceso de conversión de un mensaje, o texto plano, en galimatías, que si se interceptan, no revelan el contenido del mensaje original. Gobiernos y corporaciones desde hace tiempo emplean cifrado para mantener su información segura frente a miradas indiscretas. La aparición de Internet, donde cualquier red La administradora puede monitorizar y leer el tráfico en su red y en cualquier el tráfico que pasa por su red ha obligado a los fabricantes de software a Incorpora cifrado en los programas de software cotidianos. Usos de Kerberos Cifrado no solo para proteger los intercambios de autenticación que envía y recibe de espionajes, pero también para evitar que hackers creen mensajes falsos.

Existen muchas formas diferentes de cifrar datos. Estos métodos se denominan algoritmos de cifrado, o en el lenguaje de Kerberos, Tipos de cifrado. Existen varios tipos diferentes de cifrado que son compatibles con implementaciones de Kerberos 5. El más ampliamente apoyado El tipo de cifrado es DES, pero se está trabajando para reemplazarlo por Triple DES y el nuevo Estándar Avanzado de Cifrado (AES). Otro ampliamente el tipo de cifrado utilizado es el algoritmo RC4, que se emplea principalmente en La implementación de Kerberos por parte de Microsoft.

La ventaja de pasar a algoritmos de cifrado más potentes es protección contra el criptoanálisis por fuerza bruta. Vamos a echar un vistazo Más detalles sobre ataques de fuerza bruta contra el cifrado algoritmos en Kerberos en [el capítulo 6](https://learning.oreilly.com/library/view/kerberos-the-definitive/0596004036/ch06.html "Chapter 6. Security").

### Integridad del mensaje

Aunque el cifrado proporciona privacidad, la integridad del mensaje asegura al destinatario que el mensaje no fue manipulado durante Tránsito. Mientras que el cifrado tal y como se usa en Kerberos te da mensaje integridad para "gratis", ya que solo los dos puntos finales tienen el requisito clave para cifrar y descifrar mensajes, existen algoritmos de integridad de mensajes que pueden garantizar la integridad del mensaje sin La sobrecarga del cifrado. Verás algoritmos de integridad de mensajes se les denomina hashes unidireccionales, o simplemente hashes.

Los hashes funcionan como funciones matemáticas unidireccionales. Toman un Mensaje de entrada que es arbitrariamente largo, pásalo por un matemático y emiten un mensaje de tamaño fijo (normalmente 64-256 bits) que representa la entrada. La idea detrás de la función hash es que Aunque es fácil calcular la salida hash para una entrada dada, es matemáticamente difícil ir en la dirección contraria y derivar una entrada que produce la misma salida, de ahí su naturaleza "unidireccional".

Un ejemplo trivial de una función hash es sumar todos los bytes los valores de un mensaje juntos, y toman el módulo sumado a máximo número—digamos, 1024. No es posible reconstruir la entrada original Fluye de esta suma. Otra propiedad de un algoritmo hash es su fuerza criptográfica, o la capacidad de los atacantes para crear entradas diseñado para producir un valor hash dado. Dado que el valor hash (en este el caso, la suma de los bytes del mensaje módulo 1024) contiene menos datos que el flujo de entrada (este ejemplo sencillo solo proporciona 1025 posibles valores hash), hay muchas entradas que producirán un hash dado Valor. Estos se denominan colisiones y algoritmos de hash criptográficamente seguros Intenta reducir la probabilidad de que un atacante encuentre dos entradas que hash al mismo valor.

Así como existen diferentes algoritmos de cifrado, también existen varios algoritmos de integridad de mensajes diferentes que se utilizan comúnmente en Kerberos. De lo más débil a lo más fuerte, los algoritmos de integridad de mensajes incluidos en el MIT La distribución de Kerberos incluye CRC-32, MD5 y el Secure Hash Algoritmo (SHA1).

### Reinos, Principios e Instancias

Cada entidad contenida dentro de una instalación de Kerberos, incluyendo los usuarios, ordenadores y servicios individuales que se ejecutan en servidores tienen un _principio_ asociado. Cada principal está asociado a un clave a largo plazo. Esta clave puede ser, por ejemplo, una contraseña o una frase de paso. Los directores son nombres únicos a nivel mundial. Para lograrlo, el El principal está dividido en una estructura jerárquica.

Cada principio comienza con un nombre de usuario o de servicio. El Nombre de usuario o nombre de servicio es seguido de una instancia opcional. El instancia se utiliza en dos situaciones: para principales de servicio (que lo discutiremos más adelante), y para crear principios especiales para Uso administrativo. Por ejemplo, los administradores pueden tener dos Directores: uno para el uso diario y otro (un "administrador") principal) para usarse solo cuando el administrador necesita elevación privilegios.

El nombre de usuario y la instancia opcional, en conjunto, forman una identidad única dentro de un _reino_ dado. Cada instalación de Kerberos define un cargo administrativo un ámbito de control distinto de todos los demás Kerberos instalación. Querbero define esto como el _reino Nombre_. Por convención, el reino de Kerberos para un DNS dado dominio es el dominio convertido a mayúsculas. Por ejemplo, el calzón interior International, que posee el nombre de dominio _wedgie.org_, crearía un reino Kerberos para su usuarios llamados WEDGIE.ORG.

Aunque es la convención hacer que el nombre del reino sea equivalente a el nombre de dominio DNS, no es necesario hacerlo. Sin duda hace La configuración es más sencilla, como veremos más adelante, pero es perfectamente legal tener un nombre de reino de, por ejemplo, MIREINO. FALSA cuando tu nombre de dominio _es wedgie.org_. También hay que tener en cuenta que los reinos son sensible a mayúsculas minúsculas (a diferencia de los nombres de dominio), así que el reino MyRealm.BOGUS es diferente de MYREALM. FALSO.

Ahora examinemos un principal de Kerberos que ha sido asignado a John Doe, que trabaja en el departamento de informática de Wedgie Internacional:

```text
jdoe@IT.WEDGIE.ORG
```
Esta es la forma más sencilla que puede adoptar un principal, y es válida director tanto bajo Kerberos 4 como Kerberos 5. Este director representa el nombre de usuario jdoe, sin instancia, y un reino de ESO. WEDGIE.ORG.

#### Principales de servicio y anfitriones

Los principios de servicios son ligeramente diferentes a los del usuario directores. Para distinguir el servicio los principales para el mismo servicio pero con nombres de host diferentes, el el componente de instancia contiene el nombre de host de la máquina el servicio El director está ubicado en. Servicios que utilizan autenticación Kerberos se dice que están _kerberizados_.

Además de los principales anfitriones y de servicio, los Kerberos El sistema en sí contiene varios principios. Los más importantes de Estos directores "especiales" son los directores KRBTGT. Mientras que el La sintaxis es similar, hay algunas diferencias notables. Tomaremos un mira primero el formato principal de Kerberos 4.

#### Principios de Kerberos 4

Los principios de Kerberos 4 se componen de tres componentes: el nombre de usuario, una instancia opcional y el reino. El nombre de usuario y la instancia están separados por una punto, y el nombre de usuario y la instancia están separados del reino por un símbolo at (@). Veamos un ejemplo de Kerberos 4 Director:

```
jdoe.admin@IT.WEDGIE.ORG
```
Este ejemplo es similar al anterior, con la excepción que este principio contiene una instancia—en este caso, admin.

Los principales de servicio Kerberos 4 contienen solo el nombre de host del servidor al que se asigna el director. No hay un componente de dominio, ya que el separador para nombres de dominio es el mismo que el separador entre el nombre de usuario y la instancia (el punto). Un ejemplo de host director del _unixsvr.it.doesystems.com_ anfitrión en el IT.WEDGIE.ORG El reino sería:

```
host.unixsvr@IT.WEDGIE.ORG
```

Esta es una de las carencias de Kerberos 4, tal y como dicta que no puedes tener más de una máquina con el mismo nombre de host en Tu reino, aunque tengan nombres de dominio diferentes. Un nombre de anfitrión _de unixsvr.it.wedgie.org_ que también es miembro de el reino IT.WEDGIE.ORG Kerberos se asignaría al mismo servicio Principal, como el nombre de host de ejemplo anterior, _unixsvr.it.doesystems.com_.

En general, las formas que puede tomar un principal de Kerberos 4 Son:

```
user[.instance]@REALM
service.hostname@REALM
```

#### Principios de Kerberos 5

Los principios de Kerberos 5 contienen el mismo básico componentes como un principal de Kerberos 4. En lugar de una sola instancia componente, sin embargo, los principios de Kerberos 5 pueden contener varios componentes de subinstancia. Además, en lugar de usar un punto para separar los componentes de nombre de usuario e instancia, Kerberos 5 utiliza un reenvío Slash.

Echemos un vistazo a un ejemplo de usuario de Kerberos 5 Director:

```
jdoe/admin@IT.WEDGIE.ORG
```

Este ejemplo es equivalente al primer ejemplo de Kerberos 4, mostrando el formato del director de John Doe con un administrador instancia.

Los principales anfitriones y servicios de Kerberos 5 incluyen al nombre de dominio calificado (FQDN) del host que es el servicio Instalado activado. Al incrustar el FQDN en el principal, Kerberos 5 Permite a los administradores tener más de un host con la misma nombre de host, pero con diferentes componentes de dominio ubicados en el mismo reino. Aquí tienes un ejemplo de un principal host Kerberos 5:

```
host/unixsvr.it.wedgie.org@IT.WEDGIE.ORG
```

En general, los principios de Kerberos 5 tienen lo siguiente Formato:

```
component[/component][/component]...@REALM
```

En este formato, hay un componente obligatorio, seguido de cualquier número de componentes opcionales, separados por cortes hacia adelante. A continuación de los componentes aparece el nombre del reino, que se separa de los componentes con signo de at (@), igual que en Kerberos 4. En la práctica, existen dos tipos de principios de Kerberos 5 que verás en uso, igual que en Kerberos 4, mostrado a continuación:

```
username[/instance]@REALM
service/fully-qualified-domain-name@REALM
```

### Keys, Salts, and Passwords

Se utilizan muchos términos diferentes para hablar del cifrado en Kerberos. Todos están relacionados entre sí, pero hay algunos importantes Conceptos específicos de Kerberos que requieren discusión.

Primero, todas las claves secretas se comparten entre al menos dos partes, fin el usuario o servicio y el Centro de Distribución de Claves. Sin embargo, un método es necesitaba cambiar una contraseña alfanumérica que la gente pudiera recordar en una clave de cifrado binaria que el ordenador puede usar para cifrar y Descifrar mensajes. Se utiliza una función llamada _string2key_ para convertir la contraseña de un usuario en cifrado clave. Esta función aplica varias transformaciones a cada usuario Contraseña para convertir una contraseña basada en caracteres en una serie de números que constituyen una clave de cifrado.

La parte más importante de esta transformación se conoce como _la sal_. En términos generales, la sal es una secuencia de caracteres Eso se añade a una contraseña antes de hacerla hash para hacerla más única. Para Kerberos 5, la sal predeterminada es el nombre del reino. Sumando el nombre de realm al nombre de usuario, dos claves de cifrado diferentes son se genera si un usuario usa la misma contraseña en dos reinos diferentes. Esto significa que si un usuario usa la misma contraseña en dos reinos, y Su llave está comprometida en una de ellas, no automáticamente comprometer su llave en la otra.

### El Centro de Distribución de Claves

La _distribución de claves de Kerberos Center_ , o KDC para abreviar, es una parte integral del Kerberos sistema. El KDC consta de tres componentes lógicos: una base de datos de todos los principales y sus claves de cifrado asociadas, el _Servidor de Autenticación_ y el _Servidor de Concesión de Tickets_. Mientras que cada uno de estos Los componentes son lógicamente separados, normalmente se implementan en un un solo programa y ejecutarse juntos en un solo espacio de procesos.

En un reino de Kerberos dado, debe haber al menos un KDC. Mientras los recursos necesarios para ejecutar un KDC en una máquina son escasos, es se recomendó encarecidamente que cada KDC fuera una máquina física separada. Dado que todos los datos cruciales, incluidos los secretos para cada principal en tu reino, está ubicado en todos los KDC de la red, es Es fundamental que esos servidores sean lo más seguros posible. Además, en para que los usuarios puedan autenticarse con éxito con Kerberos habilitado al menos un KDC debe estar funcionando en todo momento.

Cada Centro de Distribución de Claves contiene una base de datos de todos los los principales contenidos en el reino, así como sus asociados Secretos. La mayoría del software KDC también almacena información adicional para cada uno Principio en esta base de datos, como la duración de la contraseña, la última contraseña Cambio, y más. Windows 2000 y 2003 mantienen esta base de datos en el Active Directory, su tienda LDAP. Implementaciones de código abierto, incluyendo al MIT y Heimdal, mantener esta base de datos en una base especializada, un archivo ligero en el sistema de archivos del KDC.

Dado que un reino de Kerberos puede contener múltiples máquinas KDC, el la base de datos de cada KDC debe mantenerse sincronizada para garantizar la unificación autenticación. Si un servidor tiene datos obsoletos, entonces intentos legítimos autenticarse contra ese servidor puede fallar, ya que no tiene una copia actualizada de la base de datos Kerberos. No hay método estándar de la sincronización se especifica mediante el protocolo Kerberos, por lo que los proveedores tienen crearon sus propios protocolos de replicación.

#### El Servidor de Autenticación

El Servidor de Autenticación (AS) emite un _Ticket_ Granted Ticket cifrado (también conocido como TGT) a los clientes que deseen "iniciar sesión" al reino de Kerberos. El cliente no tiene que demostrar su identidad al KDC; en su lugar, el TGT que se envía de vuelta a la El cliente está cifrado con la contraseña del usuario. Dado que solo el usuario y el KDC conoce la contraseña del usuario cuando el proceso de inicio de sesión intenta descifrar el ticket usando la contraseña proporcionada por el usuario, solo el La contraseña correcta descifrará correctamente el ticket. Si es incorrecto se usa la contraseña, el ticket se descifrará en basura y el usuario se le pide que lo intente de nuevo.

El TGT devuelto por el Servidor de Autenticación puede entonces ser Utilizado, una vez descifrado por el cliente, para solicitar un servicio individual Entradas. El TGT es la pieza crucial que elimina el Requisito para que un usuario reescriba su contraseña en cada vez Al servicio que contactan.

#### El servidor de concesión de tickets

No debe confundirse con el Ticket de Concesión de Multas que discutimos brevemente en la última sección, la Concesión de Tickets El servidor (TGS) emite tickets de servicio individuales a los clientes a medida que estos Pídelos. El Servidor de Emisión de Tickets recibe dos datos Del cliente: una solicitud de ticket que incluye el nombre principal representando el servicio que el cliente desea contactar y un Ticket Concediendo un ticket que ha sido emitido por el Servidor de Autenticación. El TGS verifica que el TGT sea válido comprobando que lo sea cifrado con la clave TGT del servidor Kerberos, y luego emite la Usa el ticket de servicio que solicitó.

### Entradas

Kerberos introduce el concepto de _tickets_. Conceptualmente, un ticket de Kerberos es un dato cifrado estructura emitida por el Centro de Distribución de Claves que incluye una estructura compartida clave de cifrado que es única para cada sesión, y los tickets señalan que Indique, por ejemplo, si el ticket puede ser reenviado a otro servicio, junto con otros campos. Las entradas cumplen dos propósitos: confirmar la identidad de los participantes finales y establecer una clave de cifrado de corta duración que ambas partes pueden compartir para garantizar la seguridad comunicación (llamada clave _de sesión_ ).

La mejor forma de pensar en las entradas es como una licencia (emitida por el KDC) que confirma tu identidad. Como una licencia en la vida real mundo, cada billete emitido por Kerberos incluye datos sobre ti, cómo Siempre que la licencia (o ticket) sea válida y haya restricciones en su uso. Los principales campos que Kerberos incluye en cada ticket son:

- El nombre principal solicitante (el principal del usuario)
    
- El nombre principal del servicio
    
- Cuando el ticket se vuelve válido y cuando el ticket se vuelve válido expira
    
- Una lista de direcciones IP desde las que se puede usar el ticket
    
- Una clave secreta de cifrado compartida (clave de "sesión") para Comunicación usuario/aplicación
    

Algunos de estos campos están rellenados por el KDC; por ejemplo, el KDC impone una vida útil máxima de entradas, y el KDC genera una sesión única clave cada vez que emite una entrada. Los otros campos se rellenan con el cliente y se pasa al KDC cuando hace una solicitud de ticket. Cuando un ticket es generado por el KDC, se cifra para asegurar que los atacantes no pueden tomar un ticket válido y modificarlo; por ejemplo, a Aumenta su vida útil o el nombre principal validado del cliente.

Las entradas duran relativamente poco. Una vida útil máxima típica para un billete de Kerberos son 10-24 horas. Esta vida relativamente corta equilibra la comodidad del inicio de sesión único con la amenaza de seguridad de un atacante que roba credenciales y las utiliza durante un largo periodo de tiempo. Limitando la vida útil de los tickets de Kerberos, el daño de un El ticket robado se minimiza, mientras que el usuario sigue disfrutando de la comodidad de iniciar sesión con un solo inicio de sesión durante la jornada laboral.

#### La caché de tickets (o credenciales)

Ahora que tenemos todas estas multas, ¿dónde las ponemos? Bueno, desafortunadamente, La respuesta es: depende. La implementación original de Kerberos escrita por MIT utiliza una caché de credenciales basada en archivos. Es decir, cuando tú inicia sesión en Kerberos y, a medida que te emitan entradas para Kerberizado. servicios, todos los tickets se almacenan en un archivo. Este método fue elegido porque es el más portátil; Cada plataforma tiene un y es fácil de leer y escribir en archivos. Sin embargo, esto El método es inflexible e inseguro. Por lo tanto, otros puertos del MIT código Kerberos, así como implementaciones independientes de otros Los proveedores incluyen otros métodos para almacenar tickets. Tanto el Las implementaciones de Kerberos de Microsoft y Apple incluyen un caché de credenciales basada en memoria que garantiza que las credenciales se mantengan en memoria y destruido al finalizar el inicio de sesión sesión.

Dado que la caché predeterminada de credenciales es una credencial basada en archivos cache, veremos cómo es uno. No importa dónde sea La caché de credenciales se almacena, pero sigue conteniendo la misma información: un User Principal y un conjunto de tickets de servicio que el usuario tiene obtenida durante toda su sesión de inicio de sesión. Una caché de credenciales de muestra se muestra a continuación:

```
$ klist
Ticket cache: FILE:/tmp/krb5cc_502_auJKaJ
Default principal: jgarman@WEDGIE.ORG

Valid starting     Expires            Service principal
09/10/02 01:48:12  09/10/02 11:48:12  krbtgt/WEDGIE.ORG@WEDGIE.ORG
09/10/02 01:48:14  09/10/02 11:48:12  host/cfs.wedgie.org@WEDGIE.ORG
09/10/02 04:20:42  09/10/02 11:48:12  host/web.wedgie.org@WEDGIE.ORG
```

En este ejemplo, la caché de credenciales para el principal de usuario de _jgarman@WEDGIE.ORG_ se almacena en el archivo _/tmp/krb5cc_502_auJKaJ_. Las cachés de credenciales sí solo estar asociado a un principal de usuario a la vez; si quisiera accedería a servicios con un principal _de jgarman/admin@WEDGIE.ORG_ en su lugar, yo habría tenido destruir mis tickets actuales y volver a iniciar sesión en Kerberos como _jgarman/admin@WEDGIE.ORG._
