## Ataques de Kerberos

Aunque puede que no sea posible que un hacker alimente a tu Kerberos KDC es una tarta especiada para ponerla en reposo, hay algunos electrónicos ataques que pueden comprometer la seguridad de tu sistema Kerberos. Listados A continuación se presentan posibles escenarios de compromiso y su efecto en la seguridad del sistema Kerberos.

- Compromiso raíz de un KDC de Kerberos máquina. Un compromiso a nivel raíz de una máquina KDC (maestro o cualquiera de los esclavos) otorga al atacante control total sobre el Todo el sistema de autenticación Kerberos. Aunque los Kerberos la base de datos se cifra en disco con la clave maestra de Kerberos, la La clave maestra también se mantiene en el disco del KDC, por lo que no hay intervención manual es necesario (para introducir la contraseña maestra) cuando el servicio KDC se ha iniciado. Además, dado que todas las implementaciones de Kerberos proporcionan acceso infailible a la base de datos de Kerberos para la raíz o Usuario administrador en el KDC, toda tu base de datos de Kerberos debería se considere comprometido en caso de que los atacantes consigan raíz acceso a cualquier KDC de tu red. Véase [la sección 6.4](https://learning.oreilly.com/library/view/kerberos-the-definitive/0596004036/ch06s04.html "Protecting Your KDC") más adelante en este artículo Capítulo para consejos para prevenir un ataque exitoso contra tu KDC.
    
- Compromiso de un Kerberos credenciales de administrador. Si un atacante obtiene la contraseña de un Kerberos Administrador principal, ese atacante tiene acceso completo al Toda la base de datos de Kerberos. La mayoría de las implementaciones de KDC permiten administradores para volcar remotamente el contenido de la base de datos para Fines de copia de seguridad, y un atacante puede usar esta funcionalidad para crear Una copia completa de tu base de datos de autenticación. Con acceso total a la base de datos, el atacante también puede crear y modificar cualquier Kerberos director. Asegúrate de que solo un grupo muy pequeño de usuarios tenga acceso administrativo y establecer políticas en esos usuarios que hacen cumplir Comprobación estricta de contraseñas y al menos una contraseña mensual cambios.
    
- Compromiso de raíz de un servidor máquina. Para que la autenticación mutua de Kerberos funcione, un servicio Debe tener acceso a un principal de servicio. Estos principales de servicio, como se explica en [el capítulo 4](https://learning.oreilly.com/library/view/kerberos-the-definitive/0596004036/ch04.html "Chapter 4. Implementation"), residen en el sistema de archivos del servidor, ya sea como parte de una pestaña de teclas típicamente usados por implementaciones de Unix, o los Secretos LSA en Implementaciones de Microsoft (véase Q184017 en el sitio de soporte de Microsoft). Si un atacante obtiene acceso root a una máquina servidora, todos Los servicios kerberizados que se ejecutan en esa máquina se ven comprometidos. En además, algunos servicios, como el sistema de archivos distribuido AFS, Comparte un único principio de servicio en todos los servidores. En este caso, El acceso root a una máquina de servidor de archivos AFS comprometería todos los archivos y servidores de bases de datos en la celda AFS. Una vez que un atacante tiene acceso a un responsable de servicio, el atacante puede hacerse pasar por eso servicio y también descifrar el tráfico cifrado enviado entre clientes y El servicio comprometido. La seguridad de los servicios kerberizados en funcionamiento en un servidor depende de la seguridad de ese servidor individual; Por lo tanto, todos los servidores deberían estar protegidos en proporción al valor de los recursos almacenados en ese servidor.

> [!tip]
> Es importante señalar que, mientras el compromiso de un La máquina servidor sí compromete los servicios que se ejecutan en ese Máquina, no compromete las credenciales individuales de los usuarios. En ningún momento en el intercambio de protocolos Kerberos hace un servicio Kerberos recibir cualquier información que le permita reconstruir el autenticando directamente la contraseña del usuario. Sin embargo, sigue siendo Es posible montar un ataque de fuerza bruta o de diccionario contra credenciales presentadas a los servicios, tal como el autenticador cifrado con la clave a largo plazo del usuario.
    
- Compromiso raíz de un cliente máquina. Un compromiso raíz de una máquina cliente proporcionará un Atacante con todos los tickets almacenados en caché en esa máquina. Como las entradas son Limitado en tiempo, no es un compromiso tan crítico como un atacante obtener la contraseña de los usuarios. Sin embargo, con acceso root a un cliente el atacante puede instalar de forma oculta un detector de teclado para capturar la contraseña de un usuario al iniciar sesión en su máquina. Por lo tanto, cuando una máquina cliente es comprometida, las contraseñas de todos Los usuarios que hayan iniciado sesión en esa máquina deberían ser considerados también comprometido. En caso de que un cliente se comprometa, los usuarios Quienes hayan iniciado sesión en ese cliente deben cambiar inmediatamente su Contraseñas.
    
- Compromiso del usuario Credenciales. Hay dos posibilidades en este escenario: o bien la la caché de credenciales (tickets) del usuario queda expuesta, o la contraseña de un usuario comprometido. Si un atacante obtiene la credencial no cifrada de un usuario caché, los tickets contenidos en esa caché solo son válidos para la Periodo de tiempo especificado en los tickets. Por otro lado, si un El atacante adquiere la contraseña del usuario, el atacante puede suplantar ese usuario hasta que el usuario cambie su contraseña.
    

De la lista anterior, el único hecho que subyace a todo eso Los escenarios es la importancia de mantener todas las máquinas en tu red seguro. Instalar Kerberos en tu red no disminuye la Es importante mantener todas las máquinas, incluso los escritorios de los usuarios finales, seguras frente a ataque externo. La concesión de cualquier máquina en tu red tendrá algún efecto perjudicial en la seguridad de tu autenticación Kerberos sistema.

### Otros ataques

Dado que Kerberos solo proporciona un servicio de autenticación, existen varias amenazas de seguridad que una instalación de Kerberos no hará Protege contra. Los siguientes ataques no son ataques directos contra el propio sistema Kerberos, pero existen problemas relacionados con proporcionando un servicio de autenticación seguro y disponible en general. Estos las técnicas pueden usarse para atacar cualquier sistema de autenticación, y Kerberos no es una excepción:

Denegación de servicio

Se puede llevar a cabo un ataque de denegación de servicio contra los KDC de tu organización saturándolos con autenticación peticiones. El gran número de solicitudes que llegan puede ralentizarse tiempos de respuesta a solicitudes legítimas, o incluso, en casos extremos En los casos, que se bloqueen las máquinas donde están tus KDCs. Kerberos No puede proteger contra ataques de denegación de servicio y sí lo es generalmente recomendado que tu red, incluido tu Kerberos Los KDC pueden estar protegidos desde Internet para evitar este tipo de Atacar. Añadir KDC adicionales a tu red para reducir la redundancia también puede mitigar los efectos de un ataque DoS.

El "insider"

Kerberos no puede proteger contra un internamiento Usuario autorizado que decide hacer un uso indebido de sus privilegios. Para por ejemplo, un administrador de Kerberos rebelde podría modificar o eliminar información de la base de datos de Kerberos.

Ingeniería social y exposición de contraseñas

De manera similar, Kerberos no puede proteger contra usuarios individuales que revelan sus contraseñas a los atacantes, ya sea de forma inadvertida o como resultado de una ingeniería social Atacar. El uso de Kerberos no disminuye la importancia de Formación de usuarios para mantener las contraseñas seguras y no revelarlas sus contraseñas para cualquiera, incluidos aquellos que dicen formar parte de tu personal informático. De manera similar, Kerberos no puede impedir que los usuarios desde reutilizar sus contraseñas en otros sitios menos seguros que Puede gestionar las contraseñas sin problema. Hackers que lograron Ataca un sitio menos seguro donde un usuario ha reciclado su La contraseña de Kerberos obtendrá un nombre de usuario y contraseña válidos para tu reino de Kerberos.

Fallos de seguridad en el propio software de Kerberos

Este riesgo no puede subestimarse. Desgraciadamente, Con el estado actual de la ingeniería de software, es Muy difícil escribir código seguro. Como todos los demás Paquetes de software disponibles, cada implementación de Kerberos tiene Tuve problemas de seguridad en algún momento, y estos problemas A veces puede llevar a un compromiso de tus KDCs. Por lo tanto, es extremadamente importante mantenerse informado sobre tu Kerberos parches de vendedores, y aplícalos tan pronto como se conviertan Disponible.

Ahora que hemos cubierto los ataques que se pueden llevar a cabo contra una red Kerberos, echaremos un vistazo a algunos problemas de seguridad en la El propio protocolo Kerberos.

## Problemas de seguridad de protocolos

Primero, revisitemos la razón subyacente por la que la Se desarrolló el protocolo Kerberos. Kerberos fue diseñado para proteger datos de autenticación que pasan por una red en el clear. Antes Kerberos, cuando un usuario desea iniciar sesión en un servicio remoto, el cliente El software pasaba las credenciales del usuario (una contraseña) al servidor en Texto claro. Dado que las redes son medios de radiodifusión, donde todas las emisoras conectados a un segmento de red pueden "escuchar" todo el tráfico en ese segmento, Enviar contraseñas en claro a través de una red es extremadamente inseguro. Por lo tanto, Kerberos cifra todos los intercambios de autenticación que ocurren por la red. Sin embargo, el cifrado es solo una parte de la solución, y los diseñadores de Kerberos han pensado mucho en garantizar la seguridad un sistema lo más posible. En esta sección, exploraremos varios ataques frente a los sistemas de autenticación distribuidos, como Kerberos. Vamos también discutimos las técnicas particulares que Kerberos emplea para mitigar las amenazas que suponen estos ataques.

### Diccionario y ataques de fuerza bruta

En el protocolo original Kerberos 4, el KDC emite un TGT cifrado a cualquier cliente que lo solicite. Recuerda del [Capítulo 3](https://learning.oreilly.com/library/view/kerberos-the-definitive/0596004036/ch03.html "Chapter 3. Protocols") que este TGT está cifrado con la clave secreta del usuario (derivada de su contraseña). La seguridad de todo el sistema depende de no poder descifrar esto mensaje, ya que si un atacante puede recuperar la clave usada para cifrar el mensaje, ahora tiene la contraseña del usuario y puede Suplantar a ese usuario a voluntad. Por lo tanto, si un atacante desea obtener una contraseña de usuario, puede pedir al KDC un TGT válido para el Nombre de usuario de la víctima. Aunque no hay formas de romper el cifrado métodos usados directamente en los tickets de Kerberos, el atacante puede entonces continúan forzando el descifrado del TGT mediante un ataque _de diccionario fuera de línea_.

Durante un ataque de diccionario, un atacante alimenta una lista de comúnmente contraseñas usadas, o _un diccionario_, para un cracking programar. Para cada entrada del diccionario, un programa intenta Descifra el mensaje usando la contraseña. Si se logra un impacto, el programa Informa al atacante de la contraseña del usuario.

Desde la transformación de la contraseña del usuario a la la clave de cifrado es conocida (la transformación de cadena a clave que se trata en [el Capítulo 3](https://learning.oreilly.com/library/view/kerberos-the-definitive/0596004036/ch03.html "Chapter 3. Protocols")), es trivial para un atacante para crear un programa que pueda traducir contraseñas comunes a Claves de cifrado Kerberos. Luego, el atacante recoge una gran cantidad de TGTs válidos del KDC y continúa el trabajo de descifrar los TGTs fuera de línea; es decir, para cada intento de descifrado, no tiene por qué hacerlo contacta con el KDC. En cambio, una vez que estos TGT sean adquiridos del KDC, No es necesaria ninguna comunicación adicional para atacar las contraseñas.

Este método es posible porque existe un conocido texto plano incluido en el TGT, concretamente la cadena "tgt" en sí. El El nombre principal del Servicio de Concesión de Tickets de Kerberos siempre es "krbtgt," y ese nombre principal es la señal que indica un éxito Descifrado. Para cuando el atacante ha determinado con éxito el la contraseña, el ticket ahora sin cifrar ha expirado; sin embargo, el el atacante ahora tiene una combinación válida de nombre de usuario/contraseña para el Kerberos servidor y pueden obtener nuevos tickets usando ese nombre de usuario válido y contraseña.

Hay código disponible para realizar este ataque contra los KDC de Kerberos 4 mediante un parche del programa descifrador de contraseñas John the Ripper. El código está disponible en la web de Dug Song en [http://www.monkey.org/~dugsong/john-1.6.krb4.patch-3](http://www.monkey.org/~dugsong/john-1.6.krb4.patch-3).

Un ataque de diccionario constituye un límite inferior a la seguridad de cualquier sistema de autenticación basado en contraseña. No importa el tipo de fantasía Se utiliza un esquema de cifrado, si la contraseña del usuario es sencilla, palabra fácil de adivinar, luego sucumbe rápidamente a un diccionario Atacar. Otro ataque, la _fuerza bruta ataque_ , constituye un límite superior para la seguridad de Kerberos. En lugar de intentar descifrar mensajes iterando sobre palabras en un Diccionario predefinido, un ataque de fuerza bruta prueba cada cifrado clave, una a una, hasta encontrar la clave correcta. Los criptosistemas son Diseñado con un gran espacio de teclas para realizar ataques de fuerza bruta poco práctico. Sin embargo, con el ritmo tan acelerado de la tecnología, clave Espacios que antes se consideraban poco prácticos de buscar ahora están dentro de ellos el agarre incluso de un atacante moderadamente motivado.

El cifrado usado en Kerberos v4, así como el tipo de cifrado más común en Kerberos v5, es un solo DES. DES simple, diseñado a finales de los años 70, tiene una longitud de clave de 56 bits. Cuando se diseñó Kerberos (en los últimos años años 80), forzar una clave de 56 bits no era práctico dada la velocidad de la procesadores disponibles. Según los estándares actuales, el espacio de claves de 56 bits de un solo DES se considera relativamente inseguro. En 1998, la Electrónica La Fundación Frontier demostró que con una inversión de 200.000 dólares, un el atacante determinado puede construir un "cracker DES" especializado que puede forzar la clave de cifrado de un mensaje DES en cuestión de días.[[1](https://learning.oreilly.com/library/view/kerberos-the-definitive/0596004036/ch06s02s01.html#ftn.kerberos-CHP-6-FNOTE-1)] Con la potencia de procesamiento disponible hoy en día (en 2002), el el tiempo para descifrar un mensaje cifrado usando un solo DES ha caído en Un par de horas. La demostración más dramática de la La falibilidad del DES se produjo el 19 de enero de 1999, cuando _distributed.net_ descifró una clave DES de 56 bits en el 22 horas,[[2](https://learning.oreilly.com/library/view/kerberos-the-definitive/0596004036/ch06s02s01.html#ftn.kerberos-CHP-6-FNOTE-2)] Utilizando los ciclos libres de miles de ordenadores a nivel mundial y al cracker DES de la EFF en paralelo.

Bits y la fortaleza de los criptosistemas

Al leer sobre criptosistemas de clave simétrica como DES, se mencionan invariablemente un número de "bits" de cifrado. Sin embargo, ¿Qué significa exactamente una "clave de 56 bits"? ¿Cuánto tiempo tardaría en intentarlo? ¿Cada llave? ¿Y qué pasa con una clave de 128 bits?

El número de bits en la clave de un criptosistema representa su clave o el número de claves de cifrado posibles que el Cryptosystem puede manejarlo. DES, por ejemplo, tiene una longitud de clave de 56 bits. Eso significa que hay 256, o 72.057.594.037.927.936 claves posibles. Aunque eso parece un gran una red de ordenadores personales comerciales puede buscar ese espacio clave en tan solo unas semanas. Para más atacante determinado, máquinas especializadas como el cracker DES puede construirse para acelerar el proceso.

Dado que el número de claves crece exponencialmente con el número de bits en la clave, una longitud clave de 57 bits tiene el doble del número de claves que una longitud de clave de 56 bits. Así que, una clave de 128 bits contiene más Claves posibles que hay protones en el universo visible. Forzar esa clave con la tecnología informática actual sería poco práctico, por decir lo menos.

Finalmente, al comparar la fuerza de los criptosistemas, la clave longitud de los criptosistemas de clave simétrica como DES y triple DES no puede compararse directamente con la longitud de la clave asimétrica (o sistemas de clave pública) como RSA. En términos generales, un Un algoritmo de clave pública con una longitud clave de 512 bits es equivalente a una Longitud de clave de 56 bits en un algoritmo de cifrado de clave simétrica.

Por suerte, en Kerberos v5 se introdujeron algunas nuevas funciones del protocolo para mitigar esta amenaza. El primero es el tipo de cifrado extensible soporte, que permite la adición de cifrado más fuerte técnicas a medida que la potencia informática sigue creciendo. Además, Se añadió la preautenticación, que obliga al cliente a demostrar su antes de que el KDC emita tickets cifrados al cliente. La preautenticación limita el problema de una fuerza bruta offline o Ataque al diccionario. En su lugar, un atacante remoto debe contactar con el KDC Cada vez que intenta cambiar la contraseña.

Sin embargo, el nuevo soporte de tipos de cifrado de Kerberos v5 y Las funciones de preautenticación no resuelven completamente el diccionario y Ataques de fuerza bruta. Sin duda, nuevos tipos de cifrado crearán un El ataque de fuerza bruta es menos viable al aumentar la dificultad de forzar un mensaje cifrado por muchos, muchos órdenes de magnitud. Sin embargo, todos los servidores, clientes y KDC de la red deben soportar nuevos tipos de cifrado. Si, por ejemplo, tienes muchos diferentes Implementaciones de cliente y servidor Kerberos instaladas en todo tu red (por ejemplo, un conjunto de servidores Kerberos del MIT junto con algunos clientes Windows), solo puedes usar un tipo de cifrado común compatible por todas las máquinas de tu red. MIT soporta teclas triples DES, pero Windows no lo hace, por lo que las comunicaciones entre Windows y MIT Las implementaciones de Kerberos estarán limitadas a un solo DES. Los próximos La versión 1.3 de la distribución Kerberos 5 del MIT soportará el RC4 cifrado utilizado por Windows, y por tanto refuerzan el cifrado utilizado para comunicaciones entre ambas implementaciones.

Con la preautenticación en vigor, un atacante ya no puede obtener tickets válidos y cifrados a petición del KDC. Sin embargo, el el atacante puede usar en su lugar un "detector" de red para obtener respuestas KDC tal como son enviados por cable a los clientes. Estas respuestas incluirán tickets Cifrado con las claves del cliente. Mientras el ataque ha aumentado en Dificultad por un orden de magnitud, sigue siendo un problema potencial. Además, la mayoría de las implementaciones de Kerberos (notablemente el MIT) no lo hacen obliga a los clientes a usar pre-autenticación por defecto, anulando la beneficio de seguridad que proporcionaría la preautenticación.

### Ataques de repetición

Otro ataque que se puede montar contra Kerberos es conocido como _ataque de repetición_. Ya que Todos los intercambios de protocolos son simplemente mensajes electrónicos que se envían A través de una red informática, un atacante puede escuchar la red los mensajes implicados en un intercambio de autenticación exitoso, haz una copia de los mensajes, y los reproducía más adelante. El atacante no Es necesario adivinar la contraseña de los usuarios o descifrar cualquier mensaje en este escenario. Ya que el ataque de repetición requiere acceso para escuchar todos así como la capacidad de enviar mensajes falsos, una Un ataque de repetición es un ataque _activo_. Un ataque de repetición teórica se muestra en [la Figura 6-1](https://learning.oreilly.com/library/view/kerberos-the-definitive/0596004036/ch06s02s02.html#kerberos-CHP-6-FIG-1 "Figure 6-1. Kerberos replay attack").

Figura 6-1. Ataque de repetición de Kerberos

En esta figura, vemos que Alice (la inocente usuaria final) Obtiene con éxito los tickets para autenticarse en su servidor de correo. Bob, El malvado hacker escucha disimuladamente todo el tráfico de red entre Alice, el servidor de correo, y el KDC de Kerberos. Bob no puede usar directamente el TGT que Alicia solicita en el primer paso, ya que el TGT debe descifrarse con la contraseña de Alice, que Bob no conoce (aunque ciertamente puede intentar forzar la contraseña, ya que discutido en la sección anterior). Sin embargo, cuando Alice la envía Ticket y autenticador cifrados, Bob puede interceptar ese mensaje y _reproducirlo_ para hacerse pasar por Alice y El servidor de correo.

El ticket está cifrado con la clave del servidor de correo, y el el autenticador está cifrado con la clave de sesión compartida entre Alice y el servidor de correo. Cuando el servidor de correo recibe el ticket y autenticador, descifra el ticket con su clave, recupera el clave de sesión del ticket, y utiliza la clave de sesión para descifrar el autenticador. Si todas las descifraciones tienen éxito, entonces la autenticación lo consigue.

Kerberos cuenta con varias protecciones integradas para evitar que tenga éxito Repetir los ataques. Como administrador, no tienes que preocuparte por eso habilitando cualquiera de estas protecciones; Están integrados en el particular Implementación de Kerberos que estás usando. Estas protecciones Son:

Campo de dirección en los tickets

Cuando un cliente solicita un ticket al KDC, este muestra el direcciones de red desde las que el ticket es válido. Por ejemplo, si la dirección IP de la estación de trabajo es 192.168.1.1, el Workstation llenaría esa dirección en el campo de dirección en el solicitud de ticket, y el KDC copiaría eso en el ticket vuelve a la estación de trabajo. Esta protección resuelve el problema de un atacante que intenta reproducir un ticket válido en un Estación de trabajo no aparece en el campo de dirección del ticket. Sin embargo, Esta protección no es suficiente para frustrar completamente la repetición ataques; el campo de dirección puede quedar en blanco, y el ticket sería válido para todas las direcciones. O, si el atacante tenía acceso a una máquina listada en el campo de direcciones, podía iniciar sesión y Vuelve a jugar el ticket desde ahí.

Autenticadores basados en tiempo

Dado que la seguridad basada en direcciones es imperfecta, Kerberos emplea otro plan para frustrar los ataques de repetición. Cada vez que un el cliente desea utilizar un servicio kerberizado, ella genera un autenticador, que se envía junto con el ticket al servicio Para autenticación. El autenticador no contiene nada más que un Marca de tiempo, cifrada con la clave de sesión generada por el KDC para este intercambio de billetes en particular. Cuando el servicio recibe Este autenticador comprueba la marca temporal descifrada contra su reloj del sistema. Si los dos tiempos difieren en más de cinco en cualquier dirección, el servicio rechazará el ticket y se niegan a autenticar al usuario. El periodo de 5 minutos es diseñado para permitir cierta variación entre diferentes relojes en La cadena. Sin embargo, incluso cinco minutos pueden ser más que suficientes Es hora de que un atacante repita los tickets válidos, especialmente si emplea un programa automatizado para capturar y reproducir Entradas.

Cachés de repeticiones

La última línea de defensa que tiene Kerberos contra la repetición Attacks es la caché de repeticiones. Tanto el Kerberos v4 como el v5 Los protocolos incluyen el autenticador basado en tiempo. Kerberos v5 introduce la caché de repetición para evitar que los atacantes reutilicen tickets en el corto periodo de tiempo en que los autenticadores son válidos. Cada El servicio kerberizado mantiene una caché de los autenticadores que realiza ha recibido recientemente. Cuando el servicio recibe un autenticador, revisa la caché de repeticiones. Si el servicio encuentra una copia del autenticador ya en la caché de repeticiones, rechaza la petición. De lo contrario, el servicio acepta la solicitud y añade el autenticador a la caché de reproducción para validar Más peticiones.

### Ataques del hombre en medio

Por último, un _hombre intermedio El ataque_ afecta a casi cualquier protocolo que intente verificar el Identidad de los extremos de conexión (en este caso, un usuario y la máquina desean alcanzar). Un ataque man-in-the-middle es un ataque _activo_, lo que significa que el atacante debe ser capaz de leer todos mensajes en la red, así como enviar mensajes arbitrarios suyos diseño propio.

El objetivo del ataque man-in-the-middle es suplantar al lo que hace que el usuario piense que se ha conectado al servidor legítimo, cuando en realidad está hablando con el atacante. Una vez El atacante tiene el control de la sesión, puede actuar como un simple Paso (pasando mensajes entre el usuario y el legítimo sin modificación), o puede inyectar activamente, modificar o Elimina los mensajes entre el usuario y el servidor. El atacante ahora es parte de la conversación entre el usuario y el servidor legítimo, y puede modificar cualquier mensaje que pase por ella, de ahí el nombre "Hombre del medio."

La buena noticia es que el protocolo Kerberos incluye protección incorporada contra Ataques de hombre en medio. Dado que Kerberos realiza mutuo autenticación, confirmando no solo la identidad del usuario final sino También la identidad del servidor, los ataques de hombre en el medio son frustrado.

Para prevenir ataques de hombre en medio, existe algún mecanismo para validar que la clave de cifrado del servidor debe existir. Uso de otros protocolos verificación manual (como Secure Shell), donde la "huella digital" de La clave pública del servidor se imprime en pantalla cuando el usuario se presenta por primera vez se conecta), o autoridades firmantes (en el caso de la web habilitada con SSL sitios). Kerberos utiliza el hecho de que hay una copia de todas las claves para ambos los servicios y usuarios se almacenan en el KDC para garantizar la protección contra Ataques de hombre en medio. Dado que la clave de sesión generada por el KDC y luego se envía al servicio se cifra con la clave del servicio, un El atacante no puede recuperar la clave de sesión sin el secreto del servicio clave.

Un cliente puede entonces detectar si el servidor con el que está hablando es genuino solicitando _mutuo autenticación,_ donde el servidor debe demostrar su identidad mediante recuperar la clave de sesión, cifrar una respuesta y enviarla de vuelta al cliente. Si el servidor no es genuino y no tiene copia de la clave de servicio, entonces el servidor no puede devolver una cifrada válida y el cliente se desconecta.

Mientras que Kerberos proporciona la capacidad de realizar mutuos autenticación, las aplicaciones deben tener código para habilitar esa protección. Además, existen varias aplicaciones, como los módulos PAM para la autenticación contra contraseñas de Kerberos, no use la Proceso de autenticación basado en tickets. En su lugar, introducen una contraseña a través de la red (esperemos que cifrado) y lo verifiquen en el servidor pidiendo al KDC un TGT y luego descifrando el TGT. Esto es donde se puede montar un ataque práctico de hombre en el medio Kerberos.

En este caso, el atacante quiere colocarse entre los servidor y el KDC, para que pueda suplantar el servidor de aplicaciones en pensando que ella es la verdadera KDC. Dado que las solicitudes y respuestas del KDC son simples mensajes UDP, es fácil para un atacante enviar mensajes falsos mensajes que supuestamente provienen de la dirección IP real del KDC. Así, el El ataque se lleva a cabo mediante el siguiente procedimiento:

1. El atacante elige una contraseña para usar en la cuenta que ella desea acceder a.
    
2. El atacante entonces configura un programa para escuchar la red para ver cuándo los clientes solicitan un TGT para el usuario objetivo. Cuando llega un TGT, el programa envía una respuesta TGT de vuelta a la solicitante cifrado con la contraseña elegida.
    
3. Luego, el atacante inicia sesión en el servidor y da el objetivo Nombre de usuario y la contraseña elegida. En ese momento, el programa se envía el servidor el TGT cifrado con la contraseña que el atacante ha elegido en lugar de la contraseña real.
    
4. Si el servidor recibe primero la respuesta falsa, lo hará descifrar con éxito el TGT ya que las contraseñas coinciden.
    

Para evitar este ataque, el servidor debe recuperar a su host clave de servicio desde su keytab, y luego solicitar una clave de servicio a la KDC usando el TGT que acaba de obtener en nombre del usuario. Ya que solo el servidor y el KDC conocen la clave de servicio anfitrión, un atacante externo No puede producir un mensaje falso y la cuenta se ve denegada el acceso.

El programa KDC spoof es una explotación práctica de esto vulnerabilidad, y está disponible desde [http://www.monkey.org/~dugsong/kdcspoof.tar.gz](http://www.monkey.org/~dugsong/kdcspoof.tar.gz).

### Aplicación de contraseñas seguras

La seguridad de toda tu red depende de tus usuarios Elegir contraseñas seguras. Sin embargo, la experiencia muestra que la mayoría de los usuarios Elige contraseñas bastante pobres. Este experimento se realizó con ciclos de CPU de repuesto disponibles en sistemas fácilmente disponibles en 1998. Un atacante decidido con más Los recursos disponibles lo tendrían aún más fácil. Un relacionado En 2002 se realizó un experimento para determinar la viabilidad de la contraseña ataques contra la implementación de Kerberos de Windows 2000, con ataques similares resultados.[[4](https://learning.oreilly.com/library/view/kerberos-the-definitive/0596004036/ch06s03s02.html#ftn.kerberos-CHP-6-FNOTE-4)]

Claramente, estos descubrimientos demostraron a los investigadores que era un se desvía decir que los ataques de fuerza bruta estaban fuera del alcance de la sistema de autenticación en la especificación original de Kerberos. La preautenticación, como se ha comentado antes, es una solución que evita el ataque de fuerza bruta más grave, pero otro paso importante tomar es hacer cumplir la calidad de las contraseñas de los usuarios.

Siempre que los usuarios pueden elegir sus propias contraseñas, existe la posibilidad que encontrarán la manera de elegir una contraseña insegura, pero Imponer algunas heurísticas simples en las contraseñas que los usuarios eligen da la Un administrador tiene alguna garantía de que las contraseñas no serán demasiado simples. #### MIT

El KDC del MIT puede evaluar las contraseñas proporcionadas por los usuarios basándose en Dos métricas: el número de _caracteres Clases_ que contiene y su duración. La longitud de una contraseña es obvio, pero ¿qué es una clase de personaje? El MIT KDC define cinco Diferentes clases de personajes:

- Letras minúsculas
    
- Letras mayúsculas
    
- Números
    
- Puntuación
    
- Otros personajes

Si El número mínimo de clases de caracteres es tres, luego la contraseña es válido siempre que haya al menos un personaje de cada clase en la contraseña.

### Hacer cumplir la vida útil e historial de contraseñas

## Protegiendo tu KDC

Dado que el KDC contiene las claves secretas de cifrado para todos de los usuarios así como de todos los servicios de tu administración Obviamente, es muy importante que el KDC esté bien protegido. Es es tanto una ventaja como una desventaja de Kerberos que todas son clave la información está centralizada; Por un lado, es más fácil de asegurar con fuerza una máquina que intentar asegurar fuertemente muchas máquinas distribuidas, pero por otro lado, un compromiso de la máquina KDC compromete todo Información de autenticación en el reino.

Por lo tanto, las máquinas que ejecutan software KDC deberían ser especialmente preparado y dedicado exclusivamente a este propósito. Durante el la instalación del sistema operativo, la máquina debe estar físicamente separada o Protegida desde el cortafuegos de la red para evitar la exposición al exterior. La máquina es más vulnerable a ataques externos durante la instalación del sistema operativo y del software KDC, ya que las salvaguardas Proteger la máquina aún no está configurado. Por ejemplo, automatizado gusanos como Code Red han explotado los Windows sin parchear en ejecución IIS en menos de 10 minutos de exposición al exterior.

No se debe instalar ningún otro software servidor en el KDC, especialmente los servidores con alta visibilidad pública como el correo, la web, y servidores de bases de datos. El inicio de sesión remoto, si es necesario, debería limitarse a un Un subconjunto muy pequeño de usuarios administrativos que tienen contraseñas locales separados de sus contraseñas de Kerberos. Contraseñas para el administrador o la cuenta raíz en las máquinas KDC debe estar estrictamente controlada y se cambiaba periódicamente para evitar comprometimientos.

Por último, la seguridad física de las máquinas KDC es fundamental. El acceso físico a cualquier máquina da implícitamente un atacante Acceso a nivel de administrador a esa máquina. Dado que el KDC contiene a todos de las llaves secretas de tu reino de Kerberos, el acceso físico al KDC sí Compromete todas esas llaves. Por lo tanto, los KDC deberían estar ubicados en un Habitación cerrada con acceso limitado, preferiblemente con algún tipo de entrada o salida Tala. Y recuerda cerrar sesión siempre de la consola del KDC después realizando cualquier tarea administrativa necesaria.

### Protección de un KDC Unix

### Kerberos y NAT

El siguiente escenario de cortafuegos a considerar se muestra en [la Figura 6-5](https://learning.oreilly.com/library/view/kerberos-the-definitive/0596004036/ch06s05s02.html#kerberos-CHP-6-FIG-5 "Figure 6-5. KDCs and application servers behind firewall, with clients using NAT"). En esto todos los KDC y servidores de aplicaciones están detrás de un cortafuegos corporativos, con direcciones IP públicamente accesibles y enrutables. Los clientes están ubicados fuera del cortafuegos corporativo pero viven en espacio de direcciones IP privadas detrás de un pequeño cortafuegos NAT.


![[../../assets/Pasted image 20260522050528.png]]
Figura 6-5. KDC y servidores de aplicaciones detrás del cortafuegos, con clientes usando NAT

La Traducción de Direcciones de Red, o NAT, permite múltiples máquinas para compartir una sola dirección IP. En una configuración NAT, los clientes dentro de la Los dispositivos NAT tienen direcciones IP privadas y no enrutables, según lo definido en el RFC 1918. Estas direcciones IP, aunque válidas, no son accesibles directamente a Internet en general. El dispositivo NAT se encarga de las solicitudes de retransmisión entre las máquinas internas y el Internet más grande. NAT presenta un problema a Kerberos ya que las solicitudes de tickets contienen la IP del solicitante Dirección. Porque los clientes que solicitan tickets en este caso están usando NAT, la dirección IP que proporcionan al KDC no será enrutable. Ya que la dirección privada del ticket no coincide con la dirección pública de el dispositivo NAT, los servicios kerberizados no aceptarán ninguna entrada emitida para clientes NAT.

Por ejemplo, tienes un usuario en un módem de cable con un pequeño NAT dispositivo. La dirección IP pública del dispositivo NAT es 132.68.153.28, y la red interna es el rango RFC 1918 de 192.168.1.0 a 192.168.1.255. Un cliente en 192.168.1.2 solicita un TGT a la Kerberos KDC dentro del cortafuegos corporativo. Un TGT, válido solo para la dirección IP 192.168.1.2 se devuelve al cliente.

El cambio TGT funciona bien, pero la única dirección válida que aparece en el TGT devuelto aparece la dirección NAT interna del cliente. En cuanto cuando el cliente intenta obtener un ticket de servicio usando este TGT, el La solicitud fracasará. Ya que la dirección que aparece en el ticket no la tiene si coincide con la dirección pública del dispositivo NAT, se devuelve un error de "dirección de red incorrecta" al y el intento de autenticación fallará.

Hay dos enfoques para resolver este problema. O bien todo cliente en la red NAT puede configurarse para solicitar tickets con la dirección IP de la interfaz externa en el dispositivo NAT, o en los clientes puede configurarse para solicitar tickets "sin dirección", es decir, tickets que pueden ser utilizados desde cualquier dirección IP.

Para clientes del MIT y Heimdal, utiliza la opción de solicitar tickets sin dirección. Otra solución, más general, si usas clientes del MIT es añadir La siguiente línea a la sección de tu archivo _/etc/krb5.conf_:`-A``kinit``[libdefaults]`

```
noaddresses = true
```

Esta línea es reconocida por todas las aplicaciones que utilizan el MIT Kerberos 5 librerías y hará que las solicitudes soliciten tickets sin direcciones.

Uso de tickets sin dirección para apoyar a clientes detrás de dispositivos NAT presenta poca degradación en la seguridad. La única vulnerabilidad que Presenta que si un atacante pudiera obtener una copia de tu Caché de credenciales, podría usar tus tickets independientemente de su fuente Dirección IP. También facilita un poco los ataques de repetición, pero como discutido en la sección anterior, [Sección 6.2.2](https://learning.oreilly.com/library/view/kerberos-the-definitive/0596004036/ch06s02s02.html "Replay Attacks"), Kerberos incluye otras salvaguardas contra ataques de repetición.

To enable logging in the MIT KDC, the _krb5.conf_ file can contain a stanza with several variables that control where the logging output goes. Here are the variables:`[logging]`

- `kdc`

	The variable controls where the log for the KDC’s authentication service and Ticket Granting Service is sent. The logs produced in the file specified in the KDC variable contain all of the transactions between users, servers, and the KDC.`kdc`

- `admin_server`

	The variable controls where the logs for the server are sent. The logs produced in the file specified in the variable contain all of the transactions between Kerberos administrators and the KDC that are performed through the interface.`admin_server``kadmin``admin_server``kadmin`

Each option can take several different arguments, depending on the type of file, device, or syslog facility you wish the logs to be sent to. If you want logs sent to several destinations, you can list them, one at a time, on separate lines.

- `FILE=` _`filename`_  
- `FILE`:_`filename`_

	These options send the specified logs to a file called _`filename`_. In the first form with a “=”, the file is overwritten each time the KDC starts. The second form, specified with a “:”, indicates that the file will be appended to each time the KDC starts.

- `STDERR`

	This option specifies that the logs should be sent to the standard error output of the KDC.

- `CONSOLE`

	This option specifies that the logs be sent to the console of the KDC machine.

- `DEVICE=` _`devicename`_

	This option specifies that the logs be sent to the _`devicename`_. This can be used to send logs to a particular terminal, or printer.

- `SYSLOG`:_`severity`_:_`facility`_

	This option specifies that the logs be sent to the syslog service on the KDC. The severity and facility arguments are optional, and can be used in combination with _syslog.conf_ to send KDC output to its own file, or relay to another syslog server. The available severities and facilities vary by operating system vendor, but the syslog manpage will list the options available for your OS. By default, the severity is ERR and the facility is AUTH.

Let’s take a look at an example:

```toml
[logging]
 kdc = FILE:/var/log/kdc.log
 kdc = SYSLOG:NOTICE
 admin_server = FILE:/var/log/kadmin.log
 admin_server = CONSOLE
```

In this example, all of the KDC activity (authentication service and ticket granting service) are logged to a file named _/var/log/kdc.log_, to which something is appended to every time the KDC restarts. In addition, KDC activity is logged to syslog, under the AUTH facility and the NOTICE severity. All requests and responses are logged to _/var/log/kadmin.log_ as well as the system console.`kadmin`


#### Heimdal

The controls for the Heimdal KDC logging facility are located in the _krb5.conf_ file. The options are similar to the MIT KDC logging options, but have a few important additions. Just like the MIT KDC, all of these options are contained in a `[logging]` stanza in the configuration file.

Each variable in the logging section of the Heimdal _krb5.conf_ configuration file is named after the program that is generating the logs. That is, the logs from the kdc program are sent to the destination specified by the `kdc` variable. Similarly, logs from the kadmind program are sent to the destination specified by the `kadmind` variable, and so on. In addition, a “default” variable is provided as a catchall for messages that do not have a more specific destination specified. The destination specifications are as follows:

- `FILE=` _`filename`_  
- `FILE`:_`filename`_

	These options send the specified logs to a file called _`filename`_. In the first form with a “=”, the file is overwritten each time the KDC starts. The second form, specified with a “:”, indicates that the file will be appended to each time the KDC starts.

- `STDERR`

	This option specifies that the logs should be sent to the standard error output of the KDC.

- `CONSOLE`

	This option specifies that the logs be sent to the console of the KDC machine.

- `DEVICE=` _`devicename`_

	This option specifies that the logs be sent to the _`devicename`_. This can be used to send logs to a particular terminal, or printer.

- `SYSLOG`:_`severity`_:_`facility`_

	This option specifies that the logs be sent to the syslog service on the KDC. The severity and facility arguments are optional, and can be used in combination with _syslog.conf_ to send KDC output to its own file, or relay to another syslog server. The available severity and facility arguments are system-dependent By default, the severity is ERR and the facility is AUTH.

In addition, each destination may be preceded by an optional logging level. Logging levels are integers, numbered from zero upwards; zero is the minimum of detail. To specify a logging level, prefix a destination with the range of logging levels (for example, 1-5) followed by a slash. If only one logging level is given, then only messages sent to that level will be logged to the destination.

Here is an example:

```toml
[logging]
 kdc = 0/FILE:/var/log/kdc.log
 kdc = 1-/SYSLOG:DEBUG
 kadmind = FILE:/var/log/kadmin.log
 kpasswdd = FILE:/var/log/kpasswdd.log
 default = FILE:/var/log/kerberos.log
```

In this example, KDC logs with a logging level of zero are sent to _/var/log/kdc.log_, while messages with a higher logging level are sent to syslog, facility AUTH, severity DEBUG. Messages sent from `kadmind` are stored in the _/var/log/kadmin.log_ file and `kpasswdd` logs are sent to _/var/log/kpasswdd.log_. All other messages from applications using Heimdal Kerberos are sent to _/var/log/kerberos.log_. In all cases, the log file is appended to when the respective programs restart.

#### Windows domain controllers

Windows 2000 domain controllers do not log any authentication requests by default. Windows Server 2003 is somewhat better in this regard since it logs successful authentication requests by default, but it does not log any denied requests. Thankfully, Microsoft provides very detailed logging facilities that can be enabled. A Windows domain controller can log the Kerberos KDC activity as well as domain logon and logoff events. We’ll take a look at both, from a Kerberos perspective.

First, let’s enable the logging of authentication requests for your domain. The first thing to configure is the Security Log’s maximum log file size. On Windows 2000, machines in your domain will only keep a 512 KB rotating log file by default (overwriting events that are more than 7 days old). With today’s large hard drives, there is no reason to constrain log files to less than a megabyte, so we’ll increase the file size limit to 10 megabytes in this example.

To change the maximum log file size for the security log, follow these steps:

1. Log into a Windows machine that has the Active Directory administrative snap-ins installed. You must have Domain Administrator privileges in order to modify these settings.
    
2. Open MMC and load the Active Directory Users and Computers snap-in.
    
3. Right-click on your domain, and choose Properties.
    
4. Select the Group Policy tab.
    
5. Select the Default Domain Policy GPO, and click Edit.
    
6. Navigate to Computer Configuration → Windows Settings → Security Settings → Event Log → Settings for Event Log.
    

You will now see the window shown in [Figure 6-6](https://learning.oreilly.com/library/view/kerberos-the-definitive/0596004036/ch06s06s01s03.html#kerberos-CHP-6-FIG-6 "Figure 6-6. Active Directory Group Policy event log settings").


![[../../assets/Pasted image 20260522050821.png]]
Figure 6-6. Active Directory Group Policy event log settings

By double-clicking on Maximum security log size, you’ll be presented with a dialog box. Click “Define this policy setting” and set a maximum size (in this case, 10240 Kbytes). If you would like to change the log retention options, you can change the “Retain security log” and “Retention method for security log” settings in this window.

Next we’ll enable auditing for our domain. There are two different auditing options included in Windows, rather obscurely named “logon auditing” and “account logon auditing.” They both audit authentication requests, however, they audit different parts of the login process, and store the information on different hosts. Confused yet? Let’s take a look at the two choices:

Logon Auditing

This setting toggles the auditing of local Windows login events. These login events are not constrained to Kerberos-based logins; logon auditing will record login events for every type of authentication that Windows supports, such as NTLM. This type of logging is similar to a Secure Shell (or other application-level) log on a Unix box; it records the start and finish of a user’s login session. Therefore, logon auditing occurs on the individual servers that users log in to, and the corresponding audit logs only appear in that server’s Event Log.

Account Logon Auditing

This setting enables auditing similar to the other KDC’s we have mentioned here. Every time a Kerberos ticket is granted, either through the Authentication Service or the Ticket Granting Service, the domain controller writes the details about that ticket to its Security Log when this setting is enabled. Since there is no concept of a “login session” in Kerberos, there is no way to determine when a user “logs out,” and consequently the duration of users’ login sessions, with this option alone. However, this option does provide for a nice centralized log of all Kerberos-based authentication requests, since the account logon audit records are written to the domain controllers’ event logs, instead of the individual servers’ event logs.

Okay, now that we’ve cleared that up, let’s continue on to enable these audit policies on your domain. We’re going to start at the same Group Policy window that we opened in the previous exercise.

From the Group Policy window, navigate to Computer Configuration, Windows Settings, Security Settings, Local Policies, Audit Policy. You’ll see a window similar to the one shown in [Figure 6-7](https://learning.oreilly.com/library/view/kerberos-the-definitive/0596004036/ch06s06s01s03.html#kerberos-CHP-6-FIG-7 "Figure 6-7. Active Directory Group Policy audit policy settings").

From this window, you can configure both the “Audit logon events” and “Audit account logon events.” It is recommended that both successful and failed attempts should be logged for these events.

### Understanding the Logs

Now that you’ve set up the auditing mechanism on your Kerberos KDC and your KDC is busy logging all of its activity, you need to periodically review these logs for suspicious activity. Enabling the logging activity on your KDC is useless unless the logs are actually analyzed at some point, either automatically by a script that has preset thresholds for suspicious activity, or by hand. In this section, we’ll examine the log messages emitted by each Kerberos implementation covered in this book, and describe what each message means.

Each implementation has a dramatically different log format, but since there are only a few protocol exchanges in Kerberos, the number of different log messages is relatively low. Each log message can be directly connected to an exchange between the KDC and a Kerberos client.

#### MIT

Each time the MIT KDC starts up, it logs the interfaces and ports on which it is listening to the defined KDC log file:

```bash
Jul 31 03:04:40 www.wedgie.org krb5kdc[10543](info): setting up network...
Jul 31 03:04:40 www.wedgie.org krb5kdc[10543](info): listening on fd 7: 192.168.1.83 
port 88
Jul 31 03:04:40 www.wedgie.org krb5kdc[10543](info): listening on fd 8: 192.168.1.83 
port 750
Jul 31 03:04:40 www.wedgie.org krb5kdc[10543](info): set up 2 sockets
Jul 31 03:04:40 www.wedgie.org krb5kdc[10544](info): commencing operation
```

In this case, the KDC is listening on both the Kerberos 5 and Kerberos 4 well-defined ports. Similarly, every time the KDC is shut down cleanly, it logs this fact to the log file as well:

```bash
Jul 31 15:11:57 www1.wedgie.org krb5kdc[779](info): shutting down
```

Now, let’s take a look at what is logged during Kerberos protocol exchanges. First, let’s take an example user using Kerberos 5, who is obtaining a TGT when he starts his day. The following message is recorded in the log:

```
Jul 30 23:18:26 www1.wedgie.org krb5kdc[10544](info): AS_REQ (3 etypes {16 3 1}) 192.
168.1.83(88): ISSUE: authtime 1028085506, etypes {rep=16 tkt=16 ses=16}, 
jgarman@WEDGIE.ORG for krbtgt/WEDGIE.ORG@WEDGIE.ORG
```

Let’s examine this output piecemeal. First, we have the date, time, and hostname of the KDC. This information appears whether the log is being sent to a file or via syslog. Next, we have the name and process ID of the KDC, as well as the severity of the message (in this case “info”).

The next part of this message describes the request that was made to the KDC. It begins with the type of request (AS_REQ, for an Authentication Service request). Then, it follows by listing the encryption types that the client claims to support. In this case, the client listed three encryption types that it understands. Each encryption type is specified by its numeric identifier. A complete listing of currently defined encryption types and their numeric identifiers can be found in the Kerberos Encryption Specifications document, which is on the Kerberos Clarifications site at [http://www.kerberos.isi.edu](http://www.kerberos.isi.edu/). In this particular example, the encryption types supported by the client are DES-CBC-CRC (1), DES-CBC-MD5 (3), and DES3-HMAC-SHA1 (16). Next, we see the requesting IP address, followed by the port on the KDC that the request arrived on.

The next section of this message indicates the KDC’s response to the request. In this example, the KDC issued (ISSUE) a ticket valid beginning at authtime (indicated by the standard Unix time_t value, seconds past January 1, 1970). This ticket’s encryption types for the reply, the ticket itself, and the session key, are all DES3-HMAC-SHA1. Finally, we see the principal that requested the ticket (_jgarman@WEDGIE.ORG_) and the service for which the ticket was issued (_krbtgt/WEDGIE.ORG@WEDGIE.ORG_, since the user requested a TGT).

If the realm requires pre-authentication for this user, the KDC first logs a NEEDED_PREAUTH instead of an ISSUE response, then, upon successful pre-authentication, logs the ISSUE response, as in the following example:

```
Aug 01 09:29:09 www1.wedgie.org krb5kdc[17734](info): AS_REQ (3 etypes {16 3 1}) 192.
168.1.6(88): NEEDED_PREAUTH: afsadmin@WEDGIE.ORG for krbtgt/WEDGIE.ORG@WEDGIE.ORG, 
Additional pre-authentication required
Aug 01 09:29:11 www1.wedgie.org krb5kdc[17734](info): AS_REQ (3 etypes {16 3 1}) 192.
168.1.6(88): ISSUE: authtime 1028208551, etypes {rep=16 tkt=16 ses=16}, 
afsadmin@WEDGIE.ORG for krbtgt/WEDGIE.ORG@WEDGIE.ORG
```

Now, once the user has their TGT, he wishes to connect to a remote server, and so requests a service ticket:

```
Aug 02 10:35:37 www1.wedgie.org krb5kdc[17734](info): TGS_REQ (3 etypes {16 3 1}) 
192.168.1.83(88): ISSUE: authtime 1028298937, etypes {rep=16 tkt=16 ses=16}, 
jgarman@WEDGIE.ORG for host/www1.wedgie.org@WEDGIE.ORG
```

This message is very similar to the message emitted when requesting a TGT. The only difference between the two messages is that this message is of type TGS_REQ (Ticket Granting Server request) rather than AS_REQ. All of the rest of the fields represent the same data as they did for the AS_REQ.

Now, let’s take a look at the messages that turn up in the log when things start going wrong. First, we’ll take a user who doesn’t exist in the Kerberos principal database. When he tries to `kinit`, the following message is logged:

```
Aug 02 12:07:19 www1.wedgie.org krb5kdc[17734](info): AS_REQ (3 etypes {16 3 1}) 192.
168.1.83(88): CLIENT_NOT_FOUND: root@WEDGIE.ORG for krbtgt/WEDGIE.ORG@WEDGIE.ORG, 
Client not found in Kerberos database
```

Here, we see an AS_REQ message with a response of CLIENT_NOT_FOUND. A similar message is emitted when a valid user attempts to obtain a ticket for a service that does not exist in the KDC database:
```
Aug 02 13:43:28 www1.wedgie.org krb5kdc[17734](info): TGS_REQ (1 etypes {1}) 192.168.
1.83(88): UNKNOWN_SERVER: authtime 1028298840,  jgarman@WEDGIE.ORG for afs/net.
wedgie.org@WEDGIE.ORG, Server not found in Kerberos database
```

#### Heimdal

Each time the Heimdal KDC starts up, it outputs the network ports it listens on to the KDC log file:

```
2002-08-04T14:44:51 listening on IPv4:127.0.0.1 port 88/udp
2002-08-04T14:44:51 listening on IPv4:192.168.1.83 port 88/udp
2002-08-04T14:44:51 listening on IPv4:127.0.0.1 port 88/tcp
2002-08-04T14:44:51 listening on IPv4:192.168.1.83 port 88/tcp
2002-08-04T14:44:51 listening on IPv4:127.0.0.1 port 750/udp
2002-08-04T14:44:51 listening on IPv4:192.168.1.83 port 750/udp
2002-08-04T14:44:51 listening on IPv4:127.0.0.1 port 750/tcp
2002-08-04T14:44:51 listening on IPv4:192.168.1.83 port 750/tcp
2002-08-04T14:44:51 listening on IPv4:127.0.0.1 port 4444/udp
2002-08-04T14:44:51 listening on IPv4:192.168.1.83 port 4444/udp
2002-08-04T14:44:51 listening on IPv4:127.0.0.1 port 4444/tcp
2002-08-04T14:44:51 listening on IPv4:192.168.1.83 port 4444/tcp
```

By default, the Heimdal KDC acts as a Kerberos 5 KDC, Kerberos 4 KDC, and a Kerberos 5-4 ticket translator. Now let’s continue with an example protocol exchange in which a client requests a TGT:

```
2002-08-04T15:40:09 AS-REQ jgarman@WEDGIE.ORG from IPv4:192.168.1.83 for krbtgt/
WEDGIE.ORG@WEDGIE.ORG
2002-08-04T15:40:09 Using des3-cbc-sha1/des3-cbc-sha1
2002-08-04T15:40:09 sending 606 bytes to IPv4:192.168.1.83
```

All of the Heimdal messages begin with a date, followed by the T delimiter and the time. The first message indicates that the KDC received an Authentication Service request (AS-REQ) for the principal _jgarman@WEDGIE.ORG_. Next, it lists the originating IP and the service ticket the client requests.

The next message indicates the encryption types that the KDC will use in responding to the request: in this case, triple DES. Finally, if the KDC accepts the request, it emits the last message indicating the size of the response and the IP address of the client.

If the KDC requires pre-authentication, the following messages will be sent to the log upon successful client authentication:

```
2002-08-04T17:02:09 AS-REQ jgarman@WEDGIE.ORG from IPv4:192.168.1.83 for krbtgt/
WEDGIE.ORG@WEDGIE.ORG
2002-08-04T17:02:09 No PA-ENC-TIMESTAMP -- jgarman@WEDGIE.ORG
2002-08-04T17:02:09 sending 282 bytes to IPv4:192.168.1.83
2002-08-04T17:02:09 AS-REQ jgarman@WEDGIE.ORG from IPv4:192.168.1.83 for krbtgt/
WEDGIE.ORG@WEDGIE.ORG
2002-08-04T17:02:09 Looking for pa-data -- jgarman@WEDGIE.ORG
2002-08-04T17:02:09 Pre-authentication succeded -- jgarman@WEDGIE.ORG
2002-08-04T17:02:09 Using des3-cbc-sha1/des3-cbc-sha1
2002-08-04T17:02:09 sending 624 bytes to IPv4:192.168.1.83
```

The first three messages indicate the original request, and the error response sent back by the KDC to the client requesting pre-authentication. The final five lines are similar to the non-pre-authentication case, with the addition of the `pa-data` and pre-authentication succeded messages. Requesting a service ticket generates similar output:

```
2002-08-04T17:17:42 TGS-REQ jgarman@WEDGIE.ORG from IPv4:192.168.1.83 for
afs@WEDGIE.ORG [forwardable]
2002-08-04T17:17:42 sending 527 bytes to IPv4:192.168.1.83
```

Note that the ticket options that the client requested are listed on the TGS-REQ line.

#### Windows domain controllers

As we discussed earlier, the log files for the two different audit options (logon auditing and account logon auditing) are stored on different machines’ Event Logs. The account logon auditing produces audit logs that are similar to the other KDC implementations we’ve covered. Since the account logon auditing is generated by the Kerberos KDC service running on the domain controllers, we’re going to examine what those logs look like.

There are several Kerberos-related log events that account logon auditing emits. They are listed below:

- 672 Authentication Ticket Granted
    
- 673 Service Ticket Granted
    
- 674 Ticket Granted Renewed
    
- 675 Pre-authentication Failed
    
- 676 Authentication Ticket Request Failed
    
- 677 Service Ticket Request Failed
    

Any Kerberos client looks the same from the perspective of account logon auditing. It doesn’t matter whether the requesting machine is running Windows or Unix; as long as it contacts the KDC running on one of your domain controllers, the KDC service will log both the successful and failed attempts at requesting tickets. So, let’s dive in and examine some sample event logs.

Here’s an example of a Windows machine successfully authenticating a user “jgarman” in the WEDGIE.ORG realm:

```
Event Type: Success Audit
Event Source: Security
Event Category: Account Logon 
Event ID: 672
Date:  10/1/2002
Time:  11:55:10 PM
User:  NT AUTHORITY\SYSTEM
Computer: DESKTOP
Description:
Authentication Ticket Granted:
  User Name:  jgarman
  Supplied Realm Name: WEDGIE.ORG
  User ID: WEDGIE\jgarman
  Service Name:  krbtgt
  Service ID:  WEDGIE\krbtgt
  Ticket Options:  0x40810010
  Ticket Encryption Type: 0x3
  Pre-Authentication Type: 2
  Client Address:  192.168.1.17
```

The sequence of event log entries begins with a 672 event, signifying that the Authentication Server has issued a TGT. Note that the User field contains SYSTEM, not the end user for whom the ticket was issued. The username component of the requesting principal is contained in the User Name field, which is mapped to an NT-style user name in the User ID field. Unfortunately, this implies that if you want to filter the Event Log to show activity relating to a particular user name, you’re out of luck. Also note that the Computer field always lists the domain controller’s NetBIOS name (in this case DESKTOP), not the requesting machine’s name, once again negating any ability to intelligently filter through the standard Event Viewer interface.

The Service Name field contains the first component of the principal we’ve been issued a ticket for: in this case simply, “krbtgt.” This service name is mapped to a username in the Active Directory, and the resulting name is used for the Service ID field, much like the User Name is mapped to a User ID.

Finally, we see the ticket options (in easy-to-read hexadecimal format).

After the client receives this TGT, it requests service tickets. There are quite a few that Windows requests, and their names are strange to those used to working with Kerberos on Unix machines. Let’s take a look at one:

```
Event Type: Success Audit
Event Source: Security
Event Category: Account Logon 
Event ID: 673
Date:  10/1/2002
Time:  11:55:10 PM
User:  NT AUTHORITY\SYSTEM
Computer: DESKTOP
Description:
Service Ticket Granted:
  User Name:   jgarman
  User Domain:  WEDGIE.ORG
  Service Name:  WEB$
  Service ID:  WEDGIE\WEB$
  Ticket Options: 0x40810010
  Ticket Encryption Type: 0x17
  Client Address:  192.168.1.17
```

As you can see, this Event ID is 673, indicating that the client contacted the Ticket Granting Service for a service ticket. In this case, a service ticket is granted to the WEB$ service (this is simply the NetBIOS name of the target machine, with a dollar sign appended).

Finally, let’s examine an example failed authentication attempt. Since Windows requires pre-authentication by default, you can detect password or brute-force attacks against your KDC by watching for event 675, Pre-authentication Failed messages. Here is an example:

```
Event Type: Failure Audit
Event Source: Security
Event Category: Account Logon 
Event ID: 675
Date:  10/4/2002
Time:  11:56:07 PM
User:  NT AUTHORITY\SYSTEM
Computer: DESKTOP
Description:
Pre-authentication failed:
  User Name:  Administrator
  User ID:  WEDGIE\Administrator
  Service Name:  krbtgt/WEDGIE
  Pre-Authentication Type: 0x2
  Failure Code:  24
  Client Address:  192.168.1.1
```
