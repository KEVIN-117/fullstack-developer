## La organización

La organización ficticia que usaremos como ejemplo es la Ejemplo de proveedor de servicios de Internet, un destacado proveedor de acceso telefónico local, T1 y servicio DSL en la zona de Anytown. El ISP de ejemplo cuenta con una red interna con dos divisiones principales en su organización de TI. Una división de la organización de TI proporciona soporte al usuario final y servicios a los escritorios y servidores de Windows. Este departamento administra el servidor de correo electrónico de la empresa, que ejecuta Microsoft Exchange, y ya tiene un sistema Active Directory Windows 2000 instalado para manejarlo inicios de sesión de usuario en la red de Windows.

El segundo departamento de TI administra los sistemas Unix de backend, destacando especialmente un gran banco de máquinas de alojamiento web que ejecutaban Linux y Apache. Además, el ISP de muestra cuenta con una pequeña prueba y staging donde se prueba el nuevo software antes del despliegue. El Unix Actualmente, los sistemas no disponen de un sistema de autenticación centralizado en lugar; Hay una mezcla de archivos _/etc/passwd_, _archivos htpasswd_ y hashes de contraseña almacenados en un Base de datos MySQL que gestiona las necesidades actuales de autenticación.

La configuración actual tiene problemas serios en cuanto a la capacidad de manejar punto de vista. Añadir o eliminar usuarios en las máquinas Unix es un proceso tedioso proceso que implica iniciar sesión en cada máquina por separado y añadir o Eliminar una entrada del archivo _/etc/passwd_ de la máquina local. Además, la ausencia de la sincronización entre las máquinas Unix significa que los usuarios tienen una relación separada Contraseñas de cada máquina a la que tengan acceso. Como resultado, la Muestra El ISP tiene muchos archivos _de paso_ obsoletos en sus máquinas, algunos contienen entradas para usuarios que ya no deberían tener Acceso.

Para resolver los problemas de autenticación, debería existir una infraestructura estableció que centraliza la administración del usuario información de autenticación. Además de centralizar el información de autenticación para los sistemas Unix, ha decidido la dirección establecer un sistema de inicio de sesión único multiplataforma para que el personal pueda iniciar sesión una vez a través de sus sistemas Windows de sobremesa y luego poder autenticarse de forma transparente a cualquier otro sistema, ya sea Windows o Basado en Unix. Por supuesto, Kerberos ha sido elegido para proporcionar esta capacidad. Más concretamente, Kerberos v5, ya que es la última revisión de la Protocolo Kerberos y proporciona compatibilidad con el Windows existente Configuración de Active Directory en 2000.

Ahora mismo, las únicas aplicaciones que el ISP de ejemplo está planeando para kerberizar son inicios de sesión remotos en las máquinas Unix, así como en algunas Aplicaciones X-Windows que ejecuta el personal de soporte y operaciones de red de forma regular.

## Planificación

El primer paso es una fase de planificación. Aquí evaluamos la corriente y los requisitos que los nuevos reinos de Kerberos deben cumplir, y equilibrar esos con las limitaciones de coste implicadas en el proyecto. Durante esta fase de planificación, dibujaremos el nuevo Kerberos estructura de reino, define qué conjunto de usuarios tendrá cada reino de Kerberos contener y, finalmente, preparar los sistemas necesarios para instalar el Software KDC de Kerberos.

### Planificación de los Reinos de Kerberos

La primera decisión que hay que tomar al implementar Kerberos es si habrá múltiples reinos de Kerberos y, de ser así, qué La relación entre ellos lo será. Hemos decidido dividir el organización en tres reinos para hacer cumplir la separación entre los tres funciones del ISP, a saber, la producción/negocio operaciones, los servidores Unix implicados en el soporte al cliente y Eventos de anfitriones y el laboratorio, que está aislado de todo si no.

En este caso, ya se ha establecido un reino: las ventanas Dominio de Active Directory. Este dominio se estableció como SAMPLE.COM, que también es el nombre de dominio DNS del ISP. Hay dos reinos más que estableceremos como parte de este ejemplo, llamado UNIX.SAMPLE.COM y LABS. SAMPLE.COM. Los crearemos como subdominios de los existentes SAMPLE.COM reino para facilitar las relaciones entre reinos—el La estructura jerárquica de reino crea un camino implícito de certificación para autenticación entre reinos, como vimos en [el capítulo 8](https://learning.oreilly.com/library/view/kerberos-the-definitive/0596004036/ch08.html "Chapter 8. Advanced Topics").

Con los nombres de los reinos fuera del camino, tenemos que establecer relaciones de confianza entre los reinos, si las hay. Recuerda que una relación de confianza entre reinos no es automáticamente proporcionar acceso a recursos en un reino desde el reino de confianza. Sin embargo, teniendo en cuenta esa limitación, sigue siendo importante crear un enfoque de seguridad en capas, y queremos restringir el fideicomiso las relaciones de los reinos de Kerberos tanto como fuera posible. Mientras esto sí obliga a los usuarios que deseen usar recursos en ambos reinos a iniciar sesión ambos ámbitos, hace cumplir la separación administrativa y de seguridad entre los reinos de Kerberos.

Teniendo en cuenta lo anterior, separaremos el LABS.SAMPLE.COM ámbito desde los reinos de producción SAMPLE.COM y UNIX.SAMPLE.COM, para hacer cumplir la separación del entorno de pruebas en el ámbito de laboratorios de la ámbitos de producción. Se establece un fideicomiso bidireccional entre los dos reinos de producción, SAMPLE.COM y UNIX.SAMPLE.COM, para permitir el intercambio de recursos entre los dos reinos con un conjunto de Credenciales. La [Figura 9-1](https://learning.oreilly.com/library/view/kerberos-the-definitive/0596004036/ch09s02s01.html#kerberos-CHP-9-FIG-1 "Figure 9-1. Sample ISP’s Kerberos realm layout") muestra los reinos de Kerberos implicados y el fideicomiso relaciones entre ellos.

### Planificación del KDC de Kerberos

Con los reinos de Kerberos cartografiados, ahora podemos empezar Planificar los detalles de implementación para cada uno de nuestros nuevos reinos. La [figura 9-2](https://learning.oreilly.com/library/view/kerberos-the-definitive/0596004036/ch09s02s03.html#kerberos-CHP-9-FIG-2 "Figure 9-2. Sample ISP’s network layout") muestra cierta planificación actividad. Se tomó la decisión consciente de replicar los datos ubicados en este importante ámbito en dos máquinas, para asegurar una alta disponibilidad. Además, debido a la naturaleza sensible de los datos ubicados en Estos servidores están separados de la red de alojamiento del cliente, presumiblemente detrás de un cortafuegos restrictivo que impide que los atacantes obtener acceso a los KDC desde la red anfitriona, en el caso uno de las máquinas que alojan el cliente está comprometida.

Se utiliza un razonamiento similar para el LABS.SAMPLE.COM Kerberos KDC Ubicación. A continuación, es necesario seleccionar el hardware y el sistema operativo para estos nuevos reinos de Kerberos. No se requiere una máquina potente; la número de principales que estarán ubicados en cualquiera de estos dos reinos No es lo mejor, probablemente por debajo de 100. Por lo tanto, una gama media basada en Intel máquina que ejecute un sistema operativo libre, como Linux o FreeBSD, Encaja perfectamente. Usamos FreeBSD para nuestros ejemplos, pero cualquier El sistema operativo es suficiente.

Como este es un ejemplo, usaremos dos Kerberos diferentes implementaciones para UNIX.SAMPLE.COM y LABS. SAMPLE.COM. La primera, UNIX.SAMPLE.COM, utilizará la implementación de Kerberos 5 del MIT, mientras que LABS.SAMPLE.COM utilizará la implementación de Heimdal Kerberos. Esto es algo así como un decisión arbitraria, ya que cualquiera de los KDC Kerberos disponibles funcionaría Está bien en esta circunstancia. Continuando con las decisiones de software, nosotros deben decidir qué servicios adicionales, si es que hay alguno, operar en el KDC máquinas. OpenSSH es una buena opción para proporcionar acceso remoto fines de gestión, pero no se instalan otros servicios para garantizar la seguridad de los KDCs.

La disposición del disco y la estrategia de copia de seguridad son importantes para Tenlo en cuenta durante la planificación. Como estas máquinas contendrán datos (el base de datos Kerberos) que no es fácilmente reemplazable y que debe serlo siempre disponible, es buena idea colocar el software Kerberos y base de datos en un conjunto de discos separado, hardware, espejado por RAID. Este RAID1 disco contendrá únicamente el software y la base de datos de Kerberos, y será Con atascos constantes. Colocar el software Kerberos junto con La base de datos en este disco separado tiene la ventaja de que la copia de seguridad la imagen puede restaurarse en una máquina de repuesto y el servicio restaurarse rápidamente, ya que todo el KDC de Kerberos está contenido en la imagen de respaldo. Restablecer el servicio de autenticación de Kerberos requeriría significativamente más tiempo si el software de Kerberos tenía que ser restaurado desde una copia de seguridad separada, o recompilado y reinstalado desde Scratch.

Otra idea, que puede ser más práctica en el mundo actual de platos grandes de disco duro, es colocar todo en un solo disco espejo listos. Las particiones deben establecerse en el disco para asegurar que los registros y otros espacios temporales no llenan todo el disco y afectan las operaciones del servidor Kerberos. El servidor puede ser imaginado con software como Ghost de Symantec para sistemas basados en Intel, y se pueden hacer volcados periódicos del directorio de la base de datos Kerberos. En Cualquiera de estas técnicas, un repuesto en frío puede ponerse en marcha rápidamente restaurando la imagen en el sistema de repuesto en frío. Usaremos esto esta última técnica en nuestro ejemplo.

Finalmente, existen algunos parámetros específicos de Kerberos que pueden ser ajustado al instalar nuevos reinos de Kerberos. Estos incluyen el máximo Duración de la entrada de entrada, la vida máxima renovable de las entradas y la opción para permitir tickets reenviables/sin dirección. En este ejemplo, no lo haremos hay que ajustar cualquiera de estos parámetros; Si quieres ajustar el parámetros de vida por defecto, puedes usar la configuración en el archivo _kdc.conf_ de MIT, o puedes especificar diferentes en respuesta a los indicios cuando Heimdal inicializa el reino. Las propiedades restantes pueden establecerse por principal mediante Kadmin. Consulte el Apéndice para más detalles.

## Implementación

Ahora podemos empezar a crear los dos nuevos reinos de Kerberos. Antes de comenzar, debemos establecer los requisitos previos que deben ser Satisfecho antes de que pueda comenzar la implementación de los nuevos reinos. La primera el requisito previo es un servidor DNS con DNS directo e inverso que funcione zonas para el _dominio DNS sample.com_. En nuestro por ejemplo, el servicio se aloja a través del Active Directory existente dominio, y registros DNS apropiados se han añadido a los archivos de zona Ya para todas las máquinas de nuestra red de muestras.

El segundo requisito previo es que todas las máquinas tengan NTP instalado y configurado. El dominio Windows realizará la sincronización temporal contra los controladores de dominio, pero NTP debe instalarse manualmente y configurado en las máquinas Unix. Antes de que los reinos de Kerberos estén implementados como se describe a continuación, estos dos servicios deben estar funcionando correctamente.

### Implementación de UNIX.SAMPLE.COM

Empezaremos con UNIX. SAMPLE.COM. Ambos KDCs, unixkdc1.sample.com y _unixkdc2.sample.com_, tienen una nueva instalación de la última distribución de FreeBSD. Dos de 18GB Se han instalado discos SCSI intercambiables en caliente en cada máquina, y cada caja tiene una tarjeta RAID hardware configurada para realizar el reflejo a través de la Instalado discos. La disposición de la partición se parece [a la Tabla 9-1](https://learning.oreilly.com/library/view/kerberos-the-definitive/0596004036/ch09s03s01.html#kerberos-CHP-9-TABLE-1 "Table 9-1. Partition table for Unix hosts").

Mesa 9-1. Tabla de particiones para hosts Unix

|Punta de la montaña|Descripción|Tamaño|
|---|---|---|
|/|Root drive incluye todo el sistema operativo Programas y datos|5GB|
|/krb5|Base de datos y software de Kerberos|4GB|

|/tmp|Archivos temporales|2GB|

Esta disposición permite ampliar el crecimiento de bases de datos de Kerberos, mientras que hacer cumplir la separación entre los datos críticos de la base de datos Kerberos y cualquier archivo de registro o temporal. Una disposición de particiones como la una de las anteriores asegura que estos archivos de registro no puedan llenar todo el disco, lo que puede causar que el sistema operativo o el software de Kerberos fallo o, peor aún, corromper la base de datos de Kerberos.

                max_life = 10h 0m 0s
                max_renewable_life = 7d 0h 0m 0s
                master_key_type = des3-hmac-sha1

#### Archivos de configuración de reino

Con este archivo instalado, ahora podemos crear el archivo _krb5.conf_ que se usará para cada host en el reino UNIX.SAMPLE.COM Kerberos. Fíjate en las entradas adicionales en la estrofa domain_realm, ya que no existe ningún dominio _DNS unix.sample.com_ que contenga todo el de los anfitriones en el reino UNIX.SAMPLE.COM Kerberos. Como resultado, el el mapeo entre nombres DNS y el correspondiente reino de Kerberos debe estar especificado explícitamente.

```
[libdefaults]
        default_realm = UNIX.SAMPLE.COM

[realms]
        UNIX.SAMPLE.COM = {
                kdc = unixkdc1.sample.com:88
                kdc = unixkdc2.sample.com:88
                admin_server = unixkdc1.sample.com
        };

        SAMPLE.COM = {
                kdc = exchange.sample.com:88
        };

 [domain_realm]
        .sample.com = SAMPLE.COM
        sample.com = SAMPLE.COM
        .hosting.sample.com = UNIX.SAMPLE.COM
        hosting.sample.com = UNIX.SAMPLE.COM
        dns.sample.com = UNIX.SAMPLE.COM
        billing.sample.com = UNIX.SAMPLE.COM
        unixkdc1.sample.com = UNIX.SAMPLE.COM
        unixkdc2.sample.com = UNIX.SAMPLE.COM

[logging]
        kdc = FILE:/var/log/kdc.log
        admin_server = FILE:/var/log/kadmin.log
```

Este archivo se instala en todas las máquinas que son miembros de la UNIX.SAMPLE.COM reino de Kerberos. La estrofa de tala es lo único importante para las máquinas KDC, pero no perjudica si se incluye con el archivo _krb5.conf_ instalado en otras máquinas como bueno.

También podrías introducir la información de LABS.SAMPLE.COM aquí si quieres usar Kerberos para iniciar sesión en las máquinas del laboratorio a través de Reflejo X también. Dado que no hay una clave entre reinos compartidos SAMPLE.COM y LABS.SAMPLE.COM, tendrás que iniciar sesión en el LABS.SAMPLE.COM reino de Kerberos a través de Reflejo X, ya que no puede usarlo las credenciales del dominio para autenticarte en los laboratorios Kerberos reino.

Una vez que la configuración del reino de Kerberos está terminada, las conexiones de anfitrión pueden establecerse para cada una de las máquinas en UNIX. SAMPLE.COM. Ya que Reflection utiliza el TGT adquirido por Windows durante el proceso de inicio de sesión, y se han establecido relaciones entre los Activos Dominio de directorio y el reino UNIX.SAMPLE.COM Kerberos, Reflection utiliza tus credenciales actuales de Kerberos para conseguir entradas para el Aloja Unix e inicia sesión en él. Este es solo un ejemplo de un kerberizado que pueda aprovechar la infraestructura de Kerberos. Como las necesidades crecen, se pueden hacer más aplicaciones conscientes de Kerberos para ampliar la utilidad del sistema de inicio de sesión único Kerberos.
