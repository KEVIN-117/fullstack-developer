# Tópico 2.4: Servidores de Automatización Autohospedados (Runner CI/CD)

## 🎯 Objetivo de Aprendizaje
Desplegar y asegurar un agente corredor local (Self-hosted runner) en el Home Lab y programar un pipeline automatizado de integración y despliegue continuo (CI/CD).

## 📋 Checklist de Conceptos a Dominar
- [ ] Explicar cómo el runner autohospedado extrae tareas de GitHub sin requerir puertos abiertos de entrada en el router local.
- [ ] Riesgos de seguridad al enlazar runners autohospedados en repositorios públicos (inyección de código mediante pull requests).
- [ ] Comprender el montaje `/var/run/docker.sock` y cómo interactúa el runner con el daemon de Docker del host Debian.
- [ ] Entender las partes de un pipeline declarativo (`workflow`, `jobs`, `steps`, `runners`, `secrets`).
- [ ] Conocer qué es el concepto de despliegues con cero caídas (Zero-Downtime deployment) y cómo se implementa en contenedores.

## 📚 Conceptos Mínimos a Estudiar
*   **Modelo WebSocket de Runners:** El runner abre conexiones seguras de salida (TCP 443) hacia GitHub/GitLab y mantiene polling para descargar trabajos asignados. Esto asegura que el servidor Debian pueda redesplegar sin abrir el firewall local a conexiones de internet entrantes.
*   **Seguridad Socket Docker (`docker.sock`):** Permitir al runner acceder a `/var/run/docker.sock` es el estándar en pipelines locales para que construya e inicialice imágenes. Sin embargo, equivale a privilegios root sobre el host físico (ya que puede manipular cualquier contenedor). Debe limitarse su uso exclusivamente a repositorios privados y protegidos.
*   **Estructura Workflow:** Un archivo `.yml` que define qué eventos gatillan la automatización (ej. `on: push`), los trabajos (`jobs`) a correr en paralelo o serie, y los pasos secuenciales (`steps`) de ejecución.

## 🚀 Actividades Prácticas Realizadas
1. Desplegado un agente corredor de GitHub Actions contenerizado e interconectado con el daemon de Docker físico.
2. Registrado el runner local en tu repositorio privado mediante tokens de autenticación de GitHub.
3. Diseñado el archivo de workflow `.github/workflows/deploy.yml` para disparar acciones al hacer `git push`.
4. Programado el pipeline para correr pruebas locales, compilar imágenes usando caché y refrescar los contenedores del servidor.

## 🔍 Comandos de Diagnóstico Útiles
*   `docker logs -f github-runner`: Monitorea en vivo el estado del runner de automatización.
*   `git push origin main`: Dispara el workflow en GitHub y permite observar el progreso de las tareas desde la web.
*   `docker ps --filter "name=github-runner"`: Comprueba si el contenedor del corredor está activo en Debian.
