### **Fine-Tuning a Classification Model**

Now that we’ve prepared the baseline performance data and the dataset, let’s step in and do our first hands-on fine-tuning exercise. We will explain each part as we build toward the complete script. This process will bring together the prepared dataset and the model via Hugging Face’s Trainer API. (The code for fine-tuning a classification model is available in _part4/03 -finetune-classificationModel.ipynb_.)

First, we need to import all the necessary classes from the Hugging Face Transformers and Datasets libraries, as well as standard Python libraries needed for numerical operations and evaluation metrics:

from transformers import AutoModelForSequenceClassification
from transformers import AutoTokenizer
from transformers import TrainingArguments, Trainer
from transformers import DataCollatorWithPadding
from datasets import load_from_disk
import numpy as np
import evaluate

These lines import the following transformers and libraries:

- AutoModelForSequenceClassification, TrainingArguments, and Trainer The core model and training process
- AutoTokenizer Handles text tokenization
- DataCollatorWithPadding Prepares batches of data
- load_from_disk Loads our saved dataset
- numpy For numerical operations, specifically used here in the metrics
- evaluate Loads standard evaluation metrics

If you need a quick refresher on tokenization and tokens, refer to [Chapter 4](https://learning.oreilly.com/library/view/the-developers-guide/0642572230333/xhtml/ch4.xhtml#ch4).

Next, we define the identifier for the pretrained model we’ll use and load the corresponding tokenizer. The tokenizer needs to match the model so it processes text into numerical inputs that the model understands based on its pretraining:

model_id = "distilbert/distilbert-base-uncased"
tokenizer = AutoTokenizer.from_pretrained(model_id)

Now, we load the dataset that we prepared and saved earlier with the Datasets library. This dataset contains our email summaries and their corresponding labels, which should already be split into training, validation, and testing sets within a DatasetDict. We then define a simple function to preprocess the text data via the tokenizer, which will be applied to every example in the dataset:

def preprocess_function(examples):
    # Apply the tokenizer to the 'text' column,
    # truncating sequences that are too long
    return tokenizer(examples["text"], truncation=True)

# Load the dataset saved from the data preparation step
dataset = load_from_disk("./data/mail_dataset_labeled")

# Apply the preprocessing function to the
# entire dataset using map for efficiency
tokenized_dataset = dataset.map(preprocess_function, batched=True)

The map method with batched=True efficiently applies our preprocess _function to batches of examples, adding the numerical token IDs, attention masks (binary maps that tell the model which tokens are meaningful data to be processed and which are padding to be ignored during calculation), and other necessary inputs to each example in the dataset splits.

Transformer models require their input sequences within a batch to be of the same length. Since our email summaries will vary in length even after tokenization, we use DataCollatorWithPadding. This object will take a batch of tokenized examples and dynamically pad the shorter sequences with special padding tokens so they all match the length of the longest sequence in that specific batch:

data_collator = DataCollatorWithPadding(tokenizer=tokenizer)

(We’ll cover padding in more detail in the next chapter.)

For classification tasks, we need to evaluate how well the model is performing during training and get a final performance score. This requires calculating metrics like accuracy. Hugging Face’s Evaluate library makes it easy to load standard metrics and define a function that the Trainer can use to compute these metrics from the model’s predictions and the true labels:

accuracy = evaluate.load("accuracy")

def compute_metrics(eval_pred):
    # The Trainer provides predictions and labels during evaluation
    predictions, labels = eval_pred
    # Get the predicted class ID (the one with the highest probability)
    predictions = np.argmax(predictions, axis=1)
    # Use the loaded accuracy metric to compare predictions to true labels
    return accuracy.compute(predictions=predictions, references=labels)

Next, we need to make sure our model understands the relationship between the numerical IDs it outputs and the meaningful text labels for our email categories. We do this by defining dictionaries that map labels to IDs (label2id) and IDs back to labels (id2label). These were likely created or used when you prepared your dataset, and now we’ll use them again:

label2id = {
    "IN_Bank": 0,
    "IN_School": 1,
    "US_Bank": 2,
    "US_School": 3
}

id2label = {
 0: "IN_Bank",
 1: "IN_School",
 2: "US_Bank",
 3: "US_School"
}

Now, we load the pretrained DistilBERT model that we want to fine-tune. Since our task is classification, we use AutoModelForSequenceClassification. When loading, we tell the model the number of output labels it should have (four, in our case) and provide the ID-to-label mappings so the model can correctly interpret the numerical predictions:

model = AutoModelForSequenceClassification.from_pretrained(
    model_id, num_labels=4, id2label=id2label, label2id=label2id)

Model training requires the use of a lot of settings, known as _hyper-parameters_. These settings control how the training runs, such as how fast the model learns, how much data it processes at once, and how many times it goes through the dataset. Just as with the no-code approach, we need to specify all the hyperparameters that control the training process. The TrainingArguments class is where we define all these settings, such as the location to save outputs, the learning rate, batch sizes, the number of times to go over the data, and the evaluation strategy:

training_args = TrainingArguments(
    output_dir="trainer_output/my_mail_classifier",
    learning_rate=2e-5,
    per_device_train_batch_size=8,
    per_device_eval_batch_size=8,
    num_train_epochs=3,
    weight_decay=0.01,
    eval_strategy="epoch",
    save_strategy="epoch",
    load_best_model_at_end=True,
    push_to_hub=False,
    report_to="none",
)

This creates an instance of TrainingArguments, where we define the hyper-parameters. These settings significantly impact how the training proceeds:

- output_dir Defines the directory where the model checkpoints and training results will be saved.
- learning_rate Controls the step size the model takes when updating its parameters during training.
- per_device_train_batch_size Sets the number of training examples processed at once on each available device (like a GPU). Larger batches require more memory but can sometimes lead to faster training.
- per_device_eval_batch_size Similar to the training batch size, but for the evaluation dataset.
- num_train_epochs The total number of times the training process will iterate over the entire training dataset.
- weight_decay A regularization technique used to help prevent overfitting by penalizing large weights in the model.
- eval_strategy="epoch"/save_strategy="epoch" Tells Trainer to evaluate the model’s performance on the evaluation set and save a model checkpoint at the end of every training epoch.
- load_best_model_at_end=True After training completes, loads the model checkpoint that achieved the best performance on the evaluation set (as defined by eval_strategy).
- push_to_hub=False Set this to false to prevent the Trainer from automatically uploading our trained model to the Hugging Face hub.
- report_to="none" Disables reporting of training metrics to external services.

Next, we assemble everything needed for the training run by creating an instance of Trainer. This object takes our configured model, the training settings (training_args), the tokenized training and evaluation datasets, the tokenizer used for data processing, a data collator to prepare batches, and a function to compute performance metrics during evaluation:

trainer = Trainer(
    model=model,
    args=training_args,
    train_dataset=tokenized_dataset["train"],
    eval_dataset=tokenized_dataset["validation"],
    tokenizer=tokenizer,
    data_collator=data_collator,
    compute_metrics=compute_metrics,
)

With Trainer initialized, a single line of code is all it takes to start the entire technical fine-tuning process, which will now run according to all the configurations we’ve set:

trainer.train()

The final step after the trainer.train method finishes is saving the fine-tuned model to disk:

model_path = "models/my_mail_classifier"
trainer.save_model(model_path)

We do this so we can load and use our specialized email classifier later without having to retrain it.

### **Why Not Prompt Engineering?**

We discussed prompt engineering in detail in [Chapter 4](https://learning.oreilly.com/library/view/the-developers-guide/0642572230333/xhtml/ch4.xhtml#ch4). Although it’s a powerful approach for interacting with LLMs, for some use cases, it might not be the best choice. [Table 11-3](https://learning.oreilly.com/library/view/the-developers-guide/0642572230333/xhtml/ch11.xhtml#tab11-3) shows a comparison.

_Model weights_ are the numerical parameters within a neural network or ML model. The weights are adjusted during the training process and collectively represent the patterns, features, and knowledge the model has learned from the data. They determine how the model processes input information to produce its output.

_Catastrophic forgetting_ occurs during sequential learning, such as fine-tuning, where training a model on a new task causes it to abruptly or severely lose its ability to perform previous tasks it was originally trained on. The new learning interferes with and overwrites the model’s existing knowledge and skills related to older data or tasks.

**Table 11-3:** Fine-Tuning vs. Prompt Engineering
||**Fine-tuning**|**Prompt engineering**|
|---|---|---|
|**How it works**|You update the LLM’s weights by training it on a new dataset and adapting it to a specific task or domain.|You craft clever input prompts to guide the LLM’s output, providing instructions, context, or examples.|
|**Advantages**|Can lead to significant performance improvements over prompt engineering<br><br>Allows the model to learn more in-depth knowledge and adapt to specific data distributions<br><br>Can improve generalization to new, similar tasks<br><br>Offers more control over the model’s behavior|Less computationally expensive than fine-tuning<br><br>Doesn’t require access to training data or modifying model weights<br><br>Can be very effective for certain tasks, especially with skilled prompt design|
|**Limitations**|More computationally expensive and time-consuming than prompt engineering<br><br>Requires access to training data and potentially more technical expertise<br><br>Risk of catastrophic forgetting if not done carefully|Requires careful crafting and experimentation with prompts<br><br>May not achieve the same level of performance as fine-tuning, especially for complex tasks<br><br>Can be challenging to generalize to new tasks or domains<br><br>Limited control over the model’s internal knowledge and behavior|

Use fine-tuning when you have the following:

- A need for the highest possible performance
- Complex tasks that require the model to learn in-depth knowledge
- Access to training data and the resources to fine-tune
- A need to adapt the model to a specific domain or task

Use prompt engineering when you have the following:

- Limited resources or time
- Simpler tasks or a need for a quick solution
- No access to training data or the ability to fine-tune

Fine-tuning can be like giving a small, specialized tool the perfect edge for a specific job. While a larger, more general tool might be able to do many tasks, a fine-tuned smaller tool can be much more efficient and precise. This focused approach makes the tool not only easier to handle but also much more economical while running it.

### **Introduction to PEFT and LoRA**

We will use parameter-efficient fine-tuning (PEFT) and low-rank adaptation (LoRA) for fine-tuning our LLM. But before we attempt to define these terms, we need to understand why these modes of training exist.

#### _**Regular Fine-Tuning vs. PEFT**_

With regular fine-tuning, shown in the previous example, we update all the parameters of the language model by training it on new data. This allows the model to learn new information and adapt to the specific characteristics of the new data, improving the model’s overall performance on the target task. This technique also leads to significant performance improvements, especially with sufficient data, and is relatively straightforward to implement.

On the flip side, this approach is computationally very expensive and time-consuming. It also requires a lot more data to avoid overfitting. In this common ML problem, a model learns the training data too precisely, including the noise and specific details that are unique to that particular dataset. Instead of capturing the general underlying patterns, the model essentially memorizes the training examples. This results in excellent performance on the training data itself but significantly poorer performance when the model is asked to make predictions on new, unseen data.

But even more concerning is that this kind of training leads to catastrophic forgetting. If you retrain a model on a new dataset without any special techniques, the model could overwrite the knowledge it gained from the first dataset.

This is where PEFT (_[https://huggingface.co/blog/peft](https://huggingface.co/blog/peft)_) comes into play. PEFT methods introduce a small number of additional parameters to the model instead of modifying the entire weight matrix. This significantly reduces the number of trainable parameters, making the fine-tuning process more efficient and less computationally expensive.

With fewer trainable parameters, the training process requires less memory and computational resources. This leads to faster training times, especially for large models.

[Table 11-4](https://learning.oreilly.com/library/view/the-developers-guide/0642572230333/xhtml/ch11.xhtml#tab11-4) provides a summary of the two approaches.

**Table 11-4:** PEFT vs. Regular Fine-Tuning
||**PEFT**|**Regular**|
|---|---|---|
|**When to use**|You have limited data or computational resources.<br><br>You need faster training and deployment.<br><br>You want to minimize storage requirements.<br><br>The new task is relatively similar to the original pretraining task.|You have sufficient data and computational resources.<br><br>You need maximum performance gains.<br><br>The new task is significantly different from the original pretraining task.|
|**Pros**|More efficient and faster than regular fine-tuning<br><br>Less prone to overfitting, especially with limited data<br><br>Reduces storage requirements for the fine-tuned model<br><br>Mitigates catastrophic forgetting|Can lead to significant performance improvements, especially with sufficient data<br><br>Relatively straightforward to implement|
|**Cons**|Might not achieve the same level of performance as regular fine-tuning in some cases<br><br>Requires careful selection of the target modules|Computationally expensive and time-consuming<br><br>Requires more data to avoid overfitting<br><br>Can lead to catastrophic forgetting (loss of previously learned knowledge)|

#### _**LoRA**_

LoRA is one of the PEFT methods. Think of trying to customize a car engine based on the way you like to drive. Instead of taking it apart and rebuilding it, what if you could just adjust a few key components? That’s the idea behind LoRA.

It’s like a small, specialized chip for the engine’s control system. This chip can be easily customized for various modes without changing the engine itself, such as switching between the modes eco, normal, and sport. LoRA works similarly by adding a small number of adjustable parameters to the existing model, allowing for efficient fine-tuning without the massive overhead.

This approach offers several benefits:

- **Faster and cheaper training** LoRA trains dramatically faster than a full fine-tune. By adjusting far fewer parameters, it completes the training process in a fraction of the time, which directly translates to lower compute costs (less money spent on GPU hours).
- **Lower hardware barrier** LoRA significantly reduces the amount of memory needed. This is a huge benefit, as it makes it possible to fine-tune massive models on more accessible, consumer-grade hardware instead of requiring expensive, top-tier enterprise GPUs.
- **Portable and efficient** Instead of producing a new, massive model (for example, 20GB), LoRA training outputs a tiny “adapter” file (often just 10 to 100MB). This makes it incredibly easy to store, share, and deploy many fine-tuned versions of a single base model.
- **High-quality results** Despite its efficiency, LoRA achieves performance that is comparable to, and in some cases even better than, traditional fine-tuning. You get the quality of a full fine-tune without the high cost.

Essentially, LoRA provides a lightweight and efficient way to adapt massive language models for specific tasks, making them more accessible and practical for a wider range of applications.

### **Prompting an LLM**

Before we start our fine-tuning journey, let’s explore how LLMs understand instructions or prompts. #### _**Understanding Instruction Templates**_

You’re familiar with how LLMs respond to instructions provided in plain text, often through prompting or conversational prompts. While these models are designed to understand human language, they aren’t always trained to interpret instructions and conversation history presented in the exact same format. The specific structure of your prompt—the way you delineate user input, system messages, or previous turns—can vary between models.

This is where instruction templates (also called _chat templates_) become important. An instruction template is the specific text format, including special tokens and structural rules, that a particular LLM was trained to expect when receiving instructions, context, or a chat history. Using the correct template for the model you are working with is crucial to ensure that the model properly understands your input and responds in the intended manner. Let’s look at a few examples of these model-specific templates. Hugging Face, Unsloth, and other libraries simplify the process of obtaining chat templates (we’ll use the Hugging Face platform for our examples):

#### _**Customizing Generated Response Format**_

To guide the model’s generation more precisely and influence the start of its response, a common technique when using instruction templates is to add the marker for the assistant role at the very end of your formatted prompt. This explicitly signals to the model that it is now the assistant’s turn to generate text, and its response should begin immediately following this marker.

We can also use this technique to encourage the model’s output to start with a specific prefix or phrase, effectively customizing the beginning of its response. For instance, by adding the assistant role marker followed immediately by GA: (geography assistant), we set an expectation that the model’s generated response should begin with this specific string. Let’s update our prompt accordingly and check the model’s output to see whether it follows this format:

        --snip--
        prompt = [
         # ... ...
         {
            "role": "assistant",
            "content": "GA: "
         },
        ]

        tokenized_input = tokenizer.apply_chat_template(
            prompt,
            tokenize=True,
            return_tensors="pt"
        )
        output_text = model.generate(tokenized_input, max_new_tokens=50)
        print(tokenizer.decode(output_text[0], skip_special_tokens=True))
        --snip--

**Output**  system
        You are a helpful geography assistant.
        You are able to answer questions about the world.
        user
        What is the capital of France?
        assistant
        GA:

Not quite what we had expected, right? Why didn’t the model return the response starting with GA:, or rather, why is it in a new line?

#### _**Controlling Where Generation Starts**_

Preparing input for language models isn’t just about providing context and instructions; sometimes we need precise control over exactly where the model should begin generating its response. Think of it like directing a play: You give the actor their lines up to a certain point—your cues—and then you want them to start improvising or delivering their next line immediately after your last word. How do we give the model this kind of precise cue?

Typically, chat templates add special tokens to mark the end of each message or turn, guiding the model to finish its thought or wait for the next input. However, for certain tasks, you might want the model to generate text that continues the final message provided in the prompt, rather than starting a completely new turn marked by assistant role tokens. The continue _final_message parameter controls this, allowing you to suppress the usual end-of-turn signals after the last message, instructing the model to generate text that flows directly from the point where the last message left off:

        --snip--
        tokenized_input = tokenizer.apply_chat_template(
            prompt,
            tokenize=True,
            return_tensors="pt",
            continue_final_message=True,
        )
        output_text = model.generate(tokenized_input, max_new_tokens=100)
        print(tokenizer.decode(output_text[0], skip_special_tokens=True))
        --snip--

**Output**  system
        You are a helpful geography assistant.
        You are able to answer questions about the world.
        use
        What is the capital of France?
        assistant
        GA: 09000 Paris, Île-de-France, France

This configuration shifts the model’s behavior from a structured turn-based dialogue to a continuous text-completion mode. You’ve now enabled the LLM to pick up the narrative or logical thread exactly where your prompt ends, facilitating a more natural and uninterrupted flow of information.

### **Training the LLM Using LoRA**

We are now ready to fine-tune our LLM. We will be using the PEFT approach for fine-tuning. Train the model using PEFT or LoRA with the following steps:

1. Define the LoRA config.
2. Apply configuration to the model.
3. Create training arguments.
4. Train.

Steps 3 and 4 are similar to what we did earlier for training the classification model. Let’s dive a bit into steps 1 and 2. (The code for this section is available in _part4/06-finetune-llm.ipynb_).

#### _**Reducing Parameters**_

When you fine-tune a large model the usual way, you might have to train all of its millions or even billions of parameters, and that requires significant computing power. LoRA offers a much more efficient approach. Instead of changing the original, large layers of the model, LoRA keeps them frozen and injects small, trainable adapter layers alongside them.

The most important setting in LoRA is the rank, often denoted by r. This value directly controls the size of the tiny adapter layers that are added to the model. A lower rank r means these adapter layers are very “narrow,” which adds fewer new parameters. A higher rank allows for potentially more nuanced adaptation but increases the number of parameters being trained by LoRA.

Let’s illustrate the parameter reduction. Imagine that a specific layer within a model has a weight matrix of size 1,000 × 1,000 parameters (a total of one million parameters in just this one matrix). Instead of training all one million here, LoRA with a chosen rank r (say, r=5) adds and trains two much smaller matrices for this layer: one of size 1000xr and one of size rx1000. The total number of trainable parameters that LoRA adds specifically for this layer is calculated as (1,000 × r) + (r × 1,000).

With r=5, this is (1,000 × 5) + (5 × 1,000) = 5,000 + 5,000 = 10,000 trainable parameters.

This means that for that single layer’s one million original parameters, LoRA requires training only 10,000 parameters. LoRA applies this technique to several key layers throughout the model. Summing up the relatively small number of parameters added per layer across all layers where LoRA is applied results in the total number of trainable parameters being dramatically reduced from potentially billions down to just a few million or even thousands, making fine-tuning much faster and less resource-intensive.

#### _**Configuring LoRA**_

After understanding the core concept of LoRA and the significance of rank, the next step in a technical fine-tuning process using LoRA is to define its configuration programmatically. The peft library is a popular tool for this, and it uses the LoraConfig class to hold all the settings indicating how LoRA should be applied.

First, we import the LoraConfig class from the peft library:

--snip--
from peft import LoraConfig

lora_config = LoraConfig(
  r=4,
  lora_alpha=8,
  lora_dropout=0,
  bias="none",
  task_type="CAUSAL_LM",
  target_modules = ["q_proj",
    "k_proj", "v_proj", "o_proj",
    "gate_proj", "up_proj", "down_proj"],
  modules_to_save=["lm_head"]
)
--snip--

This block creates an instance of LoraConfig, which we name lora_config. Let’s break down the key parameters within it:

- r The LoRA rank. As discussed, it’s the most critical parameter controlling the size of the small adapter matrices added to the model layers and, therefore, the number of trainable parameters. A lower r means fewer parameters but potentially less capacity for complex adaptation. In this example, r=4, indicating quite small adapter matrices.
- lora_alpha A scaling factor that adjusts the magnitude of the updates learned by the LoRA layers. It’s often set proportionally to r (for example, equal to r or 2 × r) to control the amount of influence the LoRA adaptations have on the original model’s behavior. The actual scaling applied is typically lora_alpha / r. Here, lora_alpha=32.
- lora_dropout Specifies the dropout rate to be applied to the LoRA adapter layers during training. With the dropout technique, a fraction of connections is randomly ignored during each training step. This helps prevent the small LoRA adapters from overfitting too closely to the training data. Here, a dropout rate of 0.05 (5 percent) is set.
- bias Controls the way bias terms in the target layers are handled during LoRA training. Setting bias="none" means that the bias parameters in the layers specified by target_modules will not be trained; they remain frozen at their pretrained values. Other options might train all bias terms or only specific ones.
- task_type Tells the peft library the kind of downstream task you are fine-tuning for. This helps the library correctly identify layers or apply task-specific considerations. CAUSAL_LM indicates causal language modeling, which is the standard task for most text-generation LLMs (predicting the next token based on preceding tokens).
- target_modules A list of strings specifying the exact names of the sublayers or modules within the pretrained base model where the LoRA adapter matrices should be injected. Common targets in transformer models are the weight matrices in the attention mechanism (like query q_proj, key k_proj, value v_proj, and output o_proj) and layers in the feed-forward networks (gate_proj, up_proj, down_proj). By targeting only specific, important modules, LoRA keeps the number of trainable parameters significantly lower than full fine-tuning.
- modules_to_save Specifies additional model components, like lm_head, whose original weights will also be made trainable and saved alongside the LoRA adapters. Fine-tuning lm_head is crucial as it directly impacts the model’s output probabilities and benefits from direct adaptation to your specific task.

This lora_config object now contains all the necessary instructions for the peft library to apply LoRA with your specified settings when fine-tuning a compatible base model for a causal language modeling task.

### **INSIDE A TRANSFORMER LAYER**

Transformer models, including the LLMs we’re discussing, are built from repeating layers, and each layer primarily consists of two main components working together: the attention mechanism and the feed-forward network.

The _attention mechanism_ is the model’s way of focusing on different parts of the input text when processing any single word. It allows the model to look at other words in the sequence and decide which ones are most important or relevant for understanding the current word’s meaning in context. This is crucial for understanding relationships between words that are far apart. Inside the attention mechanism, you’ll find specific linear projection layers often named q_proj, k_proj, and v_proj. These transform the input into the query, key, and value representations used for calculating attention. The o_proj layer processes the combined output from the attention step. When you see these names as target_modules in LoRA, it means LoRA is learning to subtly adjust the way the model calculates and processes attention, specializing this core focusing mechanism for your fine-tuning task.

After the attention mechanism has processed the relationships between words, the _feed-forward network (FFN)_ takes over. It’s like a standard neural network layer, but a key point is that it processes each word’s representation completely independently of the other words in the sequence. The FFN takes the context-rich information for a single word and runs it through a couple of transformation steps, adding nonlinearity. Common layers within the FFN, often seen as target_modules for LoRA, include up_proj, down_proj, and sometimes gate_proj. These layers expand (up_proj) and contract (down_proj) the representation’s dimensionality, allowing the model to further process and transform the information learned by attention. Applying LoRA here helps the model learn new ways to process and transform these individual token representations internally for the fine-tuned task.

By using techniques like LoRA to target these specific projection layers within both the attention mechanism and the FFN, you allow the model to adapt its core information processing and transformation steps for your specific task with only a tiny fraction of the original parameters, making fine-tuning efficient while specializing the model’s key functional parts.

A detailed explanation of how attention mechanisms and FFNs function internally is a topic that’s quite advanced and falls outside the primary focus of this book. We highly encourage you to explore these fascinating foundational concepts further to deepen your understanding.

Once you have loaded your base pretrained model (model) and defined your LoRA configuration detailing how LoRA should be applied (lora_config), you need to integrate the LoRA structure into the model itself. The peft library provides a function specifically for this:

--snip--
from peft import get_peft_model

peft_model = get_peft_model(
    model,
    lora_config,
)
--snip--

This is the core line. The get_peft_model function takes your original base model and your lora_config object as input. It then modifies the base model’s architecture according to the LoRA configuration. This involves injecting the small, trainable LoRA adapter layers into the specific target _modules you defined in your lora_config and, importantly, automatically “freezing” (making non-trainable) the vast majority of the original parameters in the base model.

The function returns a new model object, peft_model. This peft_model is now your parameter-efficient version of the base model, specifically prepared for fine-tuning using the LoRA method. It behaves just like a regular Hugging Face model and can be passed directly to a Trainer or used for inference, but internally, only a small fraction of parameters in the LoRA adapters will be updated during the training process, resulting in significant computational savings.

#### _**Training**_

To handle the training, we’ll use SFTTrainer from Hugging Face’s trl (Transformer Reinforcement Learning) library. This specialized toolkit simplifies the post-training process by providing high-level tools for supervised fine-tuning and other alignment techniques designed to teach the model human preferences. SFTTrainer is especially handy when working with PEFT techniques like LoRA, as it streamlines the transition from configuring training parameters to initializing the trainer with your specific model and datasets:

--snip--
from trl import SFTTrainer, SFTConfig

training_args = SFTConfig(
    output_dir="trainer_output/my_mail_classifier_llm",
    report_to="none",
    overwrite_output_dir=True,
    do_train=True,
    learning_rate=2e-4,
    num_train_epochs=3,
    bf16=False,
    fp16=False,
)

trainer = SFTTrainer(
   model=peft_model,
   args=training_args,
   train_dataset=dataset["train"],
   eval_dataset=dataset["validation"],
)

trainer.train()
--snip--

Let’s break down the code. This block instantiates SFTConfig with a set of parameters that dictate how the fine-tuning process will run. And finally, the SFTTrainer object brings together the model to be trained, the defined training configurations, and the datasets.

Here are some of the parameters used for SFTConfig:

- output_dir Specifies where the trained model checkpoints, logs, and other outputs will be saved
- report_to Set to none to prevent reporting training metrics to external platforms
- overwrite_output_dir Setting to True allows the Trainer to delete and recreate the output_dir if it already exists
- do_train Confirms that the training process should be executed
- learning_rate Sets the initial learning rate for the model’s optimizer
- num_train_epochs Defines the number of times the Trainer will iterate over the entire training dataset
- bf16=False and fp16=False Disables mixed-precision training (BFloat16 and Float16, respectively), meaning the model will likely train in full float32 precision

Once your PEFT model has completed training using the Trainer, saving your fine-tuned LoRA model is a straightforward final step, performed just as you saved the classification model earlier. Simply call the trainer.save_model method and provide a destination path. The Trainer and peft libraries ensure that the base model’s frozen weights and the newly trained LoRA adapter weights and configuration are saved together in that directory, creating a complete package ready for loading and using your fine-tuned LoRA model whenever needed.
