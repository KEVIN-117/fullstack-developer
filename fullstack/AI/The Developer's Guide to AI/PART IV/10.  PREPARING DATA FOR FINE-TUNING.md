### **Encoding the Labels**

At their core, ML models like LLMs fundamentally process numerical data. While they work with text, they do so by converting words and characters into mathematical or numerical representations behind the scenes—think back to how tokenization turned text into sequences of numbers. For our fine-tuning task, the classification labels (like IN_Bank and US_School) also need to be in a numerical format for the model to understand and use them. Therefore, the next step is to convert our text labels into unique numerical IDs.

In ML, we convert string labels into numbers because models are built on mathematical operations that require numerical input. This conversion makes the data compatible with algorithms, significantly improves computational efficiency during training, prevents the model from misinterpreting arbitrary relationships between string labels, and standardizes the data format for use across various ML frameworks and tools like Hugging Face.

We will assign IDs to the labels as shown in [Table 10-1](https://learning.oreilly.com/library/view/the-developers-guide/0642572230333/xhtml/ch10.xhtml#tab10-1).

When assigning these numerical IDs to your labels, the only crucial requirement is that each label receive a unique number. It is essential to keep track of which numerical ID corresponds to which text label, as you will need this mapping later to correctly interpret the model’s predictions.

### **Splitting the Data**

To effectively train or fine-tune a model and accurately evaluate how well it performs on data it hasn’t seen before, we cannot simply use the entire dataset for training. If we did, the model might memorize the data instead of learning general patterns—a problem called _overfitting_. To avoid this and get a realistic measure of performance, we first randomize the order of our data and then split it into three distinct sets:

- **Training dataset** The main part of the data, used directly to teach the model. The model learns from these examples, adjusting its internal workings to get better at the specific task (like classifying email). It’s where the core learning happens.
- **Validation dataset** Used while the model is being trained. It’s like giving the model a practice quiz on data it hasn’t specifically trained on. By checking performance on the validation set, we can monitor how well the model is learning, adjust the training process, and decide the best point to stop training to ensure that the model performs well on new data and doesn’t just memorize the training examples.
- **Testing dataset** Kept completely separate and used only after the model has finished training. This set provides a final, unbiased evaluation. Because the model has never seen this data during training or validation, the performance on the testing dataset gives you the most realistic idea of how well your fine-tuned model will work on completely new email in a real-world situation.

A good ratio to split the dataset into training, validation, and testing is 80-10-10:

- 80 percent of the data goes into training
- 10 percent for validation
- 10 percent for testing

Here’s what you should do for each of the files:

- Shuffle or randomize the records in the files.
- Split the data in each of the files in the ratio of 80-10-10.
- Save the data into separate files. You could name the files with the words _train_, _test_, and _validate_ in them, such as _train_us_bank.csv_, _valdate_us_bank.csv_, and _test_us_bank.csv_.

Consider the following code:

--snip--
import csv, random

random.seed(42)

path_to_in_bank = "rawData/in_bank.csv"

data_in_bank = []

with open(path_to_in_bank, "r") as f:
  reader = csv.reader(f)
  for row in reader:
    data_in_bank.append(row)

data_in_bank = data_in_bank[1:] # Remove header

# Shuffling
random.shuffle(data_in_bank)

# Splitting
train_ratio = 0.8
test_ratio = 0.1
val_ratio = 0.1
data_in_bank_length = len(data_in_bank)
data_in_bank_train_index = int(data_in_bank_length * train_ratio)
data_in_bank_test_index = int(data_in_bank_length * (train_ratio + test_ratio))

data_in_bank_train = data_in_bank[:data_in_bank_train_index]
data_in_bank_test = data_in_bank[data_in_bank_train_index:data_in_bank_test_index]
data_in_bank_val = data_in_bank[data_in_bank_test_index:]
--snip--

This reads data from one of your CSV files, shuffles it, and then divides it into the three sets: training, validation, and testing.

We shuffle the training data to prevent the model from learning any accidental patterns based on the order of the examples. This randomizing ensures that the model learns the features of the data, not just its sequence, which helps the model generalize better to new, unseen data and avoids bias.

Based on the data preparation steps we followed, we now have 12 files: our original four CSV files, each divided into three train, test, validate files. However, the fine-tuning process usually expects three files: one for the training dataset, one for the validation dataset, and one for the testing dataset.

Therefore, before we can begin fine-tuning, we need to combine and shuffle all four of our training datasets into a single _train_ file, all four validation datasets into a single _validate_ file, and all four testing datasets into a single _test_ file. Here are the steps you should follow:

1. Read the data from all four files.
2. Combine them into a single set.
3. Use the random.shuffle method to shuffle the data.
4. Save the data into a CSV file.

After following these steps for all three types of data, you will have your newly created dataset that includes three files: _train.csv_, _validate.csv_, and _test.csv_. You’ll use these files in the sections to follow.

### **Creating a Labeled Dataset**

When you prepare a dataset for training, it’s often for immediate use or use within a project. However, if you plan to share that dataset with others, or even reuse it in different parts of a complex project, simply saving it as a plain CSV or JSONL file (_[https://jsonlines.org](https://jsonlines.org/)_) can lead to problems.

The issue is that crucial metadata information about the data itself, such as the type of each column or the valid values it can hold, gets lost. For example, if you share a _train.csv_ file, someone receiving it wouldn’t automatically know that the text column is a string, or that the label column is also a string but is strictly limited to four specific values: IN_Bank, IN_School, US_Bank, or US_School. Without this embedded information, you’d have to provide separate documentation, which can easily get out of sync. Libraries like Hugging Face’s Datasets library solve this problem by allowing you to capture and embed all the important metadata directly within the dataset object, ensuring consistency and clarity whenever it’s used or shared.

Now, let’s see how we can embed this vital metadata directly into our dataset by re-creating it with the Hugging Face Datasets library. This process will ensure that our data is not only ready for training but also self-describing and robust for future use or for sharing with others. The steps include merging the content from our individual label files into a single collection, randomizing the combined data to ensure a good mix of examples in each split, and then dividing it into the training, validation, and testing sets while ensuring that each email retains its correct numerical label.

#### _**Creating the Train, Validate, and Test Datasets**_

Once we have loaded the dataset, we have to shuffle the data in these data-sets just as we did before. The shuffle function in the Datasets library is a handy tool for randomizing the order in our dataset. It’s like shuffling a deck of cards before dealing them out, and it ensures that the order of the data doesn’t introduce any bias or unintended patterns into our ML models. Here’s a breakdown of what shuffle does and why it’s important:

- **Randomizes order** The function randomly rearranges the examples in your dataset. The original order of the data is lost, and each time you shuffle, you’ll get a different order.
- **Adds a seed value** You can provide an optional seed argument to shuffle to ensure that you get the same random order every time you run the code with the same seed. This is important for reproducibility.

The Datasets library offers a convenient function called train_test_split. This function allows us to easily divide our dataset into two random subsets: a training set and a testing set.

To achieve our desired three splits—training, validation, and testing—we’ll use train_test_split in two stages. First, we’ll split our main dataset into a primary training set and a temporary set. Then, we’ll take that temporary set and split it again to create our final validation and testing datasets. Once we have these three distinct and properly randomized subsets, we’ll combine them into a single DatasetDict object, which is the standard format for managing multiple splits in Hugging Face:

--snip--
ds_in_bank_train_test_split = ds_in_bank['train']
    .train_test_split(test_size=0.2, shuffle=True, seed=42)

ds_in_bank_test_valid_split = ds_in_bank_train_test_split['test']
    .train_test_split(test_size=0.5, shuffle=True, seed=42)

ds_in_bank_split = DatasetDict({
    'train': ds_in_bank_train_test_split['train'],
    'validation': ds_in_bank_test_valid_split['train'],
    'test': ds_in_bank_test_valid_split['test']
})
--snip--

Complete this process for the rest of the datasets.

#### _**Combining the Datasets**_

The data we’ve collected and saved into separate datasets for each label needs to be consolidated into a single dataset file. This is necessary because standard fine-tuning tools and libraries are typically designed to work with one primary dataset file for training, simplifying the input process.

Along with combining the data, it’s crucial to shuffle the entire dataset. Shuffling ensures that examples from all the categories are randomly mixed throughout the training process. This prevents the model from being biased by the original order or grouping of the data and helps the model learn more accurately from a diverse sequence of examples:

--snip--
from datasets import concatenate_datasets

ds_combined_train = concatenate_datasets([
    ds_in_bank_split["train"],
    ds_in_school_split["train"],
    ds_us_bank_split["train"],
    ds_us_school_split["train"]
])
ds_combined_train = ds_combined_train.shuffle(seed=42)

// ... create the validate and test datasets

ds_combined = DatasetDict({
    "train": ds_combined_train,

Within this DatasetDict, each split remains a distinct collection of data, properly prepared and ready for its specific role in the fine-tuning and evaluation process.

#### _**Fixing the Label**_

To fix the label, we start with creating a set and a dictionary:

--snip--
label_names = [ "IN_Bank", "IN_School", "US_Bank", "US_School" ]

label2IdMap = {
    "IN_Bank": 0,
    "IN_School": 1,
    "US_Bank": 2,
    "US_School": 3
}
--snip--

Now we need to cast the column. _Casting_ is the process of explicitly instructing a program to convert a piece of data from one specific data type to another (in this case, turning an entire generic column field into a structured type). But casting is not enough. Our data will still have 0, 1, 2, or 3 as the label value. This step ensures that the underlying integer IDs in your dataset match your specific labels. If your dataset originally had IN_Bank as ID 3, this recasts, or remaps, the internal representation so that IN_Bank consistently maps to ID 0 as defined in your dictionary:

--snip--
from datasets import ClassLabel
ds = ds.cast_column("label", ClassLabel(names=label_names))
ds = ds.align_labels_with_mapping(label2IdMap, "label")
--snip--

That’s it. Save it as a new dataset and save it to disk. Then load and check the dataset again:
