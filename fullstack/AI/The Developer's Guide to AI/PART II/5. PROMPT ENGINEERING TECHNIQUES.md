### **Indicaciones de instrucción**

Los LLM solo son tan buenos como las instrucciones que les damos. Con el prompt adecuado, pueden manejar desde formatear texto hasta extraer datos, eliminar información personal identificable (PII) y clasificar texto. No necesitamos un enorme conjunto de datos etiquetado ni reglas frágiles incrustadas en nuestro código.

Veamos algunos ejemplos comunes. Mientras repasas los ejemplos, prueba tú mismo con los prompts.

#### _**Extracción de datos**_

Los LLMs pueden identificar partes semánticamente significativas del texto como nombres, títulos, ubicaciones, fechas, cantidades, identificaciones y más, incluso cuando la redacción varía. Eso los convierte en una herramienta poderosa para extraer datos de fuentes no estructuradas como PDFs, documentos de Microsoft Word, hilos de correo electrónico y publicaciones en redes sociales.

En lugar de expresiones regulares frágiles que se rompen cuando cambia el formato, un LLM puede generalizar a partir del contexto. Por ejemplo, "Sarah Whitfield, Directora de Experiencia del Cliente" es tanto un nombre como un título. La frase "$1,565 vencer antes del 1/12/2025" contiene una cantidad y una fecha. "Suite 400, 123 Main St., Austin, TX 78701" es una dirección. Aunque estos campos no estén etiquetados, el LLM es capaz de entender el significado detrás de este texto.

Se estima que entre el 80 y el 90 por ciento de los datos empresariales no están estructurados, lo que significa que tu organización casi con toda seguridad se encuentra sobre grandes cantidades de datos valiosos almacenados en documentos, bandejas de entrada y bases de conocimiento. La extracción basada en LLM te permite convertir esos datos en registros estructurados que puedes almacenar, buscar y analizar:

- Metadatos de tickets de los hilos de soporte
- Contactos de clientes por correo electrónico
- Cláusulas clave de los contratos
- Referencias de facturas

Y mucho más. A continuación se presenta una sencilla indicación para extraer la información de contacto del cliente del cuerpo de un correo electrónico. El prompt utiliza reglas básicas y especifica un formato de salida:

```
**Prompt** Given the following email:
		   Hi Jacob,

           Thank you for sending over the detailed proposal. I've reviewed it with our
           product and customer success leads, and we're excited about the project.
           
           Please put together an SOW for review so we can get things started. We'd like
           you to travel to our office in Denver, Colorado, for the kick off meeting.
       
           Thanks again for the thorough proposal. I'm looking forward to collaborating.
       
           Best regards,
       
           Sarah Whitfield
           Director of Customer Experience
           Acme Software Solutions
           sarah.whitfield@acmesoft.com · (312) 555-0182
       
           Extract the sender's name, location, and job_title, company, email, and
           phone_number.  Provide the results back in JSON format where each data element
           is an attribute.  Only return the JSON in your response.
**Response**  {"sender_name": "Sarah Whitfield", "location": "Denver, Colorado",
           "job_title": "Director of Customer Experience", "company": "Acme Software
           Solutions", "email": "sarah.whitfield@acmesoft.com", "phone_number":
           "(312) 555-0182"}
           Llama 3.2 3B (default settings)
```



El prompt especifica un formato de salida en JSON y, como puedes ver, recibimos el resultado que esperamos. El LLM es lo suficientemente inteligente como para extraer la información de contacto de Sarah de la firma del remitente con instrucciones mínimas. También se infiere que Sarah se encuentra en la oficina de Denver, Colorado, a partir del contenido del correo.

Fíjate que el LLM también capta nuestra pista para los nombres de los atributos. En el prompt, tanto job_title como phone_number se especificaban con guiones bajo. Aunque esto es útil para un prompt puntual que podamos usar nosotros mismos, no es suficiente para asegurar un formato JSON consistente para nuestro código. En [el capítulo 6](https://learning.oreilly.com/library/view/the-developers-guide/0642572230333/xhtml/ch6.xhtml#ch6), mejoraremos significativamente este prompt mostrando cómo asegurar un formato de respuesta consistente usando una salida estructurada.

Quizá pienses que Sarah en realidad no especificó su ubicación. ¡El LLM está haciendo una suposición! Dependiendo de tu caso de uso, puede que necesites instrucciones más específicas, descripciones de los campos que quieres extraer y/o ejemplos para asegurar una respuesta correcta. Hablaremos de todo esto en breve.

#### _**Eliminación de información personal identificable**_

Es importante que las organizaciones protejan nuestras PII, y en muchos casos está obligado por ley. Esto a menudo significa que cualquier PII debe ser redactada a menos que los datos se almacenen de forma extremadamente segura y cifrada.

> [!WARNING]
> 
> _Este ejemplo es el momento perfecto para reiterar la importancia de la privacidad y seguridad de los datos en lo que respecta al uso de LLM. Antes de enviar un prompt con información sensible a un LLM (y la PII es de las más sensibles), necesitas conocer el ciclo de vida de esos datos. Si usas una API alojada, asegúrate de entender cómo la empresa de alojamiento protege los datos de tus prompts y si esos datos se usarán en el entrenamiento de modelos. Si autoalojas un LLM, asegúrate de no registrar ni retener prompts de forma que pueda exponer información privada._

El texto no estructurado, como las transcripciones de chats de clientes, puede ser difícil de limpiar para obtener información personal. Las expresiones regulares y otras técnicas de análisis analizable son útiles para eliminar patrones conocidos (como los números de la Seguridad Social), pero a menudo pasan por alto casos límite y variaciones de formato. Un LLM puede complementar estas reglas identificando PII semánticamente equivalentes que la correspondencia de patrones puede pasar por alto. El siguiente prompt utiliza esa comprensión semántica para mejorar la cobertura de redacción de PII:

```
**Prompt**    Given the following customer chat, redact any personally identifiable
           information (PII) and replace it with a placeholder (for example, [name]).
           Redact the following data: name, phone number, email, and address.
       
           <chat>
           Agent: Hi Jacob, welcome to Customer First Bank. How can I help you today?
           Customer: I need to order new checks.
           Agent: Sure, I can help you with that. Can you verify a few things for me?
           I need your phone number and your address.
           Customer: Sure. My phone number is 214-555-1234 and my address is 1234 Fake
           St, Dallas, TX 75002.
           Agent: Perfect. I've ordered you a new set of checks that will be shipped to
           your address. You will receive a confirmation email at:
           jacob.orshalick@email.com.
           Customer: Thanks!
           </chat>
       
           Only return the <chat> content with the PII redacted.

**Response**  <chat>
           Agent: Hi [name], welcome to Customer First Bank. How can I help you
           today?
           Customer: I need to order new checks.
           Agent: Sure, I can help you with that. Can you verify a few things for
           me? I need your phone number and your address.
           Customer: Sure. My phone number is [phone number] and my address is [address].
           Agent: Perfect. I've ordered you a new set of checks that will be
           shipped to your address. You will receive a confirmation email at:
           [email].
           Customer: Thanks!
           </chat>
           Llama 3.2 3B (default settings)
```

Observa que el LLM entiende implícitamente nuestros marcadores de posición basándose en el único ejemplo proporcionado. También usamos un _delimitador_ XML `<chat>` para indicar el inicio y el final del contenido del chat. Los delimitadores son una excelente forma de ayudar a un LLM a identificar contenido específico dentro de tu prompt. Mostraremos más sobre los delimitadores más adelante en este capítulo.

#### _**Generación de datos sintéticos**_

Los LLM son geniales para generar datos sintéticos con fines de prueba o ejemplos. Un LLM puede generar datos sintéticos en una variedad de formatos como JSON, XML, CSV y SQL INSERT. Esta es una excelente manera de crear datos para lo siguiente:

- Entornos de desarrollo, pruebas o demostración
- Pruebas unitarias o de integración
- Escenarios de pruebas de carga
- Recrear escenarios de defectos sin necesidad de datos de producción

CSV es un formato de archivo sencillo de texto plano utilizado para almacenar datos tabulares, es decir, datos que pueden organizarse en filas y columnas, de forma similar a una hoja de cálculo o una tabla en una base de datos. En un archivo CSV, cada línea representa una fila de datos, y los valores dentro de esa fila están separados por comas. Este formato se utiliza ampliamente porque es fácil de leer para los humanos y para que los programas informáticos creen, lean y procesen.

En [el capítulo 7](https://learning.oreilly.com/library/view/the-developers-guide/0642572230333/xhtml/ch7.xhtml#ch7), verás ejemplos que cargan una base de datos vectorial con datos de productos. El siguiente prompt se utilizó para generar un archivo CSV con los datos del producto para esos ejemplos. Experimenta con variaciones del siguiente prompt para generar tus propios datos sintéticos:

```
**Prompt**    Generate a CSV file containing 30 rows of random product data. The CSV should
           have the following headers and columns, in this exact order:
       
           - product_id
           - title
           - category
           - description
           - price
       
           The first row must be the header. Each subsequent row should represent a
           unique product with a random but plausible value for each column:
       
           - product_id: A unique alphanumeric code (for example, E001 A002, etc).
           - title: A realistic product name.
           - category: Either "Electronics" or "Apparel".
           - description: A detailed, natural-sounding product description
           (2-5 sentences).
           - price: A realistic price as a decimal (for example, 199.99).
           
           The total number of rows (including the header) should be 31. Do not repeat
           any product_id. The output should be valid CSV format, with all fields
           properly quoted if necessary.
       
           Example header:
           product_id,title,category,description,price
       
           Begin generating the CSV below this line:

**Response**  I'll help you create a CSV file with random product data. First, I'll
           create a new file with the specified format.
       
           product_id,title,category,description,price
           E001,Wireless Noise-Canceling Headphones,Electronics,"Premium wireless ... ...
           A002,Classic Fit Denim Jeans,Apparel,"High-quality denim jeans with a ... ...
           ... ...
           Cursor (Agentic mode with Claude 3.5 Sonnet)
```

Aunque la mayoría de nuestros prompts se han ejecutado contra Llama 3.2 3B, este prompt se ejecutó usando un asistente de codificación con IA: Cursor (con el Modo Agente activado). Cursor estaba configurado para usar Claude 3.5 Sonnet como LLM.

Podrías ejecutar este prompt con cualquier LLM, pero un asistente de codificación con IA ofrece la ventaja de que el _artefacto products.csv_ puede generarse directamente en tu proyecto. También puedes pedir al asistente que escriba código que ingiera y utilice los datos. Puedes ver el artefacto _completo de products.csv_ en el repositorio de GitHub: _part3/vector_databases/products.csv_.

¿Qué otros casos de uso se te ocurren para los datos sintéticos? Sé creativo en función de las necesidades que ves en tu organización.

### **Persona Prompting**

Una _persona_ es una técnica de incitación que le da al LLM una identidad ficticia de personaje para asumir. La persona indica al LLM que responda y se comporte como si fuera esa persona en concreto.

Hagamos una pregunta que la mayoría de los LLM pueden responder a partir de sus datos de entrenamiento. Preguntaremos: "¿Puedes decirme cómo autenticarme en Gmail?" ([Figura 5-1](https://learning.oreilly.com/library/view/the-developers-guide/0642572230333/xhtml/ch5.xhtml#fig5_1)). La palabra _autenticar_ puede significar algo diferente dependiendo del contexto.

!["Eres un" lleva a dos opciones, "Desarrollador de software" o "Representante del Servicio de Ayuda de Google", ambas apuntando a un LLM.](https://learning.oreilly.com/api/v2/epubs/urn:orm:book:0642572230333/files/images/annot_page100_1.jpg)

_Figura 5-1: Las personas ayudan a dirigir la respuesta de un LLM sin instrucciones detalladas._

Experimentemos haciendo preguntas a Llama y viendo cómo interpreta la pregunta con cada persona. Primero, probemos la persona de desarrollador de software:

```
**Prompt**    You are a software developer. Can you tell me how to authenticate to Gmail?

**Response**  As a software developer, I can guide you through the process of
           authenticating to Gmail using OAuth 2.0, which is a widely used
           authentication protocol.
       
           **Prerequisites:**
       
           1. You have a Gmail account.
           2. You have a client ID (e.g., a web application or mobile app) registered
           on the Google Cloud Console.
           3. You have the necessary dependencies installed in your programming
           language of choice (e.g., Google API Client Library for Python).
       
       
           **Step 1: Register Your Application**
           ... ...
           Llama 3.2 3B (default settings)
```

Fíjate que Llama se centra en métodos de autenticación desde la perspectiva de un desarrollador de software. La palabra _autenticación_ significa que probablemente estamos interesados en acceder a una API segura. Ahora probemos con la personalidad del representante del servicio de ayuda de Google:

```
**Prompt**    You are a Google help desk representative. Can you tell me how to authenticate
           to Gmail?

**Response**  Hello! I'd be happy to help you with authenticating your Gmail account.

           To authenticate your Gmail account, follow these steps:
       
           **Method 1: Using a Web Browser**
           1. Go to the Gmail login page ([www.gmail.com](http://www.gmail.com)) in your
           web browser.
           2. Enter your Gmail address (username) and password in the required fields.
           3. Click the "Next" button.
           ... ...
           Llama 3.2 3B (default settings)
```

Fíjate en cómo el LLM ahora se centra en ayudar al usuario a iniciar sesión en la web de Gmail. Como representante del servicio de ayuda de Google, el modelo se da cuenta de que un usuario puede haber recibido un mensaje de _fallo de autenticación_ y está intentando averiguar qué hacer a continuación.

Las personas proporcionan instrucciones implícitas basadas en el preentrenamiento del modelo. Esto proporciona los siguientes beneficios:

- **Enmarcado de tareas más ajustado** Esto simplifica nuestros prompts al reducir la cantidad de instrucción explícita necesaria.
- **Reducción de costes** Cuanto más pequeños sean nuestros prompts, menos tokens se nos cobrarán.
- **Consistencia de la respuesta** Las personalidades fijas aseguran un tono y estilo consistentes durante las sesiones de conversación prolongadas.
- **Seguridad en la respuesta** Las identidades profesionales ayudan a restringir el alcance del dominio y a minimizar la producción riesgosa (más sobre esto en nuestra discusión sobre las barreras de seguridad en [el capítulo 6](https://learning.oreilly.com/library/view/the-developers-guide/0642572230333/xhtml/ch6.xhtml#ch6)).

Podemos decirle a un LLM que se comporte como médico, contable, crítico musical o ingeniero de software. Incluso podemos especializarnos: "Eres un ingeniero de integración de software contable con amplia experiencia integrando APIs de Quick-Books."

> [!WARNING]
> 
> _Ten especial cuidado al crear propuestas que utilicen perfiles profesionales como médicos, abogados o asesores financieros. Estos roles implican experiencia en campos regulados y pueden tener implicaciones legales o éticas si las respuestas del modelo se confunden con asesoramiento profesional. Deja siempre claro que la IA no es un experto con licencia y que sus respuestas son solo con fines informativos._

### **Preguntas de cero, uno y pocos disparos**

Hasta ahora, nos hemos centrado en prompts que usan instrucciones, contexto y consultas para generar la respuesta deseada. Como viste en nuestros elementos de prompt en [el capítulo 4](https://learning.oreilly.com/library/view/the-developers-guide/0642572230333/xhtml/ch4.xhtml#ch4), también puedes dar ejemplos de cómo quieres que responda el LLM.

Este enfoque de enseñanza por ejemplo es un tipo de _aprendizaje en contexto_. Los LLMs son de aprendizaje de cero disparo, de una sola vez y de pocos tiros. Hemos utilizado ejemplos de prompts sin disparo, pero podemos mejorar mucho la precisión de la respuesta proporcionando combinaciones ejemplo de prompt/respuesta. Esto se denomina incitación _de un solo disparo_ y _de pocas fotos_. Aquí tienes breves definiciones:

- **Indicación de disparo cero** Dependemos del preentrenamiento del modelo para generar una respuesta, recibiendo instrucciones adecuadas.
- **Prompting de un solo episodio** Enseñamos al modelo con un ejemplo en el prompt de cómo responder a las instrucciones.
- **Estímulo de pocos disparos** Enseñamos al modelo con múltiples ejemplos en el prompt de cómo responder a instrucciones, dadas las distintas situaciones.

Veamos ejemplos de prompts para ver qué tan útil puede ser esto en la práctica. Viste nuestro primer problema de clasificación en [el Capítulo 4](https://learning.oreilly.com/library/view/the-developers-guide/0642572230333/xhtml/ch4.xhtml#ch4), cuando pedimos a un LLM que nos diera el sentimiento de las publicaciones en redes sociales que etiquetaban a nuestra empresa. Un problema de clasificación es realmente que un modelo de IA aplique una etiqueta conocida a los datos de entrada. Empezaremos mejorando nuestro ejemplo de sentimiento:

```
**Prompt**    Tell me if the following statement is positive, neutral, or negative: Thank
           you @AcmeCorp! Can't wait to try this new shampoo! Sentiment:

**Response**  Sentiment: Positive
           Llama 3.2 3B (default settings)
```

El preentrenamiento del LLM es suficiente para darnos la idea, pero solo hemos dado instrucciones limitadas sobre cómo queremos que responda el modelo. Podría responder con "Sentimiento: Positivo", "Positivo" o "La afirmación es positiva." Todas estas son respuestas técnicamente válidas.

Podemos hacerlo mejor dando ejemplos al LLM de cómo queremos que responda. Intentémoslo de nuevo:

```
**Prompt**    <instructions>
           You are an expert on sentiment analysis. You will analyze a statement and
           respond with the sentiment as positive, negative, or neutral.
           </instructions>
       
           <examples>
           User: Thank you @AcmeCorp! This new shampoo has been great!
           Assistant: positive
       
           User: My order from @AcmeCorp never arrived and customer service wasn't
           helpful.
           Assistant: negative
       
           User: I wouldn't trust @AcmeCorp.
           Assistant: negative
           </examples>
       
           User: I'm an @AcmeCorp repeat customer. They ship fast and prices are great.
           Assistant:

**Response**  positive
           Llama 3.2 3B (default settings)
```

Basándonos en los ejemplos de prompt/respuesta que proporcionamos, el modelo sabía que queríamos solo la palabra minúscula positiva como respuesta. Utilizamos los roles comunes Usuario y Asistente al describir los ejemplos. Como verás en el próximo capítulo, los roles son especialmente útiles al llamar APIs directamente desde tu código.

Al utilizar un modelo preentrenado para la clasificación, la precisión depende de estos factores:

- Cómo se entrenó el modelo
- El número y variedad de ejemplos

Aquí, el modelo ya entiende el concepto de sentimiento. Los ejemplos que damos simplemente instruyen al modelo sobre cómo queremos que responda.

Supongamos que queremos identificar el departamento al que debe dirigirse un comentario en redes sociales. Esto podría ayudar a agilizar el proceso para resolver un comentario negativo enviando un ticket automático de soporte al departamento adecuado ([Figura 5-2](https://learning.oreilly.com/library/view/the-developers-guide/0642572230333/xhtml/ch5.xhtml#fig5_2)).

![Un comentario social entra en un LLM para su análisis. Si es negativo, se crea un ticket de soporte que se enruta a uno de los cuatro departamentos.](https://learning.oreilly.com/api/v2/epubs/urn:orm:book:0642572230333/files/images/annot_page104_1.jpg)

_Figura 5-2: Uso del análisis de sentimiento y la clasificación de departamentos para enrutar tickets de soporte_

Los departamentos de una empresa son de conocimiento interno. El LLM no ha recibido formación sobre estos departamentos ni sobre cómo deben dirigirse los comentarios a ellos. ¡No pasa nada! Esto es un problema de clasificación, y podemos crear otro prompt de pocas tomas que lo gestione:

```
**Prompt**    <instructions>
           You are an online customer feedback expert.
           Analyze the provided statement carefully and respond with the sentiment as
           positive, negative, or neutral.
           Specify the department the statement should be routed to:
       
           - customer_support: issues with customer support not being helpful
           - online_ordering: issues with ordering, website speed, or checkout process
           - product_quality: issues with product quality or description
           - shipping_and_delivery: issues with slow shipping or not receiving an order
           - other_off_topic: a department could not be identified
       
           Only respond with JSON that includes the sentiment and the department based
           on the <examples> provided.
           </instructions>
       
           <examples>
           User: Thank you @AcmeCorp! This new shampoo has been great!
           Assistant: {"sentiment"="positive","department"="product_quality"}
       
           User: My order from @AcmeCorp never arrived and customer service wasn't
           helpful.
           Assistant: {"sentiment"="negative","department"="customer_support"}
       
           User: I wouldn't trust @AcmeCorp.
           Assistant: {"sentiment"="negative","department"="other_off_topic"}
       
           User: I'm an @AcmeCorp repeat customer. They ship fast and prices are great.
           Assistant: {"sentiment"="positive","department"="shipping_and_delivery"}
       
           User: The @AcmeCorp website is so slow. Every time I've tried to order I
           can't even get through checkout.
           Assistant: {"sentiment"="negative","department"="online_ordering"}
           </examples>
       
           User: Don't trust @AcmeCorp. It's been weeks and my order was never even
           shipped!
           Assistant:

**Response**  {"sentiment": "negative", "department": "shipping_and_delivery"}
           Llama 3.2 3B (default settings)
```

El prompt comienza especificando una persona (experto en opiniones de clientes online). Como antes, indicamos que debe realizarse un análisis de sentimiento, pero también queremos que el departamento al que se dirija el comentario. Fíjate en que proporcionamos una lista de etiquetas válidas de departamento (como customer_support) y una descripción de los problemas que gestiona un departamento. Como antes, proporcionamos ejemplos de comentarios en redes sociales junto con la respuesta que esperaríamos.

Como puedes ver, el modelo aprende de nuestros ejemplos y genera una respuesta JSON adecuada. Sin duda podríamos analizar este JSON para automatizar la creación de un ticket de soporte, pero incluso con muchos ejemplos, el formato de respuesta no está garantizado. En el próximo capítulo, aprenderás cómo la salida estructurada nos permite garantizar un formato de respuesta (JSON) que es fácilmente consumible en nuestro código.

Si el modelo no está familiarizado con un tipo particular de etiqueta o tarea, puede que tengamos que proporcionar más ejemplos de los que razonablemente cabríamos en la ventana de contexto para enseñar correctamente al LLM. Este es un escenario en el que el ajuste fino tiene sentido. En [la Parte IV](https://learning.oreilly.com/library/view/the-developers-guide/0642572230333/xhtml/part4.xhtml), veremos un ejemplo de cómo aplicar etiquetas personalizadas a los correos entrantes.

### **DELIMITADORES EN TUS PROMPTS**

Quizá hayas notado que usamos XML para rodear las `<instrucciones>` y los `<ejemplos>` en nuestro prompt de ejemplo. Los delimitadores son una forma eficaz de separar contenido importante en tu prompt. Ayudan al LLM a identificar instrucciones, contexto y ejemplos.

No hay un delimitador estándar, pero XML, comillas y Markdown funcionan bien. Experimenta con el modelo que usas y el contenido que envías. Verás más ejemplos de delimitadores en el camino.

### **Incitación en cadena de pensamiento**

¿Alguna vez has notado que los LLMs a veces pueden resolver problemas difíciles pero luego fracasar completamente en algo sencillo, como contar el número de _r_ en la palabra _fresa_? Los LLM no razonan de forma natural como nosotros. Los humanos dividen los problemas en etapas automáticamente. Reflexionamos sobre cada parte antes de llegar a una conclusión. Los LLMs, por defecto, intentan saltar directamente a la respuesta final basándose en patrones que han visto.

Ahí es donde entra el impulso de la cadena de pensamiento (CoT). Con CoT, animamos al modelo a resolver el problema paso a paso, tal como haríamos en una pizarra en una entrevista de codificación. El modelo explica su razonamiento mientras resuelve el problema, lo que a menudo mejora la calidad de la respuesta. Esta es una de las técnicas de prompting más comunes utilizadas con agentes, ya que permite al modelo razonar las tareas necesarias para lograr un objetivo de usuario. Esto se discute más a fondo en [la Parte V](https://learning.oreilly.com/library/view/the-developers-guide/0642572230333/xhtml/part5.xhtml).

¿Cómo funciona esto? Recuerda que, a medida que el modelo predice los tokens, estos se reintroducen en el contexto para la siguiente predicción. Esto significa que el modelo básicamente se explica a sí mismo cómo resolver el problema antes de resolverlo.

Hay dos formas sencillas de activar CoT:

- Dile al modelo explícitamente: "Piensa paso a paso."
- Proporciona ejemplos que muestren el razonamiento en varios pasos dentro del prompt.

Ambos métodos guían al modelo hacia la razón en lugar de hacia la suposición. Aquí tienes algunas consideraciones sobre el tema de CoT:

- El razonamiento tiene un precio. Más tokens significan más latencia y mayores comisiones de uso.
- Algunos modelos son mejores razonando. Tu experiencia puede variar (tu experiencia puede variar).
- "Pensar en voz alta" conlleva riesgos. Consulta la advertencia que sigue.

Si has usado los últimos modelos con ChatGPT, has visto al modelo "pensar" antes de responder. Por ejemplo, los modelos de la familia GPT-5 de OpenAI (optimizados para tareas de razonamiento) pueden resolver problemas paso a paso incluso sin necesidad de una gran indicación. Cuando se requiere razonamiento, el modelo "piensa" durante su respuesta generando tokens de razonamiento antes de responder. Incluso puedes ampliar el "rascador" del modelo para ver estos tokens y cómo llegó a su respuesta. Esto puede ser útil si quieres verificar la respuesta del modelo.

Los costes ocultos de la incitación de CoT son mayor latencia y mayores costes de uso. Recuerda que las comisiones de uso con APIs alojadas se basan en el número de tokens de _entrada y_ salida. Más tokens generados para "pensar" en una respuesta significan más coste. Estos tokens adicionales también conducen a tiempos de respuesta más largos debido al mayor tamaño de la respuesta.

Un enfoque alternativo que puedes probar es la _cadena de tiro (CoD)._ CoD intenta superar los inconvenientes de CoT animando al LLM a redactar solo los pensamientos esenciales necesarios para el razonamiento. Es fácil de implementar con un indicador con "Piensa paso a paso pero mantén solo un borrador mínimo para cada paso, con cinco palabras como máximo." Esto puede lograr un rendimiento comparable, pero puede quedarse corto con tareas de razonamiento intensivas.

> [!WARNING]
> 
> _En producción, dejar que el modelo "piense en voz alta" con el aviso de CoT puede salir mal. El texto paso a paso podría filtrar accidentalmente datos sensibles, suposiciones internas o sesgos. Muchos sistemas usan CoT oculto, donde el modelo razona internamente (estilo "scratch pad") pero solo devuelve la respuesta final al usuario._

### **Encadenamiento por prompts**

El encadenamiento de prompts divide una petición compleja en una secuencia de pasos y prompts enfocados, pasando la salida de cada paso al siguiente. Al orquestar el modelo paso a paso, como componiendo pequeñas funciones en código, puedes obtener más modularidad, visibilidad y control a lo largo del flujo de trabajo.

Verás ejemplos de esta técnica de prompting a lo largo del libro a medida que seguimos construyendo soluciones más sofisticadas con LLMs. Aquí tienes algunas consideraciones clave y beneficios de usar el encadenamiento de prompts:

- **Subtareas con alcance** definido Cada prompt aborda un único trabajo (como clasificación, extracción, razonamiento o formato), por lo que el modelo nunca se enfrenta al problema completo de golpe.
- **Contratos explícitos de E/S** Defines el esquema de entrada y salida requerido para cada paso, facilitando validar, intercambiar o reutilizar prompts sin reescribir la cadena.
- **Depuración sencilla** Si la respuesta final es incorrecta, inspeccionas las salidas intermedias para localizar la etapa que falla en lugar de adivinar dentro de un prompt monolítico.
- **Reutilización de componentes** Por ejemplo, un aviso bien probado de "extraer campos de correo electrónico" puede incluirse tanto en el triaje de tickets de soporte como en la automatización de leads de ventas sin ningún cambio.
- **Menor carga de tokens y latencia** Cada prompt solo recibe los datos que necesita, recortando el uso de ventanas contextuales y acelerando la inferencia en comparación con un mega-prompt todo en uno.
- **Barandillas integradas** Inserta comprobaciones de validación (por ejemplo, confirmación de esquema JSON o puntuación de factualidad) entre pasos para detectar errores antes de que se acumulen en cascada.
- **Razonamiento transparente** Al presentar justificaciones intermedias, la cadena produce un rastro de auditoría que resulta invaluable para el ajuste, revisiones de cumplimiento y explicaciones a los interesados.

El encadenamiento de prompts permite una orquestación compleja, reutilización de prompts, mayor visibilidad en la ejecución y un mantenimiento más sencillo a largo plazo.

### **Consejos y mejores prácticas**

Como hemos mencionado, el prompting no tiene un enfoque único para todos. Las técnicas que hemos mostrado sirven como guía general, pero todos queremos llegar a un tema de trabajo más rápido. Los siguientes consejos pueden ayudarte a llegar a ello rápidamente.

#### _**Concéntrate en lo positivo, evita lo negativo**_

Da al modelo instrucciones claras y positivas en lugar de reglas de "No hagas _X_". Una redacción negativa obliga al modelo a detenerse y descubrir lo contrario de lo que quieres decir, lo que puede llevar a errores. Los comandos positivos son más cortos, más fáciles de comprobar y ayudan al modelo a seguir instrucciones de forma más consistente.

Por ejemplo, si queremos un formato de salida específico en nuestro ejemplo de sentimiento, no deberíamos decir: "No incluyas el sentimiento: en tu respuesta." Sería mejor decir: "Responde solo con el valor de sentimiento: positivo, neutral o negativo."

#### _**Collaborate with the Model on Your Prompt**_

We know that every AI model has built-in biases based on its training data. You can use this to your advantage. Start by asking the model how you could improve your prompt to get the specific result you want. You can prompt the model with input and output examples along with instructions to generate a useful prompt.

Si usas el modelo para una tarea de clasificación, empieza preguntando al modelo cómo etiquetaría los datos. La etiqueta que te da se basa en su sesgo de entrenamiento. Si puedes usar la etiqueta que proporciona o convertirlo a lo que necesitas, probablemente esperarás resultados más precisos. A esto lo _llamamos inclinarse hacia el sesgo_.

Pensando en nuestro análisis de sentimiento, podrías empezar proporcionando una afirmación y simplemente pidiendo al modelo que proporcione ese sentimiento sin _etiquetar_ _positivo, negativo_ o _neutral_. Mira con qué etiquetas responde para cada escenario.

#### _**Trata tus prompts como código**_

Los buenos ingenieros de software conocen el valor de un sistema de control de versiones (VCS). Una vez que algo funciona, incluso un pequeño cambio incremental, compromételo. Esto te da la libertad de refactorizar, experimentar o probar un enfoque completamente diferente porque siempre puedes volver a la versión funcional. Trata tus prompts de la misma manera. Puedes usar un VCS de tu elección (como Git) o una herramienta dedicada a la ingeniería de prompts.

#### _**Experimenta con variaciones de prompt**_

La forma en que formules un prompt puede cambiar completamente la calidad y precisión de la respuesta del modelo. Probar variaciones del mismo prompt te ayuda a encontrar la mejor estructura para tu tarea. También podrías probar diferentes modelos.

Puedes experimentar por tu cuenta o usar una herramienta como PromptLayer que te permite comparar varias variaciones de prompts una al lado de la otra para ver cuál produce la salida de mayor calidad para tu caso de uso específico. Aquí tienes algunos enfoques habituales para comparar y probar los prompts:

- **Pruebas A/B** Compara dos versiones de prompts cara a cara para ver cuál produce respuestas de mayor calidad.
- **Bucles de revisión humana** Resultados de muestra y que expertos del sector evalúen claridad, corrección y tono para detectar problemas que las métricas automatizadas pasan por alto.
- **Evaluación entre modelos** Envía el mismo prompt a varios modelos (como GPT-5 mini, Claude Haiku 4.5, Llama 3.2) para identificar qué LLM se ajusta mejor a tus necesidades.
- **Líneas base de regresión** Bloquea un par de prompt-modelo "conocido bueno" como referencia y reejecuta periódicamente para detectar desviación de calidad tras las actualizaciones.
- **Métricas automáticas de calidad** Si quieres automatizar métricas avanzadas de calidad de respuesta, puedes usar BLEU o ROUGE para similitud de texto, o precisión/F1 para tareas de clasificación, para puntuar resultados sin revisión manual.

Los detalles de estos enfoques están fuera del alcance de este libro, pero al menos es útil tener opciones para explorar.

### **Resumen**

Ahora tienes a tu disposición una variedad de técnicas de ingeniería rápida para crear instrucciones más claras y fiables. Estas técnicas son valiosas tanto si experimentas con ChatGPT, usas un asistente de programación con IA o incrustas prompts directamente en tu base de código. El capítulo comenzó con indicaciones de instrucciones, demostrando cómo comandos concisos y positivos pueden impulsar tareas como la extracción de datos, la redacción de PII y la generación de datos sintéticos sin analizadores hechos a mano ni expresiones regulares frágiles.

A continuación, exploramos el prompting de persona, donde asignar un rol (como desarrollador de software o representante de help-desk) reduce implícitamente el alcance del modelo, establece el tono y reduce la sobrecarga de tokens. Partiendo de esa base, el capítulo introdujo técnicas de cero, uno y pocos disparos. Al incrustar ejemplos en el prompt, puedes enseñar al modelo etiquetas o formatos de respuesta específicos de dominio, mejorando la precisión respecto a las líneas base de disparo cero. Has visto cómo esto puede ser especialmente útil para tareas de clasificación como el análisis de sentimiento.

Para razonamientos complejos, el incitamiento de CoT anima al modelo a pensar paso a paso, intercambiando costes más altos de tokens por una lógica más transparente. Una alternativa, CoD, sigue razonando de forma concisa para limitar la latencia y el gasto. También aprendiste cómo el encadenamiento de prompts refleja la composición de funciones en el código, mejorando la modularidad, la reutilizabilidad y la auditabilidad. Los sistemas se basan en este patrón para orquestar pipelines RAG, agentes y más ([véase el Capítulo 8](https://learning.oreilly.com/library/view/the-developers-guide/0642572230333/xhtml/ch8.xhtml#ch8)).

El capítulo cerraba con las mejores prácticas prácticas: enmarcar instrucciones positivas, iterar de forma colaborativa con el modelo, versionar tus prompts como código y variantes de prueba A/B o benchmark para evitar la deriva silenciosa de calidad. Juntas, estas estrategias forman un conjunto de herramientas para convertir los LLMs en componentes predecibles y de calidad productiva.
