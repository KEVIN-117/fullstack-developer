We’ve made progress by enabling the AI to search the internet, allowing it to provide more-dynamic responses. However, this still keeps the AI tethered to publicly available information, essentially operating within an expanded chat interface. True agency requires the ability to interact with resources an LLM typically cannot access directly, such as a locally hosted database containing private data.

This is precisely where the concept of tools becomes essential, and the strength of an agent framework becomes apparent. These frameworks enable developers to construct custom tools that act as secure pathways, granting the LLM controlled access to specific data sources and functionalities it would otherwise be unable to utilize.

For instance, we could build a tool that allows the LLM to query a local database for specific insights or interact with internal systems to perform designated actions. Agent frameworks streamline the creation of these vital connections, effectively extending the LLM’s reach beyond the limitations of a standard chat interface and unlocking genuine autonomous capabilities.

### **Building a Tool**

Let’s build a tool to highlight the flexibility that it brings to the agent flow. We want to find out the current stock price and save it into a file. Let’s modify the instruction as follows:

Find the latest stock price for Apple, Google and Amazon.
Convert that into a table and save it to a file.

In contrast to publicly accessible data like stock prices, the agent inherently lacks the capability to perform actions such as saving information to a file. This requires a distinct set of skills and permissions that are not part of a standard agent’s or LLM’s core functionality. To enable the agent to interact with the filesystem and perform such operations, we need to equip it with specific tools. Agent frameworks, such as Hugging Face smolagents, provide the necessary infrastructure to create and seamlessly integrate these custom tools with the LLM, extending its operational scope beyond mere information retrieval.

To give your AI agent new abilities tailored to your specific needs, you can create custom tools by writing standard Python functions. The @tool decorator is a convenient way provided by smolagents to turn one of your functions into a tool that the agent’s LLM can understand and use. By adding @tool right above your function definition, you register it and make its purpose and parameters (often described in the function’s docstring) available for the agent’s reasoning process, allowing the agent to decide when and how to call your custom function to help solve a task.

Let’s look at how to make a tool that can save data to a file:

   --snip--
➊ @tool
➋ def save_file(data: str) -> None:
    ➌ """
       Save the data to a file

       Args:
           data: The data to save to the file

       """
    ➍ with open("investments.txt", "w") as f:
           f.write(data)

    agent = CodeAgent(
    ➎ tools=[saveFile],
       model=model,
       add_base_tools=True
   )

   --snip--

By adding the @tool decorator ➊, we convert the save_file function ❷ into a tool that saves the input data into a file ➍. This tool definition is then provided to the agent ➎. The agent is able to understand what the tool is capable of doing by using the docstring that we defined ➌.

### **Writing Effective Tools**

When writing your own custom tools, here are some best practices to follow to ensure that your agent’s LLM can understand and use these tools effectively:

- Use a descriptive name for your tool function. This name helps the agent’s LLM understand exactly what the tool does (for example, save_file).
- Always include precise type hints for all function arguments and the function’s return value. These type hints are essential for the agent framework to correctly interpret the tool’s expected inputs and outputs.
- Write a comprehensive docstring for your tool function. This description serves as the primary instruction manual for the agent’s LLM, explaining the tool’s purpose and how to use it.
- Within the docstring, clearly describe what each input parameter is for. Explain these arguments in plain language so the LLM knows what information it needs to provide when calling the tool.

### **Building Reusable Tools**

By this stage, you should recognize the significant power that tools bring to the capabilities of AI agents. The ability to equip an agent with specific functionalities opens up a world of possibilities, allowing it to interact with its environment and access information in ways that would otherwise be impossible. As you plan on expanding the capabilities of your agents, integrating more and more specialized tools becomes a natural progression.

However, this expansion naturally leads to a concern regarding reusability. The prospect of having to re-create or duplicate existing tools every time you build a new agent presents a significant inefficiency. Imagine having to rewrite the same database query tool or web-scraping function for each new project. This not only consumes valuable development time but also makes maintaining and updating these tools a cumbersome process across multiple agents.

Fortunately, effective strategies can address this challenge of tool reusability. One approach involves building all the necessary tools directly within the scope of each individual agent, which is inefficient. Alternatively, you could bundle all your commonly used tools within a reusable library, which can then be imported and utilized across various agent projects.

However, another elegant solution exists: the _Model Context Protocol (MCP)_, which offers a more integrated and potentially more efficient way to manage and share tools among different AI agents.

### **Model Context Protocol**

You already understand that AI agents represent a step forward in making AI proactive and capable of complex tasks. You also know that these agents often need to utilize external tools—whether to access real-time data, perform calculations, or interact with other software services—to achieve their goals. The challenge then becomes, how do we create a reliable and standardized way for any agent to discover, understand, and communicate with any necessary tool? Writing custom code for every single agent-tool pair would quickly become unmanageable.

This is precisely the problem that the MCP _([https://modelcontextprotocol.io](https://modelcontextprotocol.io/))_ is designed to solve. MCP proposes a standard set of rules and a common language that not only enables AI agents to seamlessly integrate with and leverage external tools and data sources, but also helps define how tools and data sources must be defined.

Instead of needing unique connectors, both the agent and the tool can adhere to the MCP standard, enabling them to “speak the same language.” This protocol acts as a bridge, ensuring that an agent’s request for information or action is formatted in a way that a compliant tool can understand, and that the tool’s response is delivered back intelligibly to the agent.

Operating on a familiar client-server model, MCP positions the AI agent as the client initiating the communication and the tool or data source as the server responding to requests. The protocol layer handles the technical details of this interaction—managing the flow of messages, linking specific requests to their corresponding responses, and ensuring that the conversation follows established patterns. This standardization is critical; it means developers building agents don’t need to worry as much about the specific technical quirks of every single tool they might want to connect to, and vice versa.

#### _**MCP Concepts**_

Now that you understand the role MCP plays in standardizing the way AI agents communicate with external tools and data, let’s look at the building blocks. To grasp how MCP achieves this seamless interaction, it’s essential to understand its core components, all operating within its _client-server architecture_:

- **MCP hosts** The primary AI applications (like an LLM-powered desktop app or an IDE) that initiate and manage connections within the MCP ecosystem.
- **MCP clients** Embedded within the host application, clients maintain dedicated one-to-one connections with MCP servers. They act as the intermediary, facilitating communication between the host/LLM and the servers.
- **MCP servers** External programs or services that provide specific capabilities and information to clients. They are responsible for exposing various forms of context and functionality that the LLM needs.

#### _**MCP Components**_

Within this architecture, servers offer three types of components to clients:

- **Tools** Executable functions or capabilities that your MCP client (and by extension, the LLM) can invoke. Tools allow the LLM to interact with external systems, perform actions, or access data that was not part of its original training. Think of them as callable functions for the AI.
- **Resources** Data sources or dynamic content generators that your MCP client can read from. Resources provide information or files that the LLM can access and incorporate into its understanding or responses, without necessarily executing an action.
- **Prompts** Enable servers to define and share reusable prompt templates and structured workflows. They offer a powerful way to standardize common LLM interactions, allowing clients to easily surface these predefined instructions to users and LLMs.

#### _**MCP Transport Protocols**_

Finally, transports are the underlying mechanisms that enable communication between MCP clients and servers, handling the way messages are actually sent and received. The protocol supports two types of transports:

- **Standard input/output (stdio)** Facilitates communication through standard input and output streams. It’s especially useful for local integrations where clients and servers run on the same machine, often via command line processes.
- **Streamable HTTP** Leverages standard HTTP. Clients send requests using HTTP POST, while servers can send messages back to clients via server-sent event (SSE) streams, enabling real-time, bidirectional communication over the web.

### **Building an MCP Server**

MCP servers are now available for nearly every technical domain, from databases and payment systems to search and observability. These servers act as a powerful layer that allows an AI agent to have a “conversation” with an otherwise highly technical tool.

This capability is profound: Users can interact with complex systems without needing to fully understand their underlying mechanisms. The true power of MCP is demonstrated when a nontechnical user, like a manager, can simply ask AI the following:

**Prompt**    What was my AWS spend for the last three quarters,
           and plot that against the number of servers running?

The AI can use the appropriate Amazon Web Services (AWS) MCP servers to fetch billing data and server history, then stitch the information together and present the result. This transforms a task that previously took hours (manually logging in, navigating complex consoles, and querying multiple sources) into a request that is executed in minutes. The manager doesn’t need to log into AWS or understand its intricate navigation paths.

### **Your First MCP Server**

Let’s understand these concepts better by building our own MCP server with custom capabilities to AI-assisted applications. We will start with a simple application to illustrate the concepts.

Here’s an outline of the steps we’ll be taking:

1. Build an MCP server that exposes four operations (add, subtract, multiply, and divide) with a small twist in how each of these operations are done.
2. Test the MCP server via Postman.
3. Integrate with Claude Desktop to make the AI use this MCP server.

The code was built and tested on Python 3.13.7 and FastMCP 2.12.4.

#### _**Building a Special Calculator**_

One of the ways to learn a new concept is to build something simple and silly. So we will build a special calculator with four operations: add, subtract, multiply, and divide.

Given two numbers num1 and num2,

- add(num1, num2) will do the operation as num1 + num2 + num2
- subtract(num1, num2) will do the operation as num1 – num2 – num2
- multiply(num1, num2) will do the operation as num1 × num2 + num2
- divide(num1, num2) will do the operation as num1 / num2 / num2

Here’s how to get started:

--snip--
from fastmcp import FastMCP

mcp = FastMCP(
 ➊ name="My Special Calculator",
 ➋ instructions="""
    This is a special calculator that does some special things.
    It can add, subtract, multiply, and divide in some special ways.
    """,
)
--snip--

We are importing the core class and creating an instance of FastMCP. When we create an MCP server, we have to give it a name that we and the AI can use to identify it. We do this by using the name parameter ➊.

Treat the name parameter just as you would a critical variable or function in your code. You wouldn’t name a function f() and expect a teammate to understand what it does. The same principle applies here. The AI uses this name as a _primary instruction_ to understand its fundamental purpose.

A vague name like mcp_server forces the AI to guess. A descriptive name like PayrollReportGenerator or ImageAnalysisBot gives the AI (and your future self) vital context before it even processes a single instruction.

After defining the name, we use the instruction parameter ➋. This parameter is the public documentation for our server. Think of it as the _README.md_ file or the help text that a user sees when they first discover our server.

#### _**Defining Custom Tools**_

Now that we have created an instance of our MCP server, let’s start defining the tools and build the logic that goes with it:

--snip--
@mcp.tool
def add(num1: int, num2: int) -> int:
    return num1 + num2 + num2
# ... (similar functions for subtract, multiply, divide)
--snip--

The four functions (add, subtract, multiply, and divide) are the custom tools the agent can use. The decorator @mcp.tool is provided by the FastMCP library. It registers the function immediately following it (for example, add) as a tool available to the agent.

The type hints for these functions (num1: int, num2: int, -> int) are essential. The FastMCP framework uses them to generate a JSON schema description of the tool’s inputs and outputs. The LLM then uses this schema to correctly structure its arguments when it decides to call the tool.

#### _**Running the MCP Server**_

So far, we have defined the MCP server and the tools that are exposed by the server. Next we need to define the transport protocol or the underlying mechanisms that enable communication between MCP clients and servers. We will use the stdio transport protocol in this example, which is set by default when you call the mcp.run method on your FastMCP instance:

--snip--
if __name__ == "__main__":
    mcp.run()
--snip--

For the complete, runnable example, refer to the folder _part5/building -an-mcp-server_ at the book’s GitHub repository: _[https://github.com/jorshali/developers-guide-to-ai](https://github.com/jorshali/developers-guide-to-ai)_.

We have created our first MCP server. You can run the server as follows:

         python mySpecialCalculator-mcp-server.py

**Output**  --snip--

         --snip--

The output will confirm the name and the transport protocol used by your MCP server.

#### _**Testing with Postman**_

Now that your MCP server is built, you can test its functionality with Postman _([https://www.postman.com](https://www.postman.com/)_), a popular API testing tool. Postman provides a dedicated interface for interacting with MCP servers, making it easy to verify that your tools are exposed and functioning correctly. Here are the steps:

1. Open Postman and create a new request. Instead of a typical HTTP request, create a new request and select the **MCP** protocol type.
2. Configure the server command. In the Postman interface, you’ll see a field to enter the command to run your MCP server. Select the **stdio** transport protocol. Enter the full path to your server’s executable script.

For instance, here’s how we ran it on our system:

path/.venv/bin/python
path/mySpecialCalculator-mcp-server.py

As you can see, we’re not using the system-wide Python to run the server. We’re referring to the isolated Python interpreter within our project’s virtual environment.

Using the virtual environment’s Python solves package issues because it forces your system to use the isolated Python interpreter within your project’s virtual environment. This environment contains the specific versions of the packages your project needs, which avoids conflicts with the system-wide Python’s global packages.

To connect and explore tools, click the **Connect** button. If your server starts successfully, Postman will establish a connection, and you should immediately see a list of the tools your server exposes (for example, the four operations).

To interact with tools, click any of those listed. Postman will automatically generate a form based on the schema you defined for that tool (its expected inputs). Fill in the required values in the form fields and click **Run**. You will see the response from your MCP server, confirming your tool’s functionality.

### **MCP Transports**

Earlier, we looked at how MCP transports work, noting that the protocol relies on either stdio or HTTP to bridge the gap between clients and servers. The specific server we built at the start of this chapter utilized stdio, a choice that limits communication to processes running locally on the same machine. While efficient for local development, this direct connection means the agent and the tool must share the same physical or virtual environment.

This setup is great for tools meant just for you, running locally. The downside? It’s limited to a single user and can’t be shared over a network. To make your server network accessible, you must use HTTP transport.

Switching to HTTP turns your MCP server into a web service. It can then be hosted anywhere—in the cloud or on a dedicated remote server. This is the right choice when you need a single, centralized server that multiple clients can connect to from anywhere. You can convert the MCP server from stdio to HTTP transport by modifying the mcp.run call to the following:

--snip--
mcp.run(transport="http", host="0.0.0.0", port=8000)
--snip--

As of this writing, Claude Desktop doesn’t support HTTP transport for MCP servers.

### **Building Tools with Complex Schemas**

The MCP server we’ve built so far was a great proof-of-concept. Its tools used simple, primitive inputs (num1: int, num2: int) and returned equally simple outputs.

This is pretty far from reality. We often deal with complex, structured messages for both inputs and outputs. To handle this, we need a reliable mechanism to validate the data we get from the AI. We must also ensure that our tool’s response conforms to a predictable output schema.

With this, we can build even more complex custom MCP servers, like your own expense manager. Here’s part of the My Expense Manager MCP server that exposes the add_expense tool:

   --snip--
➊ class Expense(BaseModel):
       _id: Optional[ObjectId] = None
       description: str = Field(description="The description of the expense")
       amount: float = Field(description="The amount of the expense")
       date: Optional[datetime | str] = Field(
           description="The date of the expense", default=None)

   @mcp.tool(
       name="add_expense",
       description="Add a new expense",
   )
➋ async def add_expense(data: Expense) -> ObjectId:
       try:
           print(data.model_dump())
           result = await expenses.insert_one(data.model_dump(mode="json"))
           print(f"Added expense: {result.inserted_id}")
           return result.inserted_id
       except Exception as e:
           raise Exception(
               "Unable to add the expense due to the following error: ", e)
   --snip--

We have defined a Pydantic model Expense ➊ and used that as the input for the tool add_expense ➋.
