### **RAG VS. TOOL USE**

You may be wondering how the model knows it needs more information. Admittedly, we’re simplifying here. When you prompt ChatGPT, you’ll often see a brief “thinking” step. Behind the scenes, the model is given your prompt along with a set of tools, each with a name, input schema, and guidance on when and how it should be used.

One of those tools provides the ability to search the web. If the model infers that your question requires more current or external knowledge, it can choose to call that tool, fetch context, and then generate an answer using the information it found. That retrieval-then-generation sequence is a RAG pipeline.

Note that some systems perform retrieval before the model is called at all, and retrieval can occur once or be interleaved with generation. Tools are a more advanced concept we’ll return to in [Part V](https://learning.oreilly.com/library/view/the-developers-guide/0642572230333/xhtml/part5.xhtml) when we discuss agents.

### **Understanding the RAG Pipeline**

When it comes to RAG, you’ll often hear people refer to the RAG pipeline. The _pipeline_ in RAG is simply the end-to-end flow that takes your raw data and turns it into an LLM-powered answer.

[Figure 8-6](https://learning.oreilly.com/library/view/the-developers-guide/0642572230333/xhtml/ch8.xhtml#fig8_6) is a representation of the components within the RAG pipeline we will be building.

![Documents are chunked, embedded, and stored in a vector database. A user query retrieves chunks that augment a prompt template and are sent to an LLM.](https://learning.oreilly.com/api/v2/epubs/urn:orm:book:0642572230333/files/images/annot_page197_1.jpg)

_Figure 8-6: Components of the RAG pipeline we are building in this chapter_

A typical RAG system consists of several distinct stages, each acting as a filter in the pipeline. We’ll start with the _data ingestion pipeline_. This pipeline loads our data into a vector database for retrieval:

- **Retrieve raw data and chunk** We gather the necessary documents (README) and break them into manageable pieces (document _chunks_) so we can search the documentation efficiently.
- **Embed and index** Each document chunk will then be turned into a vector embedding by an embedding model. Those embeddings will be stored in a vector database, which uses indexing for highly performant retrieval.

Once we’ve loaded a vector database, we’ll shift our focus to the _inference pipeline_. Here we combine our data with an LLM to generate a grounded response:

- **Retrieval** When a user query is received, we will take the query and run a similarity search to pull back the top _k_ most relevant document chunks.
- **Augmentation** Prompt templates (which include some static system-level instructions) will be used to merge those document chunks and the user’s original query.
- **Generation** The populated prompt is then sent to an LLM, and the response is generated (and usually streamed back).

You will see some architectural variants of RAG later in the chapter. Every RAG variant (such as naive, cached, agentic, hybrid, or graph-based) simply tweaks one or more of these pipeline stages—for example, changing the way you chunk and index, retrieve, augment, or orchestrate the generation step.

Now that you understand the components of our pipeline, we can start building.

#### _**Understanding Chunking Basics**_

Choosing a good text-chunking strategy is key to building a reliable RAG solution. When chunking text, we have several strategies to choose from. The overall goals of a chunking strategy are as follows:

- Accurately capture the meaning of text within our embeddings
- Ensure that enough contextually relevant information is included
- Keep token length within the embedding model request limit

Choosing a chunking strategy is a balancing act, but we have many useful strategies we can experiment with for our specific use case.

Chunking provides the following benefits:

- Smaller chunks of text capture fewer topics or ideas.
- Embeddings end up with more focused meaning (improving retrieval accuracy).
- We can avoid hitting token limits while generating embeddings.
- Chunked query results mean fewer, more relevant tokens sent to an LLM.

Using the LangChain text-splitting utility simplifies chunking. This utility provides multiple chunking strategies, but let’s start by looking at CharacterTextSplitter, which is the most basic:

   from langchain_text_splitters import CharacterTextSplitter

   text = """Our system requires multi-factor Authentication (MFA). This helps
   to keep your account secure. This step-by-step guide will walk you through
   the MFA setup."""

➊ splitter = CharacterTextSplitter(
     separator="",
     chunk_size=70,
     chunk_overlap=20
   )

   chunks = splitter.split_text(text)

   print("Chunks:\n")

   for idx, chunk in enumerate(chunks):
     print(f"{idx + 1}:  {chunk}\n- character count: {len(chunk)}")

Here, we create a CharacterTextSplitter and provide it with the following parameters: separator, which is the separator to split on (for example, character, period, or newline), chunk_size, which is the number of characters that will be included in each chunk, and chunk_overlap, which is the number of characters that should overlap between each successive chunk ➊.

We have specified that each chunk should be split on any character ("") and should include no more than 70 characters. The following output results from running the preceding code:

Chunks:

1:  Our system requires multi-factor Authentication (MFA). This helps to k
- character count: 70
2:  FA). This helps to keep your account secure. This step-by-step guide w
- character count: 70
3:  step-by-step guide will walk you through the MFA setup.
- character count: 55

The CharacterTextSplitter generates an array with three chunks of text. Each chunk is less than or equal to 70 characters, with exactly 20 characters of overlapping text, as shown in [Figure 8-8](https://learning.oreilly.com/library/view/the-developers-guide/0642572230333/xhtml/ch8.xhtml#fig8_8).

![A text string divided into three overlapping chunks, with brackets showing the overlap regions between Chunk 1 and 2 and between Chunk 2 and 3.](https://learning.oreilly.com/api/v2/epubs/urn:orm:book:0642572230333/files/images/annot_page201_1.jpg)

_Figure 8-8: Visualization of chunking with_ CharacterTextSplitter _and_ chunk_overlap

Overlapping text between chunks can help do the following:

- Reduce the probability that ideas are cut in half between sequential chunks
- Create semantic similarity within sequential chunks

You will have to experiment with your text to determine the best settings, but be aware that overlapping text can lead to redundant information and an increase in storage requirements.

Notice that the text splits right in the middle of a word if necessary, which ensures that we do not exceed our character limit. While this strategy is useful for understanding, it’s not recommended because of its naive approach. In the best case, a word split like this is useless to our embedding model. In the worst case, the word is split in a way that leads to incorrect meaning.

In practice, we would want to use a smarter chunking strategy. Let’s have a look at the strategies available to us.

#### _**Choosing a Chunking Strategy**_

Here are the possible strategies with example implementations from LangChain:

- **Fixed size** Most basic approach. Naive implementation that splits text based on a character count. Generally not recommended but good for understanding.
- **Recursive** Best general text splitter to start with. Accounts for text structure by splitting on common separators (for example, paragraphs, newlines, and spaces). Chunks are variable size, but we have a better probability of capturing more complete ideas.
- **Document based** Best for specific document types. Splitter that considers the document type (such as Markdown, PDF, or HTML). Essentially the same as recursive, but uses custom split characters based on the type of document being split.
- **Semantic** For a more custom approach. Attempts to build chunks using sentence embeddings to identify semantically related content. Requires an embedding model. Generally slower and requires more compute resources than the previous strategies.
- **Agentic** More experimental than production-ready. Uses an agent to build semantic chunks. At the time of writing, this is currently slow and doesn’t scale well, but you can experiment with options for your use cases (see [Part V](https://learning.oreilly.com/library/view/the-developers-guide/0642572230333/xhtml/part5.xhtml) for more on agents).

Recursive chunking is usually a great starting point for unstructured text. The LangChain RecursiveCharacterTextSplitter splits text based on a specified number of characters but looks for _semantically meaningful_ stopping points. For example, RecursiveCharacterTextSplitter splits at the following characters by default:

- "\n\n" Double newline indicating a new paragraph
- "\n" Single newline, indicating a break in the text
- " " Spaces
- "" Any other character

The RecursiveCharacterTextSplitter starts by splitting on a paragraph ("\n\n") and, if the chunk is too big, continues to look recursively for the next separator until we reach our desired chunk size. This means the chunks may end up being variable in size but have a better chance of capturing complete ideas.

Let’s see how this approach compares to CharacterTextSplitter shown previously:

from langchain_text_splitters import RecursiveCharacterTextSplitter

text = """Our system requires multi-factor authentication (MFA). This helps
to keep your account secure. This step-by-step guide will walk you through
the MFA setup."""

splitter = RecursiveCharacterTextSplitter(
➊ separators=["\n\n", "\n", ".", " ", ""],
   chunk_size=70,
➋ chunk_overlap=0,
   keep_separator='end'
)

chunks = splitter.split_text(text)

print("Chunks:\n")

for idx, chunk in enumerate(chunks):
  print(f"{idx + 1}:  {chunk}\n- character count: {len(chunk)}")

We’ll worry about specific settings with RecursiveCharacterTextSplitter shortly, but notice we include a period as a separator ➊ and eliminate the chunk_overlap ➋. This results in the following output:

- character count: 55
2:  This helps to keep your account secure.
- character count: 39
3:  This step-by-step guide will walk you through the MFA setup.
- character count: 60

The chunks are now complete sentences, which is much more meaningful for embedding. ### **ESTIMATING CHUNK SIZE FOR EMBEDDING**

Recall that embedding models have an input token limit, just like LLMs. The mxbai-embed-large model has a 512-token limit. A common rule of thumb is that 1 token is equal to about 4 characters. That means our token limit roughly translates to about 2,048 characters.

Since RecursiveCharacterTextSplitter measures in characters, our 1,500-character limit stays safely under that estimate and works well with our documentation. If you want a hard token cap, use from_tiktoken_encoder or from_huggingface_tokenizer, which enforce chunk_size in tokens rather than characters. You can refer to [Chapter 4](https://learning.oreilly.com/library/view/the-developers-guide/0642572230333/xhtml/ch4.xhtml#ch4) for more on counting tokens. Feel free to try these tokenizers on your own.

Just remember, chunk sizing requires experimentation with your source text. Depending on your use case, specifying the maximum number of tokens may result in embeddings that include too many concepts and yield poor query results. If you aren’t getting the semantically relevant results you want, a smaller chunk size may help.

As you saw in [Chapter 7](https://learning.oreilly.com/library/view/the-developers-guide/0642572230333/xhtml/ch7.xhtml#ch7), Chroma provides convenient wrappers around embedding providers to simplify integration. OllamaEmbeddingFunction wraps Ollama’s embeddings API; we just have to specify the URL to our local Ollama server (_http://localhost:11434_) and the name of our embedding model (mxbai-embed-large) ➊.

We then initialize a Chroma Client ➋ and create a collection for our embeddings named examples_readme ➌. We configure ollama_embedding_function as the function that will be called for creating an embedding when a new record is added to our collection or a query is performed. As in [Chapter 7](https://learning.oreilly.com/library/view/the-developers-guide/0642572230333/xhtml/ch7.xhtml#ch7), we’re using Chroma’s ephemeral client, which runs an in-memory server.

Now we can use these code snippets to create a class that loads our vector database and performs queries:

 class DocumentVectorStore:
➊ def __init__(self, document_text: str):
     ollama_embedding_function = OllamaEmbeddingFunction(
       url="http://localhost:11434",
       model_name="mxbai-embed-large"
     )

     client = Client()

  ➋ self.collection: Collection = client.create_collection(
       name="examples_readme",
       embedding_function=ollama_embedding_function,
     )

     splitter = RecursiveCharacterTextSplitter.from_language(
       language="markdown",
       chunk_size=1500
     )

  ➌ chunks = splitter.split_text(document_text)

  ➍ self.collection.add(
       documents=chunks,
    ➎ ids=[f"doc{chunk_idx + 1}" for chunk_idx, chunk in enumerate(chunks)]
      )

➏ def query(self, question: str, n_results=3) -> List[str]:
     results = self.collection.query(
       query_texts=[question], n_results=n_results)

     return results.get('documents')[0]

#### _**Improving Trust with Citations**_

You’ve seen how generative AI tools, like ChatGPT, can provide citations for reference. Users don’t, and shouldn’t, trust a response just because it sounds confident. They trust evidence. In a RAG setup, that means attaching a clear source (citation) to the response. We need to be able to answer “Where did this information come from?”

During ingestion, we can capture data points like these:

- The document title
- The author or source site
- A direct link to the document
- The date the document was accessed
- A precise location of text (like page, section, or line)

For some responses, we may need to place the citation right next to a specific piece of text so the reader can check it without hunting. For longer responses, we may group the citations instead of linking every sentence.

Citations can also improve model behavior. When the model must back up its output, it tends to quote and summarize real text rather than guessing, which reduces hallucinations.

### **Advanced RAG Topics**

Think of what we’ve built so far, often called naive RAG, as your launchpad into retrieval-augmented generation. It’s simple, it works, and it’s perfect for getting started. But as your needs grow, you might hit its limits. In the rest of this chapter, we’ll dive into advanced techniques to supercharge your pipeline and unlock new capabilities. #### _**Alternative Indexing and Retrieval Strategies**_

As we mentioned, a variety of chunking strategies are available to you. We have to strike a balance when chunking text. Small chunks tend to work well when questions are more precise but tend to struggle with broad questions. Large chunks tend to lack enough detail for specific queries. This is very dependent on your specific use case. The strategies we’ll talk about here give you some additional options to consider:

- **Parent-child (two-level) retrieval** In many search tasks, you want the speed of matching against small snippets yet the return of enough surrounding text for the model to answer well. A generic fix is a two-level approach: Create embeddings for fine-grained “child” chunks for similarity search, but when one matches, pull back its larger “parent” section, perhaps the full page or chapter, to give richer context. At query time, the retriever searches the children, then stitches in the parent documents before handing them to the LLM. The result is a light index that still delivers larger, coherent passages to your prompt.
- **Multi-vector retrieval** Sometimes one embedding per document can’t capture every way a user might ask about it. A generic remedy is to create multiple vector embeddings for the same source—titles, summaries, headings, and sentence-level chunks. In this way, any of those embeddings can trigger a hit. You store several embeddings, each tagged with the same document ID. When a query comes in, the retriever checks all embeddings, aggregates the matches that point to the same original document, and returns the assembled content. This lets broad overview queries match high-level embeddings, while detailed questions still latch onto sentence-sized ones, all without inflating your prompt with unrelated text.

As an example, let’s think back to our startup team and their AI support agent problem. As their number of support articles grew, their similarity searches were struggling to find the right content because their embeddings simply weren’t focused enough. At the same time, for an LLM to generate a proper response to a support question, it likely needs an entire how-to article.

This would be a good fit for parent-child (two-level) retrieval. This is generally achieved by storing the ID of the parent document in the metadata of each chunk (see [Figure 8-10](https://learning.oreilly.com/library/view/the-developers-guide/0642572230333/xhtml/ch8.xhtml#fig8_10)).

![A vector database holds article chunks tagged with parent IDs that reference complete articles stored in a separate document store.](https://learning.oreilly.com/api/v2/epubs/urn:orm:book:0642572230333/files/images/annot_page218_1.jpg)

_Figure 8-10: The relationship between articles and article chunks in parent-child retrieval_

The _parent document_ refers to the source article from which a small chunk originated. This could also be a much larger chunk representing a paragraph, section, or chapter, for example. That way, when a query returns a small related article chunk, it can use the parent ID to retrieve the original article.

#### **Query Rewriting/Expansion**

Our users aren’t likely to ask questions in exactly the way we planned. A user might type “reset pw” or use awkward wording. Query rewriting (also known as _query reformulation_) turns their questions into clearer, more complete queries like “How do I reset my password?” so relevant documents aren’t missed.

We ask an LLM to rewrite or add variants of the user’s question before retrieval. This helps improve retrieval when the original wording is vague or shorthand. You can look into a variety of strategies:

- **Rewrite-retrieve-read** Converts the user’s query to a cleaner query to search with
- **Multi-query retrieval** Creates several alternate phrasings and searches with all of them for broader coverage
- **HyDE** “Hypothetical” queries that have the LLM invent a short “imaginary answer,” then use it to search for matching documents

In short, query rewriting adds a quick LLM rewrite step in front of your retriever that makes vague or shorthand questions easier for your system to understand and answer correctly. Just keep in mind that these techniques increase token usage and add another call to an LLM, which will impact response times.

#### **Re-Ranking/Reordering**

Remember the lost-in-the-middle effect? LLMs tend to focus mostly on what comes first and last in a long prompt. Anything buried in the middle may be completely ignored. The simple work-around is to shuffle or filter your search results so the most important chunks land at the top (or bottom) and, if possible, remove the useless chunks entirely (such as near-identical or unrelated chunks). Here are the steps:

- **Reorder** Move the chunks with the highest similarity scores or the most recent chunks to the front of the prompt.
- **Re-rank** Send the initial search hits through a smarter scoring model, then sort by that new score.
- **Compress** Drop low-value chunks entirely or merge them into a shorter summary.

By reordering or trimming the context, you keep the crucial information where the model actually pays attention and boost answer quality without changing the model itself. Keep in mind that calling an additional model can add infrastructure complexity, increase costs, and impact performance.

#### **Hybrid Retrieval**

We spent a lot of time talking about the advantages of vector search over keyword searches, but when you rely on only embeddings, you might miss exact keyword matches. This is especially true with very specific terms like _HTTP 500_ log lines and _internal server error_. This could be content like source code snippets, part numbers, or medical codes.

Hybrid retrieval runs keyword and vector searches and blends the results, giving you the best of each world. This strategy generally needs to be combined with some sort of re-ranking to properly order the results.

#### **LLM Evaluator**

We use an LLM evaluator (often called _LLM-as-a-judge_) to score faithfulness, coverage, and formatting. Think of this as the quality gate in your RAG pipeline. After you retrieve context and draft one or more answers, you hand the LLM three things: the original question, the retrieved passages, and the candidate output(s).

The LLM (the judge) checks faithfulness to sources, task fit, coverage, and formatting/safety rules. It returns a structured verdict (usually JSON) with scores, tags (hallucination, missing citation, leakage), and a pass/fail or A-versus-B pick. You can use that verdict to re-rank candidate responses, block a response, or kick off fixes like query reformulation or another retrieval pass.

#### **Agentic RAG**

For complex questions, you may need to loop through “think, retrieve, think” cycles or call extra tools. In fact, if you use the latest models in Chat-GPT, you will see this approach in action. These models use a CoT approach to step through what is needed to respond to a prompt. They will use data sources or tools to retrieve necessary information, evaluate and grade the information, determine relevance, and loop until they are able to draft an answer. We will talk more about agents in [Part V](https://learning.oreilly.com/library/view/the-developers-guide/0642572230333/xhtml/part5.xhtml).

#### _**Data Quality and Security**_

Your RAG system will be only as good as the data you feed it. Every retrieval trick in this chapter—including better chunking, smarter retrieval, re-ranking, and citations—depends on having clean, current, and trustworthy sources. Treat data quality like a first-class feature of your pipeline, not an afterthought.

Start with _authoritative_ inputs and keep them that way. Normalize formats, strip boilerplate, and aggressively deduplicate at both the document and chunk level so you don’t flood the retriever (or the model) with near-duplicates. Capture useful metadata (version, date, product, permissions, URL), because those fields power better filtering, ranking, and citations.

Enforce freshness with a clear policy: Time-box what’s considered current, archive stale copies, and re-index on a schedule. Measure what matters—log queries, retrieved chunks, and citations; track hit-rate, latency, and answer quality. When answers are wrong, observability is how you debug the pipeline, not the prompt.

> ### **WARNING**
> 
> _RAG replicates your data. Indexes, caches, and chunk stores are all additional places where sensitive content can live. Apply the same (or stricter) security controls you use for the source of truth: encryption in transit and at rest, least-privilege access, per tenant isolation, and auditable changes. Never assume a vector database is “just embeddings.” Those vectors can be used to reconstruct text._

Security starts before ingestion. Avoid pushing secrets/PII into any third-party service unless proper data security agreements and encryption requirements are in place. If you must handle sensitive content, prefer local or private endpoints (like the Ollama and Chroma setup you built) and secure access through your application, not the database. You can create traceability by logging who searched what, which chunks were returned, and which sources were cited.

If you remember nothing else, _better data beats bigger prompts_. Build your RAG pipeline to prefer clean, current, and authorized content—and protect that content everywhere it flows.

### **Summary**

LLMs bring powerful general-purpose capabilities but know nothing about your private content, wikis, tickets, email, or databases. RAG solves this by feeding exactly the right pieces of your data to an LLM at query time.

In this chapter, we built a complete RAG pipeline with LangChain and Ollama. We started by using a document-based chunking strategy to ingest and chunk documentation. We then took those chunks, embedded them using the high-performance mxbai-embed-large model, and indexed them in Chroma.

The next step was completing our RAG pipeline. We created prompt templates that grounded our LLM in system instructions and included placeholders for context and user questions. We combined these prompt templates with a vector database (Chroma) to retrieve relevant documentation, augment a prompt, and stream an LLM response. Finally, we explored advanced RAG topics: smarter chunking (such as parent-child retrieval), metadata-aware hybrid search, re-ranking/reordering to mitigate the lost-in-the-middle effect, and other architectural variants like cache-augmented or API-augmented RAG. With these patterns, you can tailor your own RAG solutions.
