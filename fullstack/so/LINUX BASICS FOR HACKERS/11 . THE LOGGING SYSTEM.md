For any Linux user, it’s crucial to be knowledgeable in the use of logfiles. _Logfiles_ store information about events that occur when the operating system and applications are run, including any errors and security alerts. Your system will log information automatically based on the series of rules that I will show you how to configure in this chapter.

As a hacker, you should be aware that a system’s logfiles can be a trail to your target’s activities and identity, but they can also be a trail to your own activities on someone else’s system. A hacker, therefore, needs to know what information they can gather, as well as what can be gathered about their own actions and methods in order to hide that evidence.

On the other side, anyone securing Linux systems needs to know how to manage the logging functions to determine whether a system has been attacked and then decipher what actually happened and who did it.

This chapter shows you how to examine and configure logfiles, as well as how to remove evidence of your activity and even disable logging altogether. First, we’ll look at the daemon that does the logging.

## The journalctl Utility

Since the publication of the first edition of _Linux Basics for Hackers_, the logging system in most Linux distributions, including Kali, has changed. Previous versions had used the syslog daemon (also known as syslogd). The newer Linuxes use a software suite known as systemd, which is intended to standardize how Linux works across all distributions of Linux.

Systemd has a similar control for logging known as journalctl (a _journal_ in computer-speak is a place where the computer stores activities and events—in other words, a _logging system_). This journalctl utility makes retrieving and viewing logfiles much easier.

One of the key differences between the older syslogd and journald is that syslogd stored logfiles as simple text files, while journald stores binary files (zero and ones). This means that the end user (you) has a much easier time interpreting the logfiles and searching them. The older-style syslog files were notoriously hard to search and interpret. System administrators often had to write scripts to search and sort the logs, but journalctl can now do these types of tasks automatically. To sum up, journalctl will make your life, as a newcomer to Linux, much easier.

Let’s take a look at it. When we simply enter the command journalctl at the prompt, _all_ of the logs are displayed on the screen via the more command:

## Log Priorities and Facilities

Logging and logfiles reflect the different priorities and facilities of the operating system and the system administrator. Some logs are very important and are given a priority of 0 or emerg(ency), while others are less important and are given priorities of 6 (info) or 7 (debug). The system administrator can determine which logs have which priority. In addition, the system administrator can select which priority logs they want to view.

Here is a list of the logging system priorities:

- emerg (0)
- alert (1)
- crit (2)
- err (3)
- warning (4)
- notice (5)
- info (6)
- debug (7)

To view the highest-priority logfiles, we can construct a journalctl query using the -p option, such as:

```
kali> journalctl –p "emerg"

Jun 30 22:59:13 kali kernel: watchdog: BUG: soft lockup - CPU#0 stuck for 23s! [swapper/0:0]
Jul 01 03:28:06 kali kernel: watchdog: BUG: soft lockup - CPU#0 stuck for 24s! [swapper/0:0]
Jul 02 10:10:26 kali kernel: watchdog: BUG: soft lockup - CPU#0 stuck for 21s! [swapper/0:0]
--snip--
```
Notice that we can also use the priority number such as 6 (info):

```
kali> journalctl –p 6
```

The journalctl utility also enables us to view the logs of a specific service using the -u option. To view the logs associated with the apache2 web server, we can construct a query such as:

```
kali> journalctl –u apache2

May 28 14:25:48 kali systemd[1]: Starting apache2.service - The Apache HTTP Server...
May 28 14:25:48 kali apachectl[118241]: AH00558: apache2: Could not reliably determine...
May 28 14:25:48 kali systemd[1]: Started apache2.service - The Apache HTTP Server.
May 29 00:00:31 kali systemd[1]: Reloading apache2.service - The Apache HTTP Server...
--snip--
```

This query can be used to find the logs of any service in Linux simply by appending the -u option followed by the name of the service.

## journalctl Queries

One of the major advantages of journalctl is the ability to query the logs specifically for events, users, and time, as journalctl has a query language that is very similar to normal human language. For instance, if I wanted to see only the events in the last 24 hours, I can query:

```
kali> journalctl –q –-since "24 hours ago"
```

[Figure 11-1](https://learning.oreilly.com/library/view/linux-basics-for/9798341655102/xhtml/ch11.xhtml#fig11-1) shows the output.

![[../../assets/Pasted image 20260522205336.png]]
_Figure 11-1: The output from a journalctl query_

This query quietly retrieves the last 24 hours of log events. In this case, the -q flag is for “quiet.” It suppresses messages that are very noisy and may leave traces of your activity.

The journalctl utility also enables you to search for events by user. As you know, the root user in Linux is designated with the user ID of 1000. So, we can search for events linked to the root user by building the journalctl query like this:

kali> journalctl _UID=1000 –-since "24 hours ago"

[Figure 11-2](https://learning.oreilly.com/library/view/linux-basics-for/9798341655102/xhtml/ch11.xhtml#fig11-2) shows the output.

This will help determine whether the root user is online and what they may be doing (only if it triggers a log).

The kernel of any operating system is its heart. It controls the entire operating system, and it is what makes Linux, Linux. If the kernel is having problems, we probably want to be aware of that. To view kernel logs, we can use the -k option (kernel). For kernel logs within the last 24 hours, we can enter:

## Using journalctl to Cover Your Tracks

If you have compromised a system, you want to make certain that you don’t leave evidence behind that can be traced back to you. Remember, the best hack is the one that the target never knew happened!

If we compromised the apache2 web server to take control of the system, the most important place to clean up are the apache2 logs. We can do this with journalctl, but here we will need root privileges using the sudo command:

```
kali> sudo journalctl –u apache2 –-vacuum-time=1d
```

This command will delete all the logs associated with the apache2 web server in the past day:

```
Vacuuming done, freed 0B of archived journals from /var/log/journal.
Deleted archived journal /var/log/journal/d3ab02d2e96b4806ad45511cf7593a25/system@0006...
Deleted archived journal /var/log/journal/d3ab02d2e96b4806ad45511cf7593a25/user-1000@0...
--snip--
```

A better and more secure solution is to shred the logfiles. With other file deletion systems, a skilled investigator is still able to recover the deleted files (deleted files are simply made available to be overwritten by the file-system; they still exist until they are overwritten). But suppose there was a way to delete the file and overwrite it several times, making it much harder to recover. Lucky for us, Linux has a built-in command, appropriately named shred, for just this purpose.

To understand how the shred command works, take a quick look at the help screen by entering the following command:

```
kali> shred --help
Usage: shred [OPTION]...FILE...
Overwrite the specified FILE(s)repeatedly in order to make it harder
for even very expensive hardware probing to recover data
--snip--
```

The full output on your screen shows that the shred command has many options. In its most basic form, the syntax is simple:

```
shred <FILE>
```

On its own, shred will delete the file and overwrite it several times—by default, shred overwrites four times. Generally, the more times the file is overwritten, the harder it is to recover, but keep in mind that each overwrite takes time, so for very large files, shredding may become time-consuming.

Two useful options to include are the -f option, which changes the permissions on the files to allow overwriting if a permission change is necessary, and the –n option, which lets you choose how many times to overwrite the files. As an example, we’ll shred all the logfiles in _/var/log/journal/subdirectory/*.*_ 10 times using the following command:

```
kali> shred -f -n 10 /var/log/journal/subdirectory name*.*
```

We need the –f option to give us permission to shred auth files, and we follow the –n option with the desired number of times to overwrite. After the path of the file we want to shred, we include the wildcard asterisk so we’re shredding everything in the subdirectory. Now try to open a logfile:

kali> mousepad /var/log/journal/filename

Once you’ve shredded a file, you’ll see that the contents are indecipherable gibberish, as shown in [Figure 11-3](https://learning.oreilly.com/library/view/linux-basics-for/9798341655102/xhtml/ch11.xhtml#fig11-3).

![[../../assets/Pasted image 20260522205415.png]]
_Figure 11-3: A shredded logfile_

Now if the security engineer or forensic investigator examines the logfiles, they will find nothing of use because none of it is recoverable!

## Disabling Logging

Another option for covering your tracks is simply to disable logging. When a hacker takes control of a system, they could immediately disable logging to prevent the system from keeping track of their activities. This, of course, requires root privileges.

To disable all logging, the hacker could simply stop logging by configuring journalctl to send logs to null. This means that instead of writing the logs to a storage device such as a hard drive, the system will send the logs into a null place (nowhere). We can accomplish this by opening and editing the journal daemon configuration file. It is at _/etc/systemd/journald.conf_. You can open with any text editor, but here I opened it with mousepad preceded by sudo to gain root privileges:

kali> sudo mousepad /etc/systemd/journald.conf

  This file is part of systemd.
```
#
#  systemd is free software; you can redistribute it and/or modify it under the
#  terms of the GNU Lesser General Public License as published by the Free
#  Software Foundation; either version 2.1 of the License, or (at your option)
#  any later version.
#
# Entries in this file show the compile time defaults. Local configuration
# should be created by either modifying this file (or a copy of it placed in
# /etc/ if the original file is shipped in /usr/), or by creating "drop-ins" in
# the /etc/systemd/journald.conf.d/ directory. The latter is generally
# recommended. Defaults can be restored by simply deleting the main
# configuration file and all drop-ins located in /etc/.
#
# Use 'systemd-analyze cat-config systemd/journald.conf' to display the full config.
#
# See journald.conf(5) for details.

[Journal]
#Storage=auto
#Compress=yes
--snip--
```

Note the line at the end that says #Storage=auto. Change that line to Storage=null and delete the comment mark before it (#). Now save the file and restart journald:

```
kali> sudo systemctl restart system-journald
```

This will stop and start journald, and when it restarts, it will use the new configuration file that sends all logs to null.

Now Linux will stop generating any logfiles until the service is restarted, enabling you to operate without leaving behind any evidence in the logfiles!

## Summary

Logfiles track nearly everything that happens on your Linux system. They can be an invaluable resource in trying to analyze what has occurred, whether it be a malfunction or a hack. For the hacker, logfiles can be evidence of their activities and identity. However, an astute hacker can remove and shred these files and disable logging entirely, thus leaving no evidence behind.
